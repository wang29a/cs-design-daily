# Unix 管道：怎样让互不认识的程序协作

这篇补上 2026 年 10 月 1 日的内容。我们从一个具体需求出发：你做了一个个人知识库，服务产生了一份日志，现在想知道出现了多少行错误。先只统计错误行数，暂时不引入排序，否则会把管道本身和排序算法的行为混在一起。

假设日志只有四行：

```text
INFO opened note
ERROR missing title
ERROR index unavailable
INFO saved note
```

最直观的实现是写一个完整程序：打开文件，逐行读取，判断是否以 ERROR 开头，再增加计数器。这个程序可以正确工作，但明天你想把错误行交给另一个程序分析，后天想改成统计警告，你就得继续扩展它。筛选、统计、输入来源和输出去向，逐渐纠缠起来。

也可以把任务拆开：让筛选程序写出一个临时文件，然后让统计程序读取。这样复用了已有工具，却新增了临时文件的命名、清理和生命周期问题。更关键的是，两者之间的协作被表达成“先产生一份完整文件，再消费它”。我们希望表达的其实更简单：前一个程序不断给出结果，后一个程序不断接收结果。

Unix 的解决方案需要两块设计同时成立。程序通过标准输入、标准输出使用稳定接口；Shell 能在启动程序时替它们安排这些接口的去向。于是可以写：

```sh
grep '^ERROR' app.log | wc -l
```

grep 的职责是选择符合条件的行，wc 的职责是统计换行符。两者没有彼此专用的通信代码。这里的关键洞察是：程序不一定要知道自己正在和谁协作，只需要遵守一个足够稳定的输入输出契约。

要理解它为什么成立，需要先把“文件描述符”与“文件”分开。文件描述符是一个进程用来访问已打开 I/O 对象的整数编号。编号 0 通常用于标准输入，1 用于标准输出，2 用于标准错误。编号的用途是约定，编号背后连接什么对象则可以调整。因此，向编号 1 写入，并不等于向屏幕写入；也可能向文件或管道写入。这是接口层提供的自由度。[MIT《xv6》的文件描述符与管道说明](https://pdos.csail.mit.edu/6.1810/2025/xv6/book-riscv-rev5.pdf)

管道在内核中提供一个缓冲区，以及一个读端和一个写端。pipe(p) 把读端描述符放进 p[0]，写端放进 p[1]。接下来 Shell 创建两个子进程。fork 之后，子进程继承的描述符仍指向同一条管道，数据因此可以跨进程传递。[pipe 系统调用手册](https://man7.org/linux/man-pages/man2/pipe.2.html)

我们用教学伪代码压缩这一过程。假设标准输入输出已经打开，p 中的描述符不会碰巧等于 0 或 1，并省略错误处理与等待子进程的代码：

```c
pipe(p);

// 左边的子进程
dup2(p[1], 1);
close(p[0]);
close(p[1]);
exec_grep();

// 右边的子进程
dup2(p[0], 0);
close(p[0]);
close(p[1]);
exec_wc();

// 父进程启动两边后
close(p[0]);
close(p[1]);
wait_for_children();
```

dup2(p[1], 1) 并没有把数据复制给编号 1，而是让编号 1 也引用那条管道的写端。随后关闭 p[1]，编号 1 仍然保留这份引用。右边同理，把编号 0 接到读端。这个区别非常重要：重新连接的是描述符与对象之间的关系，程序的筛选和统计逻辑没有改变。[dup2 系统调用手册](https://man7.org/linux/man-pages/man2/dup.2.html)

现在沿着一次真实数据流推演。grep 读到第一行 INFO，丢弃它；读到第二行 ERROR，把该行的字节写入标准输出。由于标准输出已经接到管道，这些字节进入内核缓冲区。wc 从自己的标准输入读到字节，发现一个换行符，计数加一。第三行让计数变成二，第四行被 grep 丢弃。最终 grep 结束，wc 输出 2。

但这段推演还有一个没有解释的地方：wc 怎么知道以后不会再有数据？管道为空可能只是上游暂时还没写，并不代表整个输入已经结束。对普通阻塞管道而言，所有写端引用都关闭，并且缓冲区已经读空之后，read 才返回 0，也就是 EOF。空缓冲区与输入结束是两种不同状态。[管道 I/O 语义](https://man7.org/linux/man-pages/man7/pipe.7.html)

这解释了为什么父进程也必须关闭自己继承下来的写端。假如 grep 已经结束，父进程却仍然持有一个写端，内核只能判断“未来仍有人可能写入”。wc 于是继续等待，而父进程又可能正在等待 wc 结束。没有任何数据处理代码出错，却因为一份多余引用，整个计算无法收尾。关闭描述符是通信协议的一部分。

再考虑速度差。假设我们的教学模型把缓冲区设为 8 字节，上游每秒产生 10 字节，下游每秒消费 2 字节。每秒净增加 8 字节，缓冲区很快填满。通常的阻塞写入随后等待，下游取走一些字节才会让上游继续。这个等待把下游的处理能力传回了上游。实际管道容量与平台有关，不能把模型中的 8 字节当成系统默认值。

因此，有界缓冲区解决的既是存储上限，也是速度协调问题。如果采用无限队列，差额只会变成越来越多的内存占用；如果完全不允许缓冲，又会让两边过度同步。管道选择一个中间状态：允许有限程度的解耦，达到边界后用等待约束生产者。这就是背压的具体含义。

这个设计也有明确代价。普通管道只提供字节流，不保证一次 write 对应一次 read。假设发送方连续写入 ABC 和 DEF，接收方可能先读到 AB，再读到 CDEF；双方必须依靠换行、长度字段或其他格式恢复记录边界。内核缓冲区、系统调用和进程调度也有成本。将任务拆成更多程序，可能让复用更方便，也可能增加执行开销。

还有一个常见误解需要排除。把 sort 放进管道，并不意味着排序能够一边读一边立即给出最终有序结果。如果还可能读到更小的元素，现在输出的最小值就未必真是全局最小。管道提供连接和传输能力，算法能否提前产出结果，则取决于算法自身的依赖。GNU sort 也提供临时存储相关选项，但这里没有测量 macOS sort 的具体缓冲行为。[GNU sort 文档](https://www.gnu.org/software/coreutils/manual/html_node/sort-invocation.html)

以后看到异步数据处理系统，可以沿着同样的顺序追问：组件间传递什么，边界由谁解释，缓冲上限是多少，慢消费者如何约束生产者，关闭或取消又怎样传递？这些问题共同决定“可以连接”能否进一步变成“能够长期正确协作”。

读到这里，可以用一个反事实检验理解：如果让 wc 自己还持有管道写端，grep 退出以后，wc 能否确认输入结束？答案是不能，直到那份写端引用也被关闭。能够解释这个等待，而不只记住竖线符号，就已经触及管道的设计核心。

本篇在本机执行了四行日志的 grep→wc 管道，输出确认为 2；也单独创建了管道，验证读取完数据后，只要还保留一个复制出来的写端，读端就未到 EOF，关闭最后写端后读取返回空字节。这个实验验证了关键现象，没有测量性能。完整 Shell 的创建进程顺序、错误传播、信号与优化比伪代码更复杂；本篇没有声称追踪了某个 Shell 的全部内部调用。
