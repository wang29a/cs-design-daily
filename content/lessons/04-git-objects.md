# Git：怎样让完整版本共享同一份未变化内容

这篇补上 2026 年 10 月 4 日的内容。知识库现在有一百篇笔记，你每天只修改其中几篇，却希望能够恢复任意一个已经提交的版本。保存完整目录最容易理解，但如果每个版本都复制所有文件，大量未变化内容会被反复存储。

另一种自然的想法是只保存差异：版本二记住对版本一改了什么，版本三记住对版本二改了什么。这样可能节省空间，但如果把历史语义完全定义成一条补丁链，恢复某版本就要沿着依赖关系解释这些变化。我们希望既有完整快照的清楚语义，又不必每次复制完整内容。

Git 的对象模型通过内容寻址和引用共享解决这组矛盾。对象标识由对象类型、长度与内容等信息参与计算；一份 blob 对象保存文件内容，文件名并不在 blob 内。tree 对象记录名字、模式和对应的 blob 或子 tree，commit 对象再指向根 tree，并记录父提交和提交信息。[Git Objects 官方教材](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

这里有一个很值得停下来理解的分离。文件名回答“这份内容在这个目录里叫什么”，内容标识回答“这到底是哪份内容”。名字相同，内容可以不同；名字不同，内容也可以相同。身份与位置不再绑在一起，因此不同版本可以共享未变化的对象。

为了避免一下引入一百篇笔记，我们先只保留两篇：

```text
notes/
    memory.md  内容为 M0
    network.md 内容为 N0
```

第一次提交 C0 的根 tree 引用 notes 的目录 tree；这个目录 tree 的两条记录分别指向 blob(M0) 与 blob(N0)。C0 又记录自己的作者、提交者、说明等信息。用括号中的文字表示内容对象，省略具体哈希值，能够先把注意力放在关系上。

现在只把 memory.md 改成 M1。Git 写出新的 blob(M1)，新的 notes tree 把 memory.md 指向它，但 network.md 仍指向原来的 blob(N0)。根目录的引用关系发生变化，也需要新的根 tree。新提交 C1 指向这个新根，同时把 C0 记录为父提交。

因此，修改沿着“变更文件到根目录”的路径产生新对象，而没有变化的内容可以继续共享。C1 表达完整版本，因为从它的根 tree 能找到该版本的全部文件；它也没有重新保存 N0，因为那份内容已经存在。完整的版本语义与内容复用可以同时成立。

这个推演还能解释目录层次的意义。如果改的是 notes/system/memory.md，发生变化的不只有 blob，还包括引用它的 system tree、引用 system 的 notes tree，以及更上层受影响的 tree。变化沿着引用关系向上影响对象标识。我们可以把它理解成一张由内容决定标识的对象图，而不必把“一个提交”想象成一个打包全部文件的新目录。

接下来创建一个名为 experiment 的分支。它不需要复制 C0、C1 或它们引用的文件对象；分支引用只要指向 C1 就足够。后续在这个分支生成 C2，再让 experiment 指向 C2。main 仍然可以指向 C1。稳定对象与可移动名字承担不同职责。[Git References 官方教材](https://git-scm.com/book/en/v2/Git-Internals-Git-References)

由此也能理解一个容易困惑的现象：两个提交拥有完全相同的文件树，提交标识仍然可能不同。因为 commit 对象不只有文件树，还包含父关系与提交元数据。文件内容相同不等于历史事件相同。相反，多个提交引用同一个 blob，则可以精确表达它们共享那份文件内容。

这里要避免另一个常见说法：“Git 保存快照，所以从来不保存差异。”快照描述的是逻辑对象关系，物理存储又有自己的优化层。Git 的 packfile 可以用对象间的差量压缩保存数据，取出对象时再重建。对象模型保持不变，不意味着磁盘必须为每个对象始终保存一份独立、完整的原始字节文件。[Git Packfiles 官方教材](https://git-scm.com/book/en/v2/Git-Internals-Packfiles)

所以你可以把这个系统理解成两份契约。上层对使用者承诺：某个提交描述一个可以解析的版本及其历史关系。下层负责：怎样压缩、组织和读取对象，才能减少空间和 I/O。它们有联系，但把它们混在一起，会很难解释为什么对象能被重新打包却保持同一个标识。

再看代价。不可变对象方便共享和比较，却也意味着旧对象不会因为新版本出现就自动消失。系统要判断对象是否仍被引用，并维护存储。内容寻址的可靠性依赖所采用的哈希与完整性处理，不能把标识相等当成脱离威胁模型的数学保证。压缩对象还可能增加读取时的重建工作。

更实际的限制是，它不能替你判断两段文字是否表达同一件事。哪怕两个文件含义相同，只要对象字节不同，标识也可能不同；两个分支改了相互冲突的内容，哈希只能准确指出对象，无法替人决定哪种业务语义正确。数据身份问题与语义合并问题被分别处理。

这个设计可以迁移到内容缓存与去重存储。对于不再原地修改的数据，用内容标识让多处引用共享同一份对象；把“当前使用哪个版本”放到较小、可更新的引用中。不过，一旦对象背后还存在可变外部资源，例如某个随时变化的 URL，就不能仅凭保存 URL 的对象来宣称外部内容也被冻结了。

最后做一个反事实推演：如果修改了 blob 的原始内容，却让旧标识保持不变，会破坏什么？旧提交通过这个标识读到的内容会改变，历史不再稳定，标识也不再能代表相应内容。Git 的对象模型要求变化形成新的对象身份，而历史引用继续解释原来的对象。

这就是这篇要理解的核心关系：内容对象保持稳定，目录对象安排名字，提交对象安排历史，分支引用安排当前入口。只有把四种职责各自追清楚，才能从原理解释版本共享与分支成本。

本篇在独立的临时 Git 仓库创建了两个文件与两次提交，确认改动文件的 blob 标识变化、未改文件的 blob 标识保持一致；新建分支也确实指向已有提交。正文的 M0、N0、C0 等记号仍是教学命名。具体对象数量与压缩布局取决于目录结构、已有对象及存储维护；本篇没有声称测量大型仓库的空间收益。
