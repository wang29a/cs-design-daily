# RocksDB：新文件写完，为什么还不能删旧文件

昨天我们看到，RocksDB 把更新先积累在内存中，再写成不可变的 SST 文件，后台 compaction 将多个文件合并，以整理旧版本、减少读取负担。但整理带来一个新的系统问题：新文件已经算对了，能不能立刻删除输入文件？此时一个读者可能刚刚取得旧文件集合，机器也可能在替换途中掉电。今天要吃透的是，RocksDB 怎样把“算出新结果”推进为“可以使用、可以恢复、可以回收”的完整过程。

先沿用昨天的教学例子。S1 包含 `a@1=10,b@2=20`，S2 包含 `b@3=21,c@4=30`，S3 包含 `a@5=DEL`；`@` 后面是修改序号，DEL 是删除标记。假设没有更旧快照、没有其他相关文件，此次完整合并得到 S4：`b@3=21,c@4=30`。在序号 5 的视图里，合并前后都应得到 a 不存在、b 为 21、c 为 30。本文只推演一个列族、一次普通 SST 合并，暂不加入新写入、其他后台任务、blob 文件或特殊恢复配置；图是教学模型，没有执行 RocksDB 故障注入或测量性能。

最自然的办法，是合并期间锁住数据库：等读者结束，生成 S4，删除 S1—S3，换好文件列表再放行。对小型离线整理，这个办法足够直接。但服务中的合并可能持续很久，把整个过程放进全局临界区，会让请求替磁盘整理付出等待成本。更麻烦的是，锁只能约束活着的线程。删完旧文件、还没可靠记下新文件就掉电，重启时锁已经消失，恢复程序却可能仍要求打开 S1。即使没有并发错误，也会得到无法恢复的数据库。

要拆开矛盾，先改变“数据库当前状态”的表示。目录里有哪些文件，不等于数据库现在由哪些文件组成。RocksDB 用 Version 表示一个列族在某个阶段采用的 SST 集合；这里记旧集合为 V0={S1,S2,S3}，新集合为 V1={S4}。读者取得一个集合，便沿着它完成读取；更新者另建集合，再让后续请求从新集合进入。官方文档说明，读取可能持有旧 Version，通常通过同时包含 memtable 和 Version 的 SuperVersion 间接持有。本文只画 SST 部分。[RocksDB 的存活文件与 Version](https://github.com/facebook/rocksdb/wiki/How-we-keep-track-of-live-SST-files)

观察下面的图：新读者改走 S4 后，旧读者究竟还依赖什么？

![教学图：发布 V1 后，新请求 N 持有 V1 并访问 S4，旧迭代器 R 仍持有 V0 并访问 S1、S2、S3；箭头表示持有关系，两条路径在序号 5 都输出 b=21、c=30。](assets/figures/rocksdb-version-readers.svg)

这里的 R 是发布前创建、仍未关闭的迭代器，读取序号 5 的状态。它持有旧文件集合，并不意味着它要读序号 2 的旧数据。**Version 管物理文件集合，Snapshot 管逻辑修改的可见边界**，二者不能混为一谈。S4 省去旧记录和删除标记的前提，仍是不存在需要这些历史记录的旧快照；保留 V0 则是在保护已经进入旧读取路径的用户。官方迭代器文档说明，未指定显式快照时，迭代器也提供创建时的一致视图，并通过保留资源支持它。[迭代器的一致性与生命周期](https://github.com/facebook/rocksdb/wiki/Iterator)

可是，内存里换成 V1，并不能告诉掉电后的进程该用谁。RocksDB 另用 MANIFEST 记录文件集合的变化。此次合并形成一个逻辑上的 VersionEdit：删除 S1、S2、S3 的成员资格，加入 S4。它记录的是一次完整替换的意图，而不是要求文件系统把四个文件操作变成一条物理原子操作。恢复时读取这些元数据来重建集合，不是把目录中的 SST 全部并起来。CURRENT 文件用于指向所用的 MANIFEST；并不是每次合并都改写 CURRENT。[MANIFEST 的职责和格式](https://github.com/facebook/rocksdb/wiki/MANIFEST)

这给出了一个关键顺序：先让新结果可靠存在，再可靠记录它成为成员，最后在正常运行的进程中发布新集合。核对 RocksDB 源码固定提交 `72beaf8` 的普通成功路径，可以看到输出文件的同步与关闭、输出目录同步，随后安装阶段构造输入删除和输出加入的 edit；MANIFEST 追加与同步成功之后，才安装新的 Version。目录同步也有意义：文件数据已写到介质，不代表重启后一定能通过目录找到这个文件。这里假设底层文件系统和设备履行同步承诺，不能把它推广成任意硬件故障下都不会丢失。[输出文件与目录处理](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/compaction/compaction_job.cc#L2092)、[构造并安装替换 edit](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/compaction/compaction_job.cc#L2372)、[同步 MANIFEST 后安装 Version](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/version_set.cc#L6274)

把断电位置放进这条顺序，恢复程序会选什么？

![教学图：S4 同步完成而 edit 尚未追加时断电，恢复 V0；完整 edit 同步完成而内存尚未发布时断电，恢复 V1；图中的边界不覆盖追加后但同步结果未知的区间。](assets/figures/rocksdb-publication-crash.svg)

第一处断电发生在 S4 已可靠生成、edit 尚未追加时。恢复仍使用 V0，S4 即使留在目录里，也没有取得数据库成员资格，是待清理的多余输出。第二处发生在完整 edit 已可靠记录、内存切换尚未发生时。恢复使用 V1，因为进程内存和旧读者都不会跨重启存活，已经持久化的元数据才是恢复依据。两种状态的答案仍是 b=21、c=30。必须留出一个证据边界：追加过、但同步是否成功尚不清楚时，记录可能已经落盘，不能武断地宣布一定恢复 V0；日志损坏的处理也不能概括成“都自动忽略”。这里分析的是图中两个明确边界。

由此可以自己推出持久性不变量：恢复元数据所承认的文件，必须已经可靠存在；仍可能被恢复采用的旧集合，也不能提前失去文件。如果把顺序反过来，先持久化“加入 S4”，再同步 S4，掉电后元数据就可能指向不存在或不完整的文件。若先删 S1—S3，再记下替换，恢复会要求已经被删掉的输入。新旧数据都算对并不能挽救这两种错误，错误发生在“谁获得使用资格”的协议里。

再回到活着的进程。发布 V1 后，新请求 N 使用 S4，R 仍沿 V0 读取 S1—S3，二者无需等对方完成。RocksDB 对 Version 和文件维护引用关系；一个文件不再被当前或仍存活的旧 Version 需要，才可能成为待删除对象。迭代器、短暂的 Get、正在运行的 compaction 都可能保留相关资源，所以“不是当前成员”远远不够。[过期文件何时可以删除](https://github.com/facebook/rocksdb/wiki/Delete-Stale-Files)

现在观察 R 关闭前后：哪个条件改变，才让旧文件真正退出系统？

![教学图：发布 V1 时当前入口放开 V0，但 R 仍持有 V0；R 关闭且其他持有者都结束后，V0 与旧文件才满足回收条件；符合条件与磁盘实际删除是两个时刻。](assets/figures/rocksdb-retirement.svg)

图中省略了真实实现的多层引用计数，画的是所有权关系，不是精确计数。R 关闭，且没有其他读取、合并或存活版本再需要旧文件，S1—S3 才具备回收条件；删除可能由随后清理工作执行。取得引用本身也必须受保护：不能先裸读 V0 指针，再慢慢增加计数，否则更新线程可能恰好在两步之间释放 V0。源码中的当前版本安装与引用转换属于有同步约束的路径，不是一句“加引用计数”就自动正确。[当前 Version 的安装与引用处理](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/version_set.cc#L5844)

这个设计值得欣赏的地方，是把三种责任分给了合适的表示：不可变文件允许读者继续依赖旧结果，持久化 edit 决定重启后承认哪个集合，引用关系决定运行中什么时候可以销毁旧资源。后台整理因而能够改变物理布局，而不要求正在读取的请求一起改变路径。代价也清楚：一段时间内新旧文件同时占空间；长寿命迭代器会推迟释放；系统承担同步、引用与清理的复杂性。重启后内存引用已消失，可以重新清理无用文件，但正常运行中的清理还必须保护正在生成、尚未加入 MANIFEST 的输出，不能简单地“目录减去当前集合”。

留下一个推演：如果 R 在发布后再停留一小时，能不能继续创建使用 V1 的新读者？这期间额外空间由谁承担？先沿图中的引用关系作答，再考虑是否需要限制应用持有迭代器的时间。这里没有实测一小时的空间增长，只有判断资源归属所需要的状态模型。

Linux 的 RCU 也把“从入口移除旧对象”和“回收旧对象”分开：更新入口后，先前进入的读者仍可使用旧对象，等相关读侧临界区结束再释放。共同结构是，禁止新的使用者进入旧路径，并不等于旧使用者已经离开。但 RCU 通常以宽限期判断读者结束；这里围绕文件与 Version 的持有关系，还多了一份持久化恢复协议。RCU 的内存生命周期规则不能替代 MANIFEST，也不能证明磁盘状态可靠；这只是结构上的比较，不是在声称 RocksDB 用 RCU 实现了本文机制。[Linux RCU 的移除与回收阶段](https://docs.kernel.org/RCU/whatisRCU.html)

以后遇到热更新、索引重建或存储迁移，都可以沿今天的例子检查：新结果是否先准备完整，哪个记录赋予它使用资格，旧用户靠什么安全结束，故障后又由谁重新判定成员。一个系统的替换做得漂亮，往往不是因为切换动作特别短，而是因为它把这些不同的完成条件讲清楚、分别兑现了。
