# Kafka 删掉旧消息后，为什么仍能重建最新状态

订单看板把每个订单的当前状态缓存在本地，Kafka 负责传递更新。机器重启、缓存清空后，它希望重新读日志，恢复看板。订单 77 一个月没有变化，仍然有效；订单 42 今天改了三次。若统一只留最近七天的消息，42 能恢复，77 却可能凭空消失。若保留全部变化，一个订单反复修改，又会让恢复与存储不断增长。今天要理解，Kafka 怎样删去一部分历史，同时留下恢复当前状态的依据。

此前讨论的是逐条事件与消费进度。现在换一种消息契约：生产者发送“某订单的完整新状态”，消费者按键覆盖本地表。主题仍分成分区，broker 仍追加日志，消费者仍按 offset 顺序拉取；变化发生在后台日志清理层。本文固定 Kafka 4.1.0、本地存储、仅启用 `cleanup.policy=compact`，关闭时间或大小删除这一并列策略，采用非事务、有非空键的普通记录。所有同键更新使用相同键字节并进入同一分区。以下编号、段界和清理时序都是教学设定，没有执行 Kafka 故障实验。 [主题清理策略及组合语义](https://kafka.apache.org/41/configuration/topic-configs/#cleanup.policy)

最自然的办法，是保留完整日志，再定期另做一份全量快照；恢复时先载入快照，再接后续更新。这对需要任意历史或已有可靠快照流程的系统很合适，不过快照与接续位置也要协调。另一个办法是每次写入立即找到旧记录并原地抹掉，却把日志追加路径变成了查找与修改旧布局的路径。Kafka 的取舍是继续追加，再由后台按键清理：一条完整新状态已经替代旧状态时，恢复最终答案无需重新经历所有中间值。

先给出贯穿例子。P0 的本例历史从 100 开始，顺序写入六条记录；假设全部已可读，随后滚动到基址 106 的新活动段，使六条记录所在旧段具备清理条件。末尾位置为 106，那里暂时没有新记录。`null` 是真正的空值，表示删除，不是字符串“null”，也不是普通的零字节业务内容。

```text
100: 42 → 已下单
101: 77 → 已付款
102: 99 → 待付款
103: 42 → 已付款
104: 99 → null
105: 42 → 已发货
```

从空表顺序应用，100 建立 42，101 建立 77，102 建立 99；103 覆盖 42，104 删除 99，105 再覆盖 42。最终只有 77=已付款、42=已发货。我们要保住的就是这个答案。观察图一：若删除标记尚在保留期，哪些记录足以得到同样结果，留下它们时又有哪些数字不能改变？

![图一。教学模型：P0 的六条输入为 100:42已下单、101:77已付款、102:99待付款、103:42已付款、104:99空值删除、105:42已发货。摘要为 42→105、77→101、99→104。一轮覆盖全部六条且仍保留删除标记的清理，留下 101、104、105，顺序与原 offset 不变；从空表重放得到 77已付款、42已发货、99不存在。箭头表示清理步骤，非实际运行记录。](assets/figures/kafka-compaction-rewrite.svg)

这里可以丢掉 42 的 100、103，因为 105 已完整表达它的新状态；77 的 101 虽然更老，却没有后继覆盖，必须留下。99 的 102 被 104 的删除取代。本轮假设删除标记尚不能回收，所以保留 104。顺序读取 101、104、105，仍得到同一张最终表。压缩的漂亮之处在于换了回收依据：年龄不再直接决定一份状态是否无用，同键后继能否承接答案才是关键。它也没有承诺日志随时只剩每键一条，后台尚未处理的重复记录完全可以存在。 [压缩日志的用途与基本保证](https://kafka.apache.org/41/design/design/#log-compaction)

这条推导依赖消息语义。若三条值实际是“加一件、再加两件、减一件”，只留下最后一次减一件，就无法重建数量。应用可以改为发布计算后的完整数量，或者继续保存全部增量。Kafka 清理器只按记录键判断覆盖，不会替应用证明业务操作可以省略；同一订单若被路由到不同分区，也没有跨分区找出全局最后值的承诺。

实现怎样在有限内存中做这件事？4.1.0 的 `Cleaner.doClean` 先选可清理范围，`buildOffsetMap` 扫描其中的更新，为键记录较后的位置。本例摘要可写成 `last[42]=105`、`last[77]=101`、`last[99]=104`。随后重写旧段，`shouldRetainRecord` 查询摘要：100 小于同键的 105，可以去掉；101 等于 77 的已知最新位置，留下；104 还要通过删除保留条件。源码摘要有容量限制，一轮不必覆盖全部日志，超出本轮已知边界的记录也不能仅靠猜测删掉。 [本轮边界与重写入口](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/Cleaner.java#L151-L180) · [摘要容量与扫描](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/Cleaner.java#L635-L677) · [记录保留判断](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/Cleaner.java#L492-L523)

留下 101、104、105，不代表把它们改号成 100、101、102。否则，一个原已保存“下次从 103 继续”的消费者，会突然用旧地址解释新内容。压缩只造成空洞，保持剩余记录的原始顺序和位置。本例请求 103，可继续取得尚存的 104、105，处理后恢复位置推进到 106；不能因为 103 已不在，就把它当作末尾。这里讨论保留范围内的空洞，与删除型主题把消费位置推到范围之外不同。 [位置不变与空洞读取](https://kafka.apache.org/41/design/design/#log-compaction-basics)

物理上也不是一边读旧文件一边把字节挤到前面。清理器生成新段，完成写入与刷新后替换段集合；正在追加的活动段始终不参与这轮压缩。代价被移到后台扫描、摘要内存、重写 I/O 与临时空间，还需要调度、限速及文件替换管理。更新密集、键集合相对稳定时，省掉的旧值多；每条记录都使用新键时，几乎没有可省的内容。压缩资格也不等于立刻完成，不能把清理延迟配置读成精确的删除闹钟。 [活动段与后台工作的分工](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/LogCleaner.java#L50-L72) · [新段刷新与替换](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/Cleaner.java#L267-L277)

删除标记让这套设计多出一个时间条件。若 104 把 99 的旧值清掉后，自己也立刻消失，新启动的空表确实不会建立 99；可是已经读过 102 的老缓存怎么办？它需要收到一次明确的删除，才知道自己的旧值作废。没有记录，并不等于给每个已存在的消费者发送了“不存在”的通知。

图二分出一种故障时序。消费者 C 在清理前已读完 102，保存下一位置 103，本地还有 99=待付款。若它停得足够久，等旧值和删除标记都已被后续清理回收，再从 103 继续，会得到什么？

![图二。教学故障时序：C 在清理前读完 102，本地已有 99待付款，下一位置为 103。暂停期间，清理先去掉 99 的旧值并保留 104 删除标记；等待删除保留条件满足且后续清理完成，104 也消失，只剩 101、105。C 恢复后从 103 读到 105，追到 106，但本地 99 仍错误存在。若丢弃旧缓存，从空表完整重建，则只建立 77、42，不建立 99。箭头表示时间，不表示配置到期即同步删除。](assets/figures/kafka-compaction-tombstone.svg)

C 只看到 105 对 42 的覆盖，追到 106，却没有任何消息要求删掉 99。于是“进度已经追上”与“状态已经正确”分离了。保留删除标记的意义，就是给持续读取者和正在全量重建者一段观察删除的机会。`delete.retention.ms` 约束这段保留，官方也要求从头扫描者在该窗口内完成，才有相应最终状态保证。它不是为每个消费组登记的无限保护；超过窗口，不能假定原缓存仍可无损增量接续。 [删除保留与扫描时间条件](https://kafka.apache.org/41/configuration/topic-configs/#delete.retention.ms)

实际回收还要后续清理执行，不能说 104 一写入就启动一个准确到期即删除的闹钟。4.1.0 现代记录格式的判断读取批次删除期限，未设置期限或尚未到期时保留；清理过程维护这个期限。图二只假设有关条件已满足、回收已发生。补救也要区分场景：若允许丢弃本地旧表，从空表完整重建，本例即使已无 104，也不会复活 99；若要保留旧表，则必须有可靠的补齐或校验机制，不能仅调整 offset。 [删除期限的实现说明](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/LogCleaner.java#L74-L79)

这与 RocksDB 合并有共同结构：前台追加版本，后台去掉不再承担答案的旧值，并用删除标记阻止旧值继续有效。但 RocksDB 的显式快照会向引擎登记旧边界，合并必须保住那些视图；Kafka 消费者保存一个较早的 offset，并不会因此注册“必须保留这个时点所有旧状态”的快照。两者可以复用“清理前先证明承诺不变”的判断，不能互换历史保护条件。压缩主题适合恢复最新键值，审计每一次状态变化则需要另保历史；若再同时启用 `delete` 策略，整段过期也会改变恢复前提。 [RocksDB 快照对合并的约束](https://github.com/facebook/rocksdb/wiki/Snapshot#implementation)

最后独立推演：把 105 改成 42 的删除标记，第一次清理应留下哪些记录？若随后又写入 106:42→重新下单，旧删除还必须长期留下吗？再比较一个两天内能完整重建的服务与一个允许停机一个月后沿用旧缓存的服务，它们能否采用相同的删除保留窗口？先沿本地表逐步求答案，再决定愿意把恢复成本交给谁。
