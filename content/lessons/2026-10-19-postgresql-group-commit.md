# PostgreSQL：怎样让多笔事务共用一次磁盘同步

三个客户端分别修改三个互不相关的账户，然后同时请求 COMMIT。昨天的 SSI 回答了哪些并发决定可以共同成立；今天假设这三笔事务已经满足各自的正确性要求，追问另一个问题：如果每笔提交都要等日志可靠保存，数据库是不是非得做三次昂贵的磁盘同步？能不能只做一次，却仍分别兑现三份持久化承诺？

我们继续 PostgreSQL 18 的普通持久表，采用 fsync=on、synchronous_commit=on，未配置同步备库，并假设文件系统与设备正确兑现同步请求。这里只讨论主机崩溃后恢复所需的本地 WAL 保证，不把它扩大成磁盘损坏后仍不丢数据或备库已应用。临时表、unlogged 表、两阶段提交与异步提交不在本例路径里。[提交成功需要等待到哪一层](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)

先交代系统位置。执行修改的后端进程更新共享缓冲区里的表页，并生成足以支持恢复的 WAL；提交路径确认本次提交记录已经持久化，再继续完成事务状态发布和结束工作。脏数据页可以稍后写回，恢复时重做尚未落到数据文件的修改。日志在这里是恢复依据，不是 SQLite 那种读者按 WAL 页版本直接选择答案的同一套读路径；早先 WAL 篇建立的先后关系可以复用，具体实现不能混用。[PostgreSQL 的 WAL 与恢复分工](https://www.postgresql.org/docs/18/wal-intro.html)

最自然的方案，是每个后端写完自己的提交记录，就各自发起一次同步。单客户端、提交间隔很大时，它并不浪费太多：本来就没有别人可以一起等。并发很高时则不一样。WAL 是一条共享的有序日志，把后面的位置可靠保存，前面的记录也已经包含在这份可靠前缀中；若另一笔事务刚替你保存了所需内容，再同步一次就未必增加任何保证。

关键洞察是把请求改写成一个条件：不是“我必须亲手同步一次”，而是“共同日志至少已经持久化到我需要的位置”。PostgreSQL 用 LSN 表示日志位置，它描述字节位置，不是事务编号，也不是时间戳。记事务 T 的提交记录结束位置为 eT，共享的已刷新位置为 F；这笔事务的本地 WAL 持久化义务就是 `F >= eT`。谁推进 F 不重要，重要的是这个前沿背后的证据可靠。

下面是教学模型，没有运行数据库或转储实际 WAL。为了让数字可读，省略共同日志基址，以 KiB 为相对位置单位，不表示真实记录大小。初始 F=120，三笔事务 A、B、C 的提交记录结束位置分别是 eA=160、eB=200、eC=240。它们各自需要的此前修改日志都已生成；这些日志可以交错排列，不能把整条 WAL 想成三个互不重叠的事务文件。

先观察第一幅图：同样已经写到 240，为什么有一种状态仍不能满足任何一笔提交的持久化要求？

因为写入系统缓存与保存到稳定存储不同。为突出这点，本例选择能把写出与同步分开解释的路径，W 表示已写出位置。W=240、F=120 时，后面的日志可能仍在易失缓存中，进程退出与机器掉电的结果也可能不同；不能因为 write 已返回，就把 F 改成 240。完成所选方法要求的同步后，才有依据更新已刷新前沿。真实 wal_sync_method 可能采用 fdatasync、fsync 或带同步语义的打开方式，不能断言每种平台都恰好调用同名系统函数。[写出、同步及方法差异](https://www.postgresql.org/docs/18/wal-configuration.html)

现在让 A 发起到 160 的刷新请求。假设它真正准备 I/O 时，B、C 的日志也已完整进入可刷出的前缀，系统选择把请求扩大到 240，一并写出并同步。这个动作不需要把三个事务合成一个事务：只是在相邻日志上共享一段持久化工作。等 F 从 120 推进到 240，A 检查 240≥160，B 检查 240≥200，C 检查 240≥240，各自的要求都满足。这就是组提交能够成立的因果基础。

![教学时序：A 取得刷新职责，把已完成插入的日志同步到 240 KiB；B、C 等待后重新检查 F，因 200、240 均已覆盖而跳过重复同步。随后 D 的提交记录结束位置为 280，F 仍为 240，D 还必须等到自己的目标被覆盖。向下表示步骤，三笔共用一次是选定时序，不保证每轮固定批量或固定领头者。](assets/figures/pg-group-followers.svg)

PostgreSQL 18.0 固定提交 `3d6a828` 的 `XLogFlush(record)` 正是接收目标位置。它先检查目标是否已经刷新；未满足时，准备可写范围并竞争 WALWriteLock。没立即取得锁的后端等待锁释放，再循环检查共享结果，而不是醒来就强行同步。取得锁后还要再检查一次，避免自己排队期间别人已完成工作。这把锁保护的是 WAL 写出与刷新职责，并没有把各事务的所有查询计算都排成一个全局队列。[刷新目标与等待后的重检](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/transam/xlog.c#L2773)

还存在一个不能略过的边界：多进程可以并发向 WAL 插入记录，已经分配到某个位置，不代表前面每一段都写好了。因此源码在实际写出前，用 `WaitXLogInsertionsToFinish` 等待有关插入完成，才把可安全刷出的范围交给写入路径。我们的 240 是一个已完成的连续前缀，不是“某个进程曾经报出过的最大号”。若跳过前面的空洞仍把 F 推到 240，早于 240 的提交就可能获得一份没有完整恢复依据的保证。[可写前缀与正在进行的插入](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/transam/xlog.c#L2838)

同步完成、共享结果公布后，等待者才能用新的 F 判断。B、C 不需要亲自接触磁盘；它们需要的是自己目标被可靠覆盖的证据。D 稍后生成的提交记录结束于 280，此时 240<280，仍须等待后续刷新。不能因为“这一批刚同步过”就允许后来者搭便车，也不能把唤醒通知本身当作条件成立。通知让进程有机会重查，前沿比较才决定这次义务是否结束。

到这里可以写出不变量：在本例同步提交路径中，成功结束事务之前，包含自身提交记录的 WAL 前缀必须已经可靠刷新；F 只能描述已完成的持久化工作，不能由请求位置或写出位置冒充。固定源码的 `RecordTransactionCommit` 调用 `XLogFlush(XactLastRecEnd)`，随后才进入相应事务提交状态处理。F 达标说明这一步义务已满足，不等于锁释放、状态发布及向客户端送出响应都已在同一瞬间完成。[事务提交接到刷新边界的位置](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/transam/xact.c#L1497)

用一个反事实检验：若只写到 W=240 就返回三笔提交成功，机器立即断电，易失缓存丢掉后面的日志，恢复可能找不到本已承诺的提交记录，成功承诺便被破坏。反过来，F 已可靠达到 240，而数据文件里的三个账户还留着旧内容，却不构成同样的矛盾：恢复可以依据完整 WAL 重做。数据页写回也有自己的先写日志规则，缓冲管理器在写持久表页前确保该页所需 LSN 已刷新；数据页可以落后，却不能领先于恢复依据。[表页写回的 WAL 约束](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/buffer/bufmgr.c#L4330)

共用同步也不改变事务的身份。A、B、C 各有自己的提交记录与状态，不因共享一次 I/O 而获得跨事务的业务原子性，更不保证三份客户端响应同时到达。如果服务器已持久化并提交，却在回复途中断线，客户端仍可能不知道结果；这是结果确认与重试协议的问题，不能靠组提交推断“没有收到成功就一定没提交”。

为什么不故意多等一会儿，把更多人凑进来？这确实可能摊薄固定同步成本，但也会增加等待。PostgreSQL 的 commit_delay 默认是 0；即使没有主动延迟，在前一轮刷新进行时积累的后续请求，仍可能形成下一轮共享。设置非零延迟还受 fsync 和 commit_siblings 等条件约束，不是每笔事务固定睡一段时间，也不保证凑齐某个数量才放行。[组提交机会与延迟条件](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-COMMIT-DELAY)

可以作一个简单成本推导：若一次固定同步开销是 S，一轮覆盖 n 笔事务，这部分摊销约为 S/n。但单笔延迟并不是 S/n：它仍要承担排队、实际写出与同步，主动等候还可能拉高尾延迟。日志字节数、锁竞争、设备带宽和数据页后台写回也没有消失。并发小、同步本来很快时，凑批等待可能得不偿失。本文没有测量 S、n 或吞吐，不能把模型当成调参结论；把 synchronous_commit 关掉更是改变成功承诺，不能算成同等保证下的组提交优化。[异步提交改变的保证](https://www.postgresql.org/docs/18/wal-async-commit.html)

这可以与 TCP 的累计确认作一个具体联系。TCP 确认推进到某个字节边界，可以一次覆盖多个已连续收到的区间；WAL 刷新前沿也让多个较早目标同时满足。共同结构是用一个连续前缀压缩许多完成事实，而不能跨越缺口。差异必须保留：TCP ACK 表示接收方传输层已接收，不表示远端应用已持久化；这里 F 表示选定本地存储保证下的日志持久化，也不表示副本已应用。二者只是结构相似，确认语义不能互换。[TCP 累计确认的语义](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4)

最后独立推演：如果第一次只把 F 推到 200，A、B、C 各自该怎样继续？如果 C 的目标记录只分配了位置、尚未完成插入，为什么不能直接按 240 放行？这个设计值得欣赏的地方，是把每人重复执行一次动作，改成多人共同等待同一个可证明条件；工作可以共享，承诺仍逐笔核对。本文核对 PostgreSQL 18 文档及 18.0 固定源码，未运行数据库、追踪系统调用、注入断电或测量性能；图中位置与批次都是教学模型。
