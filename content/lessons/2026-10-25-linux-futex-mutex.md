# Linux：锁大多没人争，为什么还需要内核

沿着昨天的聊天服务继续想：网络事件已经到达，两个工作线程现在要更新同一个连接统计表。假设临界区只是把计数 X 加一，通常很快结束，而且多数时候只有一个线程来访问。我们需要互斥，却不希望每次拿锁、放锁都进入内核；遇到真正的长等待，又不希望线程一直占着 CPU 空转。今天要理解的设计，是 Linux 怎样让用户态原子操作负责常见路径，再由 futex 把少见的竞争接到内核等待与调度机制上。

最直接的办法，是把锁交给内核：进入临界区前请求它分配所有权，离开时再通知它。这样方便集中组织等待者，但无竞争时也要承担系统调用成本。另一个自然方案是自旋：不断用原子指令尝试把“空闲”改成“占用”。持锁时间很短、持锁线程正在另一个 CPU 上推进时，自旋可以合理；如果持锁者被调度走，等待者反复尝试却不能让它更快释放，反而消耗执行资源。真正需要分开的，是**争取所有权与等待别人释放**这两件事。[futex 的用户态与内核分工](https://man7.org/linux/man-pages/man2/futex.2.html)

futex 不是一把现成的完整互斥锁。它提供等待和唤醒等底层操作，标准库在上面组织锁、条件变量等接口。应用通常使用标准库的同步原语；理解 futex，是理解这几层怎样配合，而不是把一段教学代码直接替换生产锁。[futex 的定位](https://man7.org/linux/man-pages/man7/futex.7.html)

## 让一个共享整数承接两种路径

先限定模型：同一进程的线程 A、B，共享一个按 4 字节对齐的 32 位原子整数 L，以及受它保护的 X，初始都为 0。只有持锁者能访问 X；没有超时取消、递归加锁、持锁者死亡或优先级继承。以下依据 Linux 6.12 源码作机制推演，没有执行本机 futex 调用追踪或性能测试。等待和唤醒使用进程私有 futex 操作，内存一直有效到全部使用者退出。Linux 的 futex 字确实是 32 位，即使进程运行在 64 位机器上也是如此。[futex 字与私有操作约定](https://man7.org/linux/man-pages/man2/futex.2.html)

给 L 约定三个值：0 表示锁空闲；1 表示锁被持有、尚未标记需要唤醒；2 表示锁被持有，而且释放时可能需要唤醒等待者。2 不是等待人数，也不保证此刻已经有人睡着，它保留的是一份不能轻易丢弃的唤醒责任。这些数值是用户态锁实现的约定，普通 WAIT/WAKE 操作并不会自动替你解释这三种状态。

无竞争时，A 用原子比较交换，把 L 从 0 改为 1。比较和修改不可被其他线程插进来，因此只有一个线程能成功获得这个空闲状态。A 把 X 从 0 改为 1，释放时原子地把 L 换回 0；若旧值是 1，就不需要唤醒系统调用。这里锁的所有权已经在用户态确定，内核无需为每次成功获取做记录。

为了跟踪竞争，下面写一份省略自旋优化的教学伪代码。CAS 成功时返回真，exchange 写入新值并返回旧值；acquire 与 release 表示内存顺序，稍后解释。wait_private 是 `FUTEX_WAIT_PRIVATE`，wake_private 是 `FUTEX_WAKE_PRIVATE`；wait 因值变化或信号返回时重新尝试，其他错误的处理不在这份伪代码中。

```text
lock():
    if CAS_acquire(L, expected=0, new=1):
        return
    while exchange_acquire(L, 2) != 0:
        wait_private(L, expected=2)

unlock():
    old = exchange_release(L, 0)
    if old == 2:
        wake_private(L, at_most=1)
```

这个结构参考 Rust 1.90.0 标准库中的 futex 互斥实现，但不是其逐行转录：真实代码还会短暂自旋、避免不必要的重复写入。此处用重复 exchange 换取更容易推演的状态关系，也没有覆盖所有互斥锁实现。[固定版本：Rust 的三状态锁及释放路径](https://github.com/rust-lang/rust/blob/1.90.0/library/std/src/sys/sync/mutex/futex.rs)

现在改变时序，让 A 尚未释放时 B 来加锁。观察图中 L=2 的两个时刻：为什么第一次不代表 B 拿到了锁，第二次却代表 B 已经成为持有者？

![教学时序：A 把 L 从0改成1取得锁，B 竞争失败后把1换成2并等待；A 更新X为1后把2换成0并唤醒B；B 的 exchange 读到旧值0才取得锁并保留L为2，随后更新X为2，释放并尝试唤醒。](assets/figures/linux-futex-handoff.svg)

图 1：从上到下推进时间。框中是选定时刻的所有权、共享值与等待状态；没有新增竞争者，箭头不是实际线程追踪。

B 的首次 CAS 失败，接着 exchange 把 1 换成 2。旧值是 1，说明 A 仍占着锁，B 只标记竞争，不能进入临界区。它请求“如果 L 仍为 2，就等待”。选定这次时序中，B 成功进入内核等待，A 随后完成 X=1，把 L 从 2 换为 0。旧值 2 提醒 A 发起一次最多唤醒一个等待者的操作。B 返回用户态后重新 exchange，只有读到旧值 0，才证明自己刚刚占有了空闲锁。

为什么 B 获锁后保留 2，而不直接改回 1？如果还有其他睡眠者，保留唤醒责任，能使下一次释放继续唤醒它们；即使这次没有别人，也允许一次没有唤醒对象的调用。B 读到 X=1，加到 2，再释放锁。其唤醒可能返回 0，这是“没有找到等待者”，并非加锁失败。[FUTEX_WAKE 的数量与返回值](https://man7.org/linux/man-pages/man2/FUTEX_WAKE.2const.html)

## 最危险的，是准备睡眠的那条缝

还不能因为有了等待队列就宣布正确。把图 1 的中间两步换一下：B 已把 L 标记成 2，却还没来得及入队；A 就把 L 改为 0，并发出唤醒。内核此时找不到睡眠者，返回 0。如果 B 接下来不检查条件就睡下，锁明明空闲，却可能再没有线程来唤醒它。这是昨天 epoll 也遇到的边界：状态变化与建立等待关系，不能让双方都错过对方。

看下面这条交错。唤醒没有被存成一张可留待以后领取的票，B 为什么仍然安全？

![教学交错：B 把L标记为2后尚未入队；A 释放锁使L为0，wake返回0；B 随后调用WAIT期待2，内核发现当前0不等于2，返回EAGAIN而不入睡；B 再次exchange看到旧值0并获得锁。](assets/figures/linux-futex-check-sleep.svg)

图 2：本图选择释放先于 WAIT 检查的顺序；若等待先建立，则应由后续 WAKE 找到等待者。省略其他线程、地址故障与信号分支。

关键在 `FUTEX_WAIT` 的承诺：读取 futex 字、比较期望值、决定阻塞，与同一个 futex 上的相关操作形成受保证的原子关系。B 带着期望值 2 进入内核，却看见 0，就返回 -1、`errno=EAGAIN`，不会按已经过时的判断睡眠。反过来，如果等待已经建立，A 的唤醒就必须能够接住它。这保证的不是“每次变化都收到一条消息”，而是正确使用协议时，不能既漏掉条件变化，又漏掉等待者。[FUTEX_WAIT 的比较并阻塞约定](https://man7.org/linux/man-pages/man2/FUTEX_WAIT.2const.html)

Linux 6.12 源码把这个交错直接画在 `waitwake.c` 开头：等待路径在散列桶锁保护下复查用户字并入队，唤醒路径查找匹配的等待者；还有等待者计数与内存屏障，支持“看起来无人等待时跳过加锁”的优化。不能只学到“先检查再睡”五个字，删掉它背后的锁、顺序和状态协议。[固定源码：等待与唤醒的顺序论证](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/futex/waitwake.c#L10)，[值检查与入队准备](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/futex/waitwake.c#L592)

## 被叫醒以后，责任仍回到用户态

等待返回不等于获得所有权。假设 A 释放并唤醒 B 后，新线程 C 抢先把 0 改成 1。B 随后 exchange 读到 1，就必须重新标记 2 并等待；如果 B 把“被唤醒”当成通行证，会和 C 同时进入临界区。互斥不变量因此很具体：只有成功把旧值 0 改成占用状态的线程才能进入；唤醒只提供再次竞争的机会。普通 WAIT/WAKE 也没有先到先得的保证，等待返回还必须按可能发生伪唤醒来处理。[FUTEX_WAKE 的选择边界](https://man7.org/linux/man-pages/man2/FUTEX_WAKE.2const.html)，[WAIT 返回后的复查要求](https://man7.org/linux/man-pages/man2/FUTEX_WAIT.2const.html)

另一个条件是数据可见性。锁不只是保护 L 这个整数，还要让 B 获锁后看到 A 对 X 的修改。释放侧的 release 与成功获取侧的 acquire 配合，才建立被保护数据的先后关系；不能把“内核唤醒过我”或 `volatile` 当作这种同步的替代品。尤其无竞争路径根本不进入内核，数据同步必须由用户态原子协议成立。[Rust 原子内存顺序的 acquire/release 定义](https://doc.rust-lang.org/std/sync/atomic/enum.Ordering.html)

这种分工的收益，是常见的无竞争获取与释放只需用户态原子操作；成本则转移给库实现者维护状态、内存顺序与错误边界。发生竞争时仍要承担缓存行争用、系统调用和调度延迟。临界区极短时，自旋可能比睡眠划算；临界区很长时，futex 只能避免等待者空转，不能缩短持锁者的工作。这个模型也不负责持锁者死亡恢复、递归、超时取消或优先级继承，不能据此概括所有 pthread 锁。锁字更不能在仍有使用者时被释放或复用。

可以先独立推演：若 B 在慢路径获锁后把 2 改成 1，而另一个等待者 D 仍睡在内核里，B 释放时会漏掉哪一份责任？再判断：若等待几乎总是短到持锁者马上退出，省去短暂自旋会把什么成本交给谁？这里没有性能实测，判断需从条件出发。

在 Rust 中，这种底层等待机制还能与另一种设计组合：`MutexGuard` 把锁的使用权放进一个带生命周期的对象，guard 被销毁时自动解锁。futex 回答“竞争时怎样等待并继续争取”，guard 回答“正常作用域退出时由谁负责释放”。它们都把责任交给能维护相应状态的一层，但解决的边界不同：自动释放不会让临界区变短，内核等待也不会自动替业务结束持锁。把所有权、数据可见性、等待资格与释放责任分别讲清，才是这套系统配合得漂亮的地方。[Rust MutexGuard 的作用域释放约定](https://doc.rust-lang.org/std/sync/struct.MutexGuard.html)
