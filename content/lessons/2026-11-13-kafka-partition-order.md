# Kafka 为什么把需要保序的事件放进同一个分区

昨天我们用一条订单日志解释了消费进度。现在订单越来越多，通知服务要同时处理订单 42 和订单 99。每个订单都必须先通知下单成功，再通知付款成功，最后通知发货。两个订单彼此独立，订单 42 的短信慢一点，订单 99 仍应继续。既要保留先后关系，又想增加处理能力，应该把哪部分工作排成一条队？

把整个主题放进一个分区最自然。所有事件进入同一条日志，消费者按日志顺序处理，就有一个容易解释的次序。数据量小、确实需要比较所有事件时，这个选择很实用。但在普通消费者组的分区分配模型下，一个分区在同一时刻由组内一个消费者实例负责。继续增加实例，无法把这条分区日志的分配再拆开；这条链的生产、存储和处理能力也有各自上限。

另一个自然方案是把记录轮流发到多个分区。写入更分散，却可能把订单 42 的下单放在 P0、付款放在 P1。两个分区被独立拉取和处理，P1 对应的消费者先完成，用户就可能先收到付款通知。给事件带上时间戳也不会让另一个分区立即交出更早但尚未到达的事件。若强行恢复全局次序，处理方又要为跨分区的数据建立合并与等待规则。

Kafka 的选择是让分区承担有序日志的职责，让应用用 key 把需要共同排序的事件送往同一个分区。生产者选择分区后，把记录发往该分区的 leader；消费者组再把分区分给实例。独立分区可以由不同 broker 和不同消费者承担。一份主题因此有多条各自前进的日志，应用选择哪些业务关系必须落在同一条里。 [按语义选择分区的设计](https://kafka.apache.org/41/design/design/#load-balancing) · [普通消费者组的分区分配](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#consumergroups)

本篇固定 Kafka 4.1，路由细节核对 Java 生产者 4.1.0。例子有两个分区，key 是稳定的订单标识；每个订单由一个有序发送流程依次发出三种事件，前一种发送成功后才发下一种，消费方顺序完成对应处理。图中假设记录已经可读，用教学哈希值 h42 = 8、h99 = 5 简化取模计算；offset、哈希值和处理时序都是教学设定。

Java 内置的带键路径先对序列化后的 key 求 Murmur2 哈希，转成非负整数，再对分区数取模。这个路径生效的条件是没有显式指定分区、没有自定义分区器，并且没有开启忽略 key 的设置。按模型计算，8 % 2 = 0，所以订单 42 的下单、付款、发货都去 P0；5 % 2 = 1，所以订单 99 的事件都去 P1。实际业务必须让不同写入方对同一标识采用一致的序列化与路由规则。 [生产者的分区选择分支](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/KafkaProducer.java#L1466-L1485) · [带键路由公式](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/producer/internals/BuiltInPartitioner.java#L326-L331)

看图一。订单 42 在 P0 的三个位置是 100、101、102，订单 99 在 P1 的三个位置是 7、8、9。哪个先处理完会影响另一个订单的先后关系吗？

![图一。教学哈希 8 % 2 把订单 42 放进 P0，5 % 2 把订单 99 放进 P1。P0 保存 100 下单、101 付款、102 发货，P1 保存 7 下单、8 付款、9 发货。通知组的 N0、N1 分别顺序处理一条分区日志，最终下一位置为 103 和 10。箭头表示各自的事件流，各分区可独立推进。](assets/figures/kafka-partition-order.svg)

假设 N0 正在处理 P0 的付款事件 101，N1 已经处理完 P1 的发货事件 9。这两种状态可以同时成立。订单 42 的发货仍排在它自己的付款之后，订单 99 无需等这笔付款通知。N0 完成 102 后，下一位置为 103；N1 完成 9 后，下一位置为 10。恢复状态因此是每个分区一个位置。P0 的 100 和 P1 的 7 不能用大小来比较业务发生的先后，两个数字只在各自日志内有意义。

能并行多少，取决于应用愿意把多大的范围放在一起排序。如果用整个商家的标识作 key，同一商家的所有订单都会集中；若只需要每个订单内有序，用订单标识就能保留更多独立性。哈希也可能让多个不同订单碰巧落在同一分区，它们会共享这条日志和分配单位。某个订单或商家的流量特别大时，多加几个消费者也无法自动拆开这个热点。更多分区也带来日志、副本、缓冲和分配管理成本，分得更细需要收益来支撑。

这里的关键不变量是，需要按同一日志推进的事件，必须持续遵守同一套映射。key 相同还不够，分区数和路由约定也参与决定位置。图二改变一个条件，把主题从两个分区扩到三个。订单 42 的下单已经在 P0，下一条付款会去哪？

![图二。独立的扩容分支。订单 42 的教学哈希保持为 8，扩容前 8 % 2 = 0，下单事件已在 P0 的 100。扩容后生产者获知三个分区，8 % 3 = 2，付款事件进入 P2 的 0。旧记录仍留在 P0，两个分区的处理方可能先处理付款。箭头表示扩容前后的教学时序。](assets/figures/kafka-partition-expansion.svg)

分区数变成 3 后，8 % 3 = 2。获知新分区数的生产者会把付款送进 P2，已有的下单仍在 P0。Kafka 增加分区时不会自动把旧记录搬过去。即便生产者先确认下单写入、再发送付款，消费方仍可能先推进 P2，后推进 P0。每条分区内部的次序都成立，跨分区的订单状态却已经需要额外协调。若多个生产者刷新元数据的时间不同，切换期间还可能同时采用旧映射和新映射。 [增加分区对按键路由的影响](https://kafka.apache.org/41/operations/basic-kafka-operations/#modifying-topics)

因此，严格依赖按键顺序的系统，需要把扩容当作映射迁移。一个可推演的方案是先停止旧流的新写入，在原分区中为各条流确定处理边界，等这些边界完成，再让业务启用新映射。这样把代价显式付在切换等待和协调上。具体迁移协议还要处理故障与重试，单纯增加分区并不会替应用确定新旧流的衔接条件。

生产和处理两端也都参与顺序的兑现。如果付款由另一个生产者先发到 Kafka，放进同一分区后，日志只能记录这个实际进入的次序。Java 生产者在关闭幂等、允许重试且同连接有多批在途时，前批失败而后批成功，也可能改变追加次序。消费方若把同一分区的事件交给多个线程同时执行，完成顺序仍可能改变。本例让每个订单的发送流程与分区内处理串行，才把日志顺序接到了通知顺序。 [重试与生产者保序条件](https://kafka.apache.org/41/configuration/producer-configs/#max.in.flight.requests.per.connection)

Amazon Kinesis 的 partition key 也把相关记录聚到同一个 shard，序号在 shard 范围内解释，独立 shard 可以各自推进。它用 MD5 得到哈希，再按 shard 的哈希区间映射；这里核对的 Kafka Java 路径使用哈希对分区数取模。两者都把相关性变成路由输入，但路由计算和调整边界的机制各有约定，不能仅凭都提供 key 就套用同一份迁移过程。Kinesis 的严格递增写入也要求遵守它的串行写入与序号接口条件。 [Kinesis PutRecord 的映射与序号契约](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_PutRecord.html)
