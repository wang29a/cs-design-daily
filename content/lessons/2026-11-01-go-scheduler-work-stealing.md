# Go：任务集中在一边，其他线程怎样接过工作

一个请求把四份输入 1、2、3、4 分成四项独立计算 A、B、C、D，各自求平方，最后汇总为 30。机器有并行执行的条件，可任务恰好都排在同一侧，另一侧却没有活干。前面我们知道 goroutine 能保存调用状态、等待时让出线程，今天追问下一层：任务已经可以运行，运行时怎样让有限的执行资源真正接到它们，同时不把“分配任务”本身变成大家争抢的瓶颈？

最自然的是一个公共待办队列。所有执行线程都到这里领任务，负载不均时也不怕任务被关在别人那里；工作量不大、每项工作较重时，这很清楚。但如果任务不断产生、不断领取，许多线程会反复修改同一组共享状态，排队领取的成本可能侵入每一项工作的路径。另一种办法是各有各的队列：常见操作只碰自己的状态，却可能一边排长队、一边没事做。Go 的选择是让常见调度尽量留在局部，缺工作时再把别处的一批任务接过来。[固定源码对集中状态与局部性的取舍](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L37)

本文仍固定 Go 1.25.0 官方提交 `6e676ab2`，讲标准工具链 runtime 的实现。先补齐位置：G 是带执行状态的 goroutine，M 是真正执行指令的系统线程，P 是运行用户 Go 代码所需的一组调度、分配等资源。M 要配合一个 P 才能执行用户 G；局部可运行队列放在 P 上，不是永久绑定某条系统线程的一份私产。P 可以在不同 M 之间交接，它也不是固定物理 CPU。[G、M、P 的职责](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/HACKING.md#L16)

## 局部拥有，不等于永远独占

设 `GOMAXPROCS=2`，有 P0、P1。当前 M0 配合 P0 执行请求处理者 X；M1 配合 P1 正在寻找工作。X 先前产生的 A、B、C、D 都已进入 P0 的普通局部队列，按队头到队尾排列；P1 的普通队列为空。四项计算互不依赖，没有线程绑定。为聚焦转移，选定全局队列为空、网络和定时器没有交来新任务、没有其他可运行任务介入；这不是整个运行时只有这几种状态的承诺。

特别说明普通队列：这个版本每个 P 有一个 256 槽的环形队列，另有用于优先衔接任务的 runnext 槽。我们把两边的 runnext 都设为空，因此可以准确追一批普通队列任务；不能把实际调度器压成“每次只从一个 FIFO 取头”。以下为固定源码支持的教学交错，没有运行调度 trace 或测量速度。[队列与 runnext 的表示](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/runtime2.go#L641)

M1 在本地没有取得任务，其他来源也没有工作，进入寻找可转移工作的路径。`stealWork` 会以随机起点安排对其他 P 的尝试，并限制搜索轮次；我们选定它找到 P0。这个动作通常叫工作窃取，但不是抢走正在执行的 X，更不是把 X 的一半指令自动拆开。转移对象是已经可运行、尚在队列中的 G。[寻找其他 P 的工作](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L3795)

观察图中前后两刻：P1 接过 A、B 之后，为什么 B 直接运行，A 反而先留在队列？

![教学状态对照：转移前M0持P0运行X，P0普通队列从头到尾为A、B、C、D；M1持P1寻找工作，P1队列空。转移成功后P0仍运行X、队列剩C、D；M1与P1开始运行B，A进入P1队列。中间箭头表示成功转移A、B，不是移动正在执行的X。](assets/figures/go-scheduler-steal.svg)

图 1：两边 runnext 及全局队列均为空，省略其他运行时工作；只画选定交错，不是负载或耗时测量。

答案来自具体批量策略。`runqgrab` 看到队列长度 n，会尝试取 `n - n/2` 项，整数除法向下取整，也就是约一半、奇数时向上取整。这里 n=4，取头部 A、B。`runqsteal` 再把这一批最后一项 B 返回给调度器立即执行，把其余 A 公布到 P1 的队列，P0 留下 C、D。这样既拿到眼下能运行的一项，又留一点后续工作，避免每做完一项都重新找别人。[批量领取与返回一项执行](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L7228)

这不是“必须先运行 A”的顺序契约。A、B、C、D 的业务依赖必须显式表达，不能把创建顺序当成执行或完成顺序。约一半也只平衡任务数量，A 算一秒、B 算一毫秒时，队列各有两项不等于工作耗时均等；本例平方计算只是用于说明输入与结果，不拿它测并行收益。

## 真正交接的是执行权，不是指针副本

把 G 的指针抄到另一边很容易，难的是 P0 也可能正好开始领取队头。假设队头序号 h=0、队尾序号 t=4，有效范围为 `[h,t)`，四个位置依次存 A、B、C、D。序号选择没有绕环；真实槽位用序号对 256 取模定位。P1 可以先读这四项范围并把 A、B 复制到自己的未公布槽位，但复制成功并不表示它已经拥有执行权。

关键步骤是一次条件提交：只有 P0 的队头仍为 0，才把它改成 2。比较并交换，也就是 CAS，在这里把“确认依据没变”和“消费这批位置”连为一个原子决定。成功以后，P0 的有效范围变为 `[2,4)`，不再能按旧范围领取 A、B；P1 才可继续处理接到的批次。数组旧槽里即使还有 A、B 的指针，也只是过期内容，不是另一份可运行资格。

反过来，如果 X 恰好结束，P0 的本地领取先把 h 从 0 改成 1、取得 A，P1 还按旧判断提交 0→2 就必须失败。它不能拿着已抄到的 A 开始运行，而要重新读取范围再尝试。图中请区分“读到一个指针”和“成功消费一个位置”。

![独立竞争分支：P1观察P0队头h=0、队尾t=4并暂存A、B，但未取得执行权；X结束后P0先以CAS把队头0改为1并取得A；P1再尝试要求旧头为0的CAS失败，不能执行暂存的A、B，只能重读新范围。箭头表示动作先后，不是机器时钟测量。](assets/figures/go-scheduler-claim.svg)

图 2：这是与图 1 成功分支不同的竞争交错。未公布槽里的副本可以被后续重试覆盖；失败不等于丢失一批合法任务。

本地领取 `runqget` 和跨 P 领取 `runqgrab` 都通过队头的原子更新提交消费；生产方先写好任务槽，再公布队尾，接收方不能把尚未公布的槽当成任务。这些次序与原子操作共同守住不变量：**同一份排队记录只能被一个路径成功消费，不能让同一 G 同时交给两个执行线程。**G 以后阻塞、唤醒、再次入队是新一次调度，不在这个不变量里被禁止。[本地领取的提交](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L7160)，[任务写入与队尾公布](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L7040)

回到图 1 的成功分支，调度器通过 `execute` 把选出的 B 从 Runnable 转为 Running，并接到当前 M 的执行上下文。随后选择这样的后续：X 完成本地工作，P0 依次推进 C、D；P1 在 B 结束后推进 A，不再发生别的转移。业务汇总最终收齐 A=1、B=4、C=9、D=16，得到 30，这段任务处理结束。转移本身没有完成任何计算，也没有保证这条教学完成顺序；它只是改变了谁有资格继续推进哪些 G。[取得任务以后怎样开始执行](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L3319)

## 局部效率，还要接回全局公平

若每个 P 永远只顾本地，少数任务不断互相唤醒，就可能使全局队列里的任务长期得不到机会。因此 `findRunnable` 除了常见的局部路径，还会按调度计数适时查看全局工作；本地无工作时也会从全局批量取任务。局部队列满了，则有把一批任务移到全局队列的慢路径。公共队列没有消失，只是无需成为所有普通操作的必经之路。[全局检查与工作来源](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L3414)，[队列满时的批量外送](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L7090)

没有找到工作时，也不能让所有线程永远忙转。运行时协调搜索者数量、线程休眠与新任务唤醒，避免把本可节省的 CPU 用在找任务上。可见“局部队列加窃取”还要与网络就绪、定时器、GC 工作及线程停启衔接，才成为一个可用的调度系统；本篇没有把这些相邻协议的正确性一并证明。[搜索与线程停启的配合](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L37)

设计的收益，是把常见路径的共享竞争，换成局部操作与空闲时才需要的跨 P 协调。代价包括搜索失败、原子重试、队列迁移和可能损失的数据局部性。它不会自动切分正在跑的长任务，也不承诺每项任务在固定时间内开始；抢占另有机制。`GOMAXPROCS=2` 更不等于机器始终给两个完整 CPU，容器配额和系统负载仍限制物理执行资源。没有额外可运行任务时，多一次窃取也不会制造并行性。

Java 的 ForkJoinPool 也用工作窃取，让线程接手其他活跃任务产生的工作，适合一项计算继续拆出子任务的情形。共同结构是局部组织工作、空闲方主动补足；差别是它面向提交到执行器的任务及 fork/join 协作，Go 这里调度的是可恢复的 goroutine 状态，并与自己的网络等待等路径结合。Java 文档也不保证遇到阻塞 I/O 或任意外部同步时总能补足线程；不能只看见“窃取”两个字就认定阻塞与资源管理语义相同。[Java 25 ForkJoinPool 的职责与边界](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ForkJoinPool.html)

最后独立推演：若 P0 普通队列有五项，一批会尝试取几项，立即运行与留给接收方队列的又各有几项？若 P1 已抄到 A，但 P0 先消费了它，为什么不能“先跑再说”？再把条件改成只有 X 一个长任务、两边队列全空，这套设计还能把 X 自动变成两份并行工作吗？能分清任务状态、排队所有权和真实计算资源，才知道这种安排在什么条件下值得采用。
