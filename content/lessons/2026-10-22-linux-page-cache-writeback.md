# Linux：write 已经返回，内核怎样继续替你把数据写回磁盘

一个服务修改文件，write 返回写入两个字节；另一个进程马上读取，也确实看见了新内容。可机器此时断电，新内容仍可能消失。昨天我们分清了名字、文件身份和打开状态，今天继续追问：描述符已经找到文件，字节又由谁接住？Linux 怎样让应用及时使用新数据，同时把慢得多的存储工作留给后台，而不漏掉后来发生的修改？

我们只讨论 Linux 6.12、本地普通文件的缓冲 I/O：不使用 O_DIRECT、O_SYNC、O_DSYNC 或 DAX，不引入用户态 stdio 缓冲、mmap、截断和文件替换。文件系统与设备正确实现 fsync 的同步要求。今天另设一个预先存在、长度为 4096 字节的文件，用 I17 标识；它的第一块缓存数据已经读入，字节偏移 100、101 分别为 A、B，其余字节不变。4096 是教学设定，不是所有 Linux 平台和缓存对象的固定大小。下面没有运行内核实验或测量性能。

最直接的方案，是每次修改都等存储可靠保存后才返回。对必须逐次确认持久化、写入量不大的任务，这是清楚的选择。但若应用连续更新同一小片数据，每次都承担设备等待，会把存储时延直接放进前台路径。反过来，若每个进程自己缓存文件，又需要协调其他读者：写者看见 XY，读者却拿着另一份 AB，谁来判断哪份有效？

Linux 的页缓存把问题改写成：由内核按文件和文件内位置管理共享的内存数据，缓冲读写先围绕这份状态进行，再由受追踪的后台工作把修改送往存储。它不只是读取旧内容的捷径，也可以暂时承接尚未写回的新内容。于是“别的读者能看见”和“断电后仍保留”分成了不同完成条件。[页缓存的 address_space 与写回职责](https://docs.kernel.org/6.12/filesystems/vfs.html#the-address-space-object)

沿昨天的对象关系再走一步。写者 fd 3 与读者 fd 5 来自两次独立打开，它们有独立的读取位置，但通往同一 I17 的文件映射和页缓存。本例记第一块缓存为 P0。以 4096 字节划分，偏移 p 属于编号 `p // 4096` 的块，块内偏移为 `p % 4096`；因此 100、101 都落在 P0。真实内核用 folio 管理缓存内存，一个 folio 可以涵盖多个基础页，这里的 P0 只是缩小到一块的教学模型，不把它当成物理磁盘扇区。

写者定位到 100，将 XY 交给 write，假设返回 2，没有错误或短写。新字节已复制进页缓存，并产生待写回工作；应用不必继续保留原来的输入缓冲区。读者在这次调用结束后定位到 100，通过普通缓冲 read 读两个字节，得到 XY，即使此时设备上的旧内容仍是 AB。这里选择两次调用先后发生，不声称并发覆盖写总能给读者一份原子快照。[write 返回量与可见性、持久性的区别](https://man7.org/linux/man-pages/man2/write.2.html)

因为独立的是打开位置，不是每个描述符各有一份文件内容。固定 Linux 6.12 提交 adc218676eef25575469234709c2d87185ca223a 中，通用缓冲读取 `filemap_read` 沿 file 的 f_mapping 取得缓存 folio，再复制到读者缓冲区；`generic_perform_write` 则通过文件系统的 write_begin/write_end 配合，把输入字节复制进 folio。这是可核对的通用路径，具体文件系统也有自己的实现，不能把函数名写成所有 I/O 的唯一调用链。[缓冲读的取页与复制](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/filemap.c#L2610)、[通用缓冲写的准备、复制和结束](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/filemap.c#L4015)

接下来不能只说“过一会儿刷盘”。内核至少要区分两件事：D 表示这块内存还有待安排的脏数据，W 表示有一轮写回尚未结束。它们对应 Dirty 与 Writeback 两类状态的教学压缩，省略文件系统的块级标记、索引标签和同步细节。只保留一个“脏或不脏”的开关，会把尚未开始的新工作与正在进行的旧工作混起来。

先从修改后的 D=1、W=0 开始。写回路径在必要保护下接手这批修改，清理对应脏标记并建立写回状态，进入 D=0、W=1。此时 D=0 绝不是“数据已持久化”，甚至连本轮 I/O 都还没结束。为看清并发问题，我们选择一种合法时序：设备已经取得本轮的 XY 数据，但完成通知尚未返回。

这时写者把偏移 101 的 Y 改为 Z，write 成功返回，页缓存变成 XZ，新修改重新置脏，得到 D=1、W=1。允许这种交错的路径必须把两份责任都记住。某些设备或文件系统路径要求写回期间内容稳定，会让修改先等待；本文不承诺所有路径都允许同样交错，更不声称每次写回都会复制一份不可变快照。[需要稳定页时的等待条件](https://docs.kernel.org/6.12/core-api/mm-api.html#c.folio_wait_stable)

第二幅图请盯住第四步：旧 I/O 完成时，到底该清掉哪一个状态？

![教学状态演化：缓存先为 XY，D=1、W=0；写回接手后 D=0、W=1；旧 I/O 通知到来前再改为 XZ，D=1、W=1；旧轮结束仅清 W，留下 D=1、W=0；下一轮写回成功且无后续修改时，D=0、W=0。选定旧轮只携带 XY 的时序，不代表实际 DMA 或磁盘追踪，也不表示已完成 fsync。](assets/figures/linux-pagecache-redirty.svg)

答案是只结束那轮 W，保留新产生的 D。第一轮送出去的是 XY，它的成功不能替后来的 XZ 注销工作。固定源码中的 `folio_clear_dirty_for_io` 参与接手脏数据，`__folio_start_writeback` 建立写回状态，`__folio_end_writeback` 结束 Writeback 并处理相关标签与计数，并不会因为旧轮完成就无条件清掉当前 Dirty。实际转换依赖锁、原子状态和文件系统协作，D/W 不是让应用直接赋值的两枚开关。[脏数据的接手与写回状态处理](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/page-writeback.c#L2987)

之后不再修改文件，下一轮把 XZ 写出并成功结束，才到 D=0、W=0。反事实也就明确了：若第一轮回调把 D 一起清零，XZ 可能失去再次写回的标记；若随后把缓存当作可直接丢弃的旧副本，重新读取可能只剩 XY，已经接受的 Z 无声消失。核心不变量不是“完成过一次写回”，而是新修改不能被旧完成事件冒领，仍有写回责任的数据也不能按普通干净缓存随意丢弃。

但 D=0、W=0 仍不等于一次 fsync 已经成功。设备完成某轮写入，可能只代表数据进入设备的易失缓存；页缓存状态也不是一份独立的断电保证。在本例两次 write 都结束、写者暂停后，对写者句柄执行 fsync 并检查成功，文件系统才须完成相应数据与所需元数据的同步责任，在既定存储保证下把 XZ 可靠保存。若是新建或改名的文件，目录项还有自己的同步要求；这里预先存在的 I17 没有名称变化。[fsync 的数据、元数据与目录边界](https://man7.org/linux/man-pages/man2/fsync.2.html)

这也说明 write 成功与“保存成功”之间多出的责任。write 允许短写，应用要处理实际返回量；后台写回失败，还可能到之后的 fsync 才报告，不能把前一次返回 2 当作后续工作永不失败的证明。fsync 失败时也不能继续宣布持久化完成。页缓存提供共享与缓冲，不提供跨多个写调用的业务事务原子性；判断内容是否完整，仍需文件格式或更高层协议。[写回错误怎样传给同步请求](https://docs.kernel.org/6.12/filesystems/vfs.html#handling-errors-during-writeback)

性能收益与成本来自同一个安排。多个修改有机会在内存中合并，后台可以组织写回，前台也能暂时避开逐次设备等待；代价是内存占用、复制和同步管理，以及还未兑现的存储工作。若制造脏数据的速度长期超过设备处理能力，缓存只会被耗尽。因此 Linux 不只有后台写回阈值，也会在压力增长后限制制造脏页的任务；缓冲写并不保证 write 永远快速返回。这与管道、RocksDB 的背压相通：暂时欠下的工作，必须最终反馈给入口。[脏页后台阈值与前台压力](https://docs.kernel.org/6.12/admin-guide/sysctl/vm.html#dirty-background-bytes)

还可以与 RocksDB 的 memtable 切换作一个更精确的比较。它可以把旧 memtable 冻结用于 flush，让新写入进入新的活动 memtable；两者同样避免把“正在输出旧工作”误当成“所有新工作已完成”。区别是 RocksDB 明确分开不可变旧表和新表，页缓存例子中同一块内存可以再次变脏，必须保留 D/W 等状态；而 memtable 的恢复与回收还受 WAL、文件发布等协议约束，不能拿一页的干净标记代替那些证明。[RocksDB 写入与 memtable 的分工](https://github.com/facebook/rocksdb/wiki/MemTable)

最后独立推演：若没有第二次改成 XZ，第一轮结束时 D/W 应是什么？若第二次修改在第一轮通知返回之后才发生，为什么仍不能省掉新一轮工作？先分清共享数据、待办责任与完成证据，再判断一个“成功”到底覆盖了哪次修改。今天的设计把前台数据使用与后台存储职责分开，又用明确状态把它们接回去；这比笼统地说“加一层缓存更快”更接近它在 Linux 中的价值。
