# Linux：文件名删掉了，为什么已经打开的程序还能继续读

服务正在往 app.log 写日志，管理员把这个文件改名归档，又创建了一份同名的新文件。文件名明明回来了，服务却还在向旧文件写；即使把旧名字也删除，磁盘空间也可能没有立刻释放。这不是缓存把删除操作忘了，而是 Linux 把“通过名字找到谁”和“已经拿到谁的使用资格”分成了不同关系。今天就沿一次打开、读取与删除，把这层分工讲透。

先把它放回系统。应用调用 open、read、close 等接口，Linux 内核中的 VFS 负责统一文件系统操作，再由具体文件系统处理相应对象。应用不必为每种磁盘格式重写读取逻辑，但普通文件、管道和设备仍有各自语义。本文只推演本地文件系统上的可定位普通文件，所有调用成功、串行执行，无其他写者、硬链接、内存映射或隐藏持有者；不扩展到网络文件系统、崩溃恢复和安全擦除。实现入口核对 Linux 6.12，接口语义核对 Linux man-pages，图和输出均为教学模型，没有运行 Linux 实验。[VFS 在系统中的位置](https://docs.kernel.org/6.12/filesystems/vfs.html)

最自然的模型是：一个文件名对应一份数据，read 时再按这个名字找数据。对一次性读取、期间没人改名的小工具，它很容易实现。但服务打开文件后可能运行数月，目录随时发生变化。如果每次读都重新查名字，删除会让已经开始的操作突然失去目标；同名新文件出现后，读取甚至可能悄悄跳到另一份内容。若反过来规定“有人使用就不能改名或删除”，目录维护又必须等待所有使用者退出。

洞察是让名字只负责寻找，让已经建立的引用负责继续使用。目录里的一项关联把名字连接到文件身份；打开成功后，进程得到的整数描述符连接到一份打开状态，再由它持有实际对象。于是名称可以变化，既有使用者的对象身份仍然稳定。不需要靠一个永远不改名的约定，让所有程序保持一致。

这里必须分清三种东西。app.log 是某个目录里的名字；inode 表示文件身份及相关元数据，例如大小、权限和硬链接数，不是把全部文件字节塞进去的一块结构，也不是全局永久编号。下面用 I17 作为同一文件系统中一个仍存活对象的教学标识。一次 open 则新建一个 open file description，保存当前偏移和文件状态标志；Linux 中对应 struct file。它的“file”不是又复制一份数据，而是一次打开所需的状态。[inode 的身份与链接数](https://man7.org/linux/man-pages/man7/inode.7.html)、[打开状态与描述符](https://man7.org/linux/man-pages/man2/open.2.html)

让 I17 的内容固定为六个字节 ABCDEF，没有换行。假设本进程的 0、1、2 已占用，接下来没有其他描述符分配。第一次只读 open(app.log) 返回 3，建立打开对象 X，偏移为 0。dup(3) 返回 4，它引用同一个 X；再次只读 open(app.log) 返回 5，建立新的打开对象 Y，偏移也为 0。X 与 Y 都使用 I17，数据没有复制，却可以各自记录读到了哪里。[dup 共享哪一层状态](https://man7.org/linux/man-pages/man2/dup.2.html)

现在按顺序读，每次请求两个字节。3 读出 AB，X 的偏移从 0 变成 2；4 接着读出 CD，因为它也使用 X，偏移再变成 4；5 仍从 Y 的偏移 0 读出 AB，Y 变成 2。这里假设各次读取返回所请求的字节数，未发生短读或错误；一般 read 允许少于请求量，位置应按实际返回数量推进。文中的“3 读两个字节”是操作简写，不是 C 的完整函数签名。[普通文件的读取与偏移推进](https://man7.org/linux/man-pages/man2/read.2.html)

观察第一幅图：为什么 3 与 4 会相互影响进度，5 却不会？

![教学引用图：目录中的 app.log 指向 I17，内容为 ABCDEF。描述符 3、4 共同引用打开对象 X，完成前两次读取后偏移为 4；描述符 5 引用独立对象 Y，偏移为 2。箭头表示关联或引用，省略挂载与 dentry 等中间结构，没有复制数据。](assets/figures/linux-vfs-open-state.svg)

差别不在描述符数字相邻，也不在它们属于同一进程，而在引用是否汇合到同一个打开对象。把偏移放进 inode，所有独立读取者就会争抢同一份进度；给每个描述符都复制独立偏移，又无法表达 dup 所需要的共同进度。单独设立打开状态，才允许应用在“同一份数据、独立进度”和“同一份数据、共享进度”之间选择。描述符本身还有 FD_CLOEXEC 等标志，不能据此推断 dup 以后所有标志都共享。

源码可以把这幅图接到真实入口。固定提交 adc218676eef25575469234709c2d87185ca223a 中，struct file 包含 f_inode、f_path、f_pos 等字段；dup 通过 fget_raw 取得既有 file 的受保护引用，再把它安装到新描述符槽位。ksys_read 则从描述符取得 file，使用其中的偏移执行 vfs_read，随后更新位置。读取没有把最初传入 open 的字符串再查一遍。真实引用获取和位置同步有并发协议，不能用“先拿裸指针，稍后加计数”代替。[打开对象字段](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/include/linux/fs.h#L1032)、[dup 的引用安装](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/file.c#L1379)、[read 沿打开对象取位置](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/read_write.c#L701)

此时对 app.log 执行 unlink。它移除的是目录里的这个名字。因为例中没有其他硬链接，I17 的硬链接数由 1 变成 0；这不等于打开引用也变成 0，X、Y 仍然持有它。之后普通 open(app.log) 若不带创建选项，会因名字不存在而失败，但 3、4、5 的使用关系没有被剪断。[unlink 删除名字与保留打开对象的规则](https://man7.org/linux/man-pages/man2/unlink.2.html)

接着创建并写好一份同名文件，内容为 XYZ，关闭创建它的句柄。这个新对象记为 I23；新的只读 open(app.log) 返回 6，建立对象 Z，偏移从 0 开始。旧引用不会自动迁移。4 继续读两个字节，得到旧 I17 的 EF，X 从 4 变成 6；6 请求三个字节，得到新 I23 的 XYZ，Z 变成 3。同一个路径字符串在两个时刻找到不同对象，没有任何一次读取需要在两个对象间拼接内容。

第二幅图追踪删除、重建和释放：新名字出现后，哪些关系改变，哪些仍然存在？

![教学时序：unlink 后再创建同名 app.log，目录关联改为新对象 I23，内容 XYZ；旧描述符 3、4、5 仍使用 I17，内容 ABCDEF。4 续读 EF，6 读 XYZ。关闭 3、4 仍有 Y 保留 I17，关闭 5 后，在无其他硬链接和持有者的假设下，旧对象才满足回收条件。](assets/figures/linux-vfs-unlink-lifetime.svg)

读取也有结束条件。此时 3 与 4 共用的 X 已到长度 6，再用 3 请求一个字节，read 返回 0；5 仍在位置 2，还能读出 CDEF 才到末尾。普通文件的这次 EOF 表示当前偏移没有更多字节，不要求所有写者关闭；如果文件后来增长，后续读取仍可能获得新数据。这与早先管道篇的“缓冲区读空且所有写端引用关闭”不同：接口可以统一，结束条件必须依对象解释。

最后关闭 3，只是少了一个通往 X 的描述符，4 仍可使用 X；再关闭 4，X 的这组使用关系结束，但 Y 仍让 I17 存活。直到关闭 5，且本例排除的其他持有关系确实不存在，旧文件才可回收。硬链接数统计的是名字，不是打开次数；真实系统中映射也能在描述符关闭后继续有效，因此不能把“本进程看不见旧 fd”当成系统再无使用者。[close 的释放语义](https://man7.org/linux/man-pages/man2/close.2.html)、[映射可以跨越描述符关闭](https://man7.org/linux/man-pages/man2/mmap.2.html)

由此得到不变量：名字的移除不能让仍有效的引用突然指向已回收对象；旧引用也不能因为同名对象出现而被悄悄改绑。反过来，若 unlink 立即释放 I17 的存储，再给新文件复用，4 的下一次读取可能碰到别人的数据或失效状态。若内核把 4 自动改指 I23，之前读到 ABCD，接下来却按旧偏移 4 访问长度只有 3 的新文件，连贯读取就失去了意义。

这也解释了日志轮转的成本。把旧文件改名、创建新 app.log，只安排了名称；已有写句柄仍使用旧对象，需要服务按约定关闭并重新打开，才能切换输出。rename 本身不会改绑旧描述符，unlink 后遗留的打开引用还可能继续占空间。代价转移给了使用者的生命周期管理，收益则是目录维护不必强制中断已有操作。每次独立打开还需要内核维护打开对象、描述符表项和引用同步；忘记关闭的句柄也会延长资源占用。[改名不影响已打开描述符](https://man7.org/linux/man-pages/man2/rename.2.html)

不过，稳定身份不等于稳定内容。另一个句柄若原地修改或截断 I17，旧读者并没有自动获得历史快照。RocksDB 的旧 Version 与这里有相似的持有结构：新入口改变，不代表旧使用者已经离开；但 RocksDB 依赖不可变 SST、版本与快照规则维护读取语义，普通文件引用只保住对象生命，并不保住旧字节。把这两种保证分开，才能判断“保留旧引用”究竟解决了什么。[RocksDB 的存活文件与 Version](https://github.com/facebook/rocksdb/wiki/How-we-keep-track-of-live-SST-files)

昨日检查点还有一个边界可带过来：名称操作在运行中成功，不等于断电后状态已经持久化。文件数据与目录项的同步是额外职责，不能因为旧 fd 还能读，就宣布删除或重建已安全落盘。[文件同步与目录同步的区别](https://man7.org/linux/man-pages/man2/fsync.2.html)

最后自己推演：若删名前另有一个硬链接 backup.log 指向 I17，关闭全部旧描述符后，为什么还不能仅凭刚才的条件判断旧数据会消失？若把 dup(3) 改成第二次 open，前两次读取各会得到什么？不必背对象名，沿图中的两层共享关系重新推导。这个设计值得欣赏的地方，是把发现对象、维持使用状态和决定回收分开，让名称的灵活变化与既有操作的连续性同时成立；应用仍要承担关闭资源、切换句柄和保护数据内容的责任。
