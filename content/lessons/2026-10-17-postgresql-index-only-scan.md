# PostgreSQL：索引里明明有答案，为什么还要回表

应用反复查询账户 7 的额度：`SELECT balance FROM accounts WHERE id=7`。我们已经有按 id 查找的 B-tree，能不能顺便把 balance 放进去，让数据库从索引里直接返回 100？如果表很大，少走一次散落在别处的表页，似乎就是现成的优化。但前两篇带来了一个障碍：索引找到的可能是旧版本，也可能是另一个事务尚未提交的新版本。“拿得到数值”与“这个数值属于我的快照”，不是同一件事。

今天继续 PostgreSQL 18 的普通 heap 表。表页保存行版本及其事务信息，B-tree 负责按键定位，执行器负责按计划扫描并返回结果，VACUUM 维护可回收状态。我们只追一个接口问题：执行器什么时候可以相信一个索引候选，从而跳过访问表页的可见性检查？这能把快照、索引和后台维护连接成一条因果链。

最直接且正确的办法，是所有候选都回表：拿到 TID，即页号和行指针槽位，再检查该行对当前快照是否可见。表页已经在缓存、查询很少、更新频繁时，这种做法完全可能足够好。不过，对大量稳定数据，它会重复检查早已没有争议的行。另一种自然想法是把事务信息也复制进每个索引。那就要让行版本状态与多份索引一起维护；今天不把这说成所有数据库都不可行，只问 PostgreSQL 能否利用自己现有的职责分工省掉重复工作。

先解决“数值在哪里”。教学表使用下面这一个唯一 B-tree，id 是搜索键，balance 是叶层携带的附加数据，唯一性只约束 id。查询不需要其他字段，因此所需数值都能从这个索引取得。这是覆盖查询的条件，不保证优化器一定选用它，也不保证执行时一次都不回表。[覆盖索引、INCLUDE 与扫描适用条件](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)

```sql
CREATE UNIQUE INDEX accounts_id_balance
    ON accounts (id) INCLUDE (balance);
SELECT balance FROM accounts WHERE id = 7;
```

这些 SQL 用来说明接口，没有在本机执行。以下页号和事务号也都是教学安排：初始行由已提交的 T100 创建，额度为 100，位于表页 42、槽位 1；该页此前已被确认全部可见。只读 Repeatable Read 事务 R 在更新前通过首次 SELECT 固定旧快照。T101 随后把额度改为 90，新行放在同页槽位 4，并正常提交。新读者 N 此后才取快照；先不做旧行及索引项清理。

这里特意改变了昨天的一个条件：balance 现在也被普通 B-tree 引用。修改 100→90 不符合昨天的 HOT 条件，因而新版本需要新索引项。索引中可能暂时同时保留 `(id=7,balance=100,TID=(42,1))` 与 `(id=7,balance=90,TID=(42,4))`。唯一索引并不承诺物理上只留一个同键条目；多版本检查与唯一性维护要让这种过渡状态仍符合约束。[唯一索引为什么允许物理上的同键条目](https://www.postgresql.org/docs/18/index-unique-checks.html)[非 HOT 更新与索引列范围](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/heap/README.HOT#L142)

现在换一个提问方式。如果某个表页上所有行版本都已经老到对现存读者可见，后续读者在它再次变化前也都能看见，那么还需要对这个页上的每一行重复证明吗？关键洞察是，把许多逐行判断合成一份按页保存的充分条件。PostgreSQL 为表维护 visibility map，称为可见性地图。每个表页有一个 all-visible 位；它为 1，表示系统已经确认这个页满足全部可见条件，可以让符合要求的索引扫描直接采用索引数据。[可见性地图与两种标记](https://www.postgresql.org/docs/18/storage-vm.html)

地图实际为每个表页保留两个位，另一个 all-frozen 服务冻结维护；今天只追 all-visible，把它记作 `V[页号]`。V=0 不是宣告行不可见，而是没有这份整页保证，必须回到精确检查。这个不对称很重要：宁可多检查，不能凭不可靠的“应该没问题”返回错误年代的数据。

第一幅图里，索引同时给出了两个数值。观察 V[42]=0 时，究竟是谁决定 R 返回 100、N 返回 90？

![教学图：T101 提交后，索引仍可能有账户 7 的两个候选，额度 100 指向 (42,1)，额度 90 指向 (42,4)。页 42 的 V=0 时必须访问表页检查快照；旧快照 R 接受 100、排除 90，新快照 N 排除 100、接受 90。两者输出均取自通过检查的索引项。箭头表示检查流程，省略其他行。](assets/figures/pg-ios-candidates.svg)

扫描先取得一个候选，再查其 TID 所属表页的 V。若 V=1，可跳过这次回表；若 V=0，就访问表页，用查询的快照检查对应版本，不可见则继续下一个候选。R 检查旧行，认为 T101 的替换不属于自己的历史，接受索引中的 100；检查新行则排除 90。N 的结论相反，接受 90。处理完 id=7 的候选范围，本次查询结束，各返回一个额度。这里按候选分别解释，不要求两个同键条目具有图示的物理遍历顺序。

在这个执行节点里，即使回表检查了可见性，最后投影所用的数据仍来自索引项。回表不是总为“补取缺少的列”，也可能纯粹为了核实这条记录能不能用。PostgreSQL 18.0 固定提交 `3d6a828` 的 `IndexOnlyNext` 明确执行了地图检查与 `index_fetch_heap` 回退，然后从索引提供的数据填充输出。因此，计划叫 Index Only Scan，不等于实际运行的 Heap Fetches 必为零。[执行器的检查、回退与输出来源](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/executor/nodeIndexonlyscan.c#L120)

现在补上动态过程：最初 V[42]=1，为什么刚才又成了 0？因为更新会使整页保证失效。第二幅图要观察，提交能否直接把这个位设回去，以及 R 还在时清理者为什么必须等待。

![教学时序：初始页 42 已确认全部可见，V=1，可直接使用索引中的 100。T101 更新 100→90 时撤销整页保证，V=0；提交后旧快照 R 仍需 100，V 仍为 0。R 及其他保护条件不再阻碍后，本例 VACUUM 清理旧版本与旧索引项，并确认页上其余行也全部可见，才把 V 置为 1；新查询可直接返回索引中的 90。向下表示先后，不表示固定等待时长。](assets/figures/pg-ios-lifecycle.svg)

T101 修改表页时清除其全部可见标记及地图位。清位发生在新索引入口发布之前；执行器读取新入口时，必须也能观察到保证已被撤销。源码利用索引页锁的内存顺序保证这一点，删除路径还要结合取得快照时的同步关系。这不是“一个位天然线程安全”，而是表示与发布次序共同形成协议。[写者清位的位置](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/heap/heapam.c#L4096)、[读者为何不会用过期保证接受新条目](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/executor/nodeIndexonlyscan.c#L134)

T101 提交也不等于页已对所有人可见。R 还要读 100，新版本 90 对它仍不可见，旧版本也不能提前丢弃。等 R 结束，其他相关保护条件也允许回收后，本例安排一次 VACUUM：清理死版本及旧索引项，并检查该页剩余行是否均已提交且足够老。只有整页满足条件，才能重建 V=1；单独“没有人正在写”不够，“账户 7 已经稳定”也不够，因为同页其他账户可能还不满足条件。[VACUUM 的全部可见判断](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/heap/vacuumlazy.c#L3605)

不变量现在可以清楚地说出来：扫描能够据以跳过回表的 V=1，必须由相应的整页可见性保证支持；让保证失效的修改必须按同步规则撤销它。反过来，V=0 可以暂时保守。若 T101 产生新索引项却忘了清位，R 扫到 90 就可能跳过判断，接纳不属于旧快照的值，甚至把两条候选都返回。精确检查被省掉后，没有后续步骤自动纠正这次错误。相反，清位后迟迟不重设，只会让本可省掉的检查继续发生，正确答案仍能保住。

这份保证还得跨越崩溃恢复。表页自身的全部可见标记与地图标记需要保持协议关系；如果恢复后地图说可以跳过，表页却丢失了让后续写者知道“应清位”的状态，未来更新仍可能错误沿用旧保证。源码因此说明置位时的 WAL 要求，以及修改重放必须同步撤销地图位。我们不展开完整恢复路径，但不能把它当作掉电后随便保留也安全的性能缓存。[地图标记的 WAL 与恢复约束](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/heap/visibilitymap.c#L34)

为什么值得多查这张图？作一个容量计算：假设表的 heap 占 1 GiB，页为 8 KiB，共 131072 页，每页两个地图位，位数组约 32 KiB。这里忽略地图页头、取整及缓存管理开销，不是测量结果。它不能证明某次查询快多少，却解释了为什么小地图更有希望驻留缓存，而大表页未必都能留下。收益是用地图访问替代部分表页访问，并不是不再读索引、不再访问任何辅助状态。[地图的页号到位数组映射](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/heap/visibilitymap.c#L103)

代价也很具体：按页压缩，意味着同页一个账户更新，也会影响其他未变账户跳过检查的机会。更新越频繁，V 越容易为 0；长快照与清理进度都会限制重新置位。覆盖索引还复制了 balance，增大索引，并让修改 balance 失去昨天的 HOT 优化机会。对于频繁写的账户表，这个交换未必合算；变化少、覆盖查询多的数据才更可能从中受益。VACUUM 因而不仅负责清空间，也参与恢复一部分读取优化条件。[后台维护与索引扫描的联系](https://www.postgresql.org/docs/18/routine-vacuuming.html#VACUUM-FOR-VISIBILITY-MAP)

最后接回 Bloom 过滤器。Cassandra 用它可靠排除某些不含目标分区键的 SSTable，模糊情况继续精确查找；这里 V=1 可靠地放行可见性检查，V=0 则回到行版本判断。共同结构是把充分证据放进小摘要，把不确定性交给原有正确路径。区别在于，Bloom 因哈希叠加产生概率性误报，地图按页保存确定条件，保守程度来自更新与维护进度；不能把 Bloom 的误报率公式拿来估算地图命中率。[Cassandra 中的过滤与精确查找](https://cassandra.apache.org/doc/stable/cassandra/managing/operating/bloom_filters.html)

留一个独立推演：账户 7 不变，但同在页 42 的账户 8 刚被更新，查询 7 还能只因“它没变”就跳过回表吗？若把更多列加入 INCLUDE，你获得了哪些查询能力，又让哪些写入更贵？这个设计值得欣赏之处，是把稳定数据的共同事实压缩成可复用的证明，同时明确规定谁撤销、谁重建以及不确定时退回哪里。本文核对文档与固定源码，没有运行数据库、采集 EXPLAIN ANALYZE、注入崩溃或测量性能；图和数值都是教学推演。
