# Go 的 context 怎样把取消沿调用树传下去

商品页同时查推荐和库存。推荐慢了，页面可以降级成没有推荐的版本，但还要等库存。推荐服务已经发出一笔画像查询，页面决定放弃推荐时，这笔查询也该停止。如果用户随后离开，剩下的库存查询也失去用途。服务面对的是两种不同范围的停止请求，有时只撤掉一条分支，有时要撤掉整项工作。

前一讲的 `select` 已经能让一个 goroutine 同时等结果和取消。现在多了一个问题，谁来决定哪些等待者该收到同一次取消？Go 把这层关系放进标准库 `context`，由调用方把上下文传给下游。运行时提供 channel 的关闭和唤醒，业务代码在等待点观察信号并退出。以下以 Go 1.25.0 官方源码中的普通 `WithCancel` 路径为准，状态交错是教学推演。[Go 官方的 context 设计说明](https://go.dev/blog/context)

## 用调用关系表示取消范围

如果全部工作共用一个停止开关，关掉它时库存也会一起停。只有整项工作同进同退时，这样做才合适。也可以给每个操作单独建开关，由入口保存所有关闭函数。入口很容易登记自己直接启动的操作，可画像查询是推荐模块在更深处创建的。要让入口也管到它，就得把每层新增和结束的任务都同步到同一张清单，还要保证清单与取消操作之间没有空隙。

Go 让每一层只描述自己的直接关系。请求用 `WithCancel(context.Background())` 得到 R 和 `cancelR`。推荐 S、库存 I 分别从 R 派生，画像 H 从 S 派生。每次 `WithCancel` 返回派生的上下文和一份取消它的函数。下游只需拿着上下文就能观察取消。持有 `cancelS` 的推荐调用方可以停止 S 及其下游。库存 I 要响应的是自己的取消或父节点 R 的取消。[WithCancel 的接口契约](https://pkg.go.dev/context@go1.25.0#WithCancel)

取消推荐后，R 的子集合会留下哪一条边？库存为什么仍能继续等结果？

![图一。R 的直接子节点是推荐 S 和库存 I，S 的子节点是画像 H。第一次取消后 S 和 H 的 Done 已关闭，R 仍登记 I。第二次取消关闭 R 和 I 的 Done。箭头表示派生关系或阶段先后，颜色区分可继续与已通知。](assets/figures/go-context-cancel-tree.svg)

最初 R 的直接子集是 `{S, I}`，S 的直接子集是 `{H}`。这些集合保存的是取消传播需要访问的上下文。几个 goroutine 也可以共用 H，各自接收同一个 `H.Done()`，因此不能从图里的节点数推算任务数。以画像查询为例，若结果尚未就绪，它可以在 `select` 中同时等待结果和 `H.Done()`。后者一旦关闭，已在等的接收者可以继续，后来进入等待点的接收者也能观察到取消。一次关闭就把通知保留给了所有观察者，发送一条普通消息则只交付给一个接收者。[关闭 channel 广播取消的例子](https://go.dev/blog/pipelines#explicit-cancellation)

当入口决定降级推荐并调用 `cancelS()`，S 在自己的锁保护下记下 `context.Canceled`，关闭已有的 Done，再访问 H。H 也记录取消错误并关闭自己的 Done。假设画像结果此时仍未就绪，画像的等待可以沿取消分支返回 `H.Err()`，推荐可以结束这一支的工作。第一次调用清空 S 的直接子集，并在释放 S 的锁后从 R 的子集合里摘掉 S。R 和 I 保持可用。随后用户离开，`cancelR()` 关闭 R 的 Done，传播给它仍登记的 I。若库存也在等待且没有结果，它沿自己的取消分支返回。图中的已关闭描述通知状态，任务实际何时退出还取决于调度和业务的退出路径。[Go 1.25.0 的取消、遍历与解除登记](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L544-L577)

节点尚未有人取用 Done 时，源码可以直接保存一个预先关闭的 channel，后来第一次读取便得到可接收的信号。若已经有人等在该节点的 Done 上，则关闭原来那个 channel。重复调用取消函数会遇到已经写入的错误，直接返回。这使取消状态保持单向变化，旧观察者和晚到的观察者都能收到一致的结果。[Done 的延迟创建和取消路径](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L448-L461) · [首次取消时的状态写入](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L554-L566)

## 新孩子登记时，取消也可能已经发生

沿用上例。推荐模块原本准备发一个备用查询，正在从 S 派生 L，入口同时决定取消 S。如果 L 先检查 `S.Done()`，看到还开着，然后过一会儿才把自己加入子集合，会发生什么？在这段间隙里，S 可能已经遍历完 H 并清空集合。若 L 此时仍按先前的检查结果登记，就会加入一个再也不会被正常取消流程扫描的集合。S 已取消，L 却可能一直等结果。

标准库在识别出普通的 `cancelCtx` 父节点后，会持有父节点的锁，再检查取消错误和登记新孩子。取消路径也用这把锁写入错误和遍历子集合。图中两种顺序都从 L 尚未完成登记开始。想一想，谁获得 S 的锁决定了哪一步兑现 L 的取消？

![图二。L 登记先取得 S 的锁时，后续取消从子集合访问 L。S 取消先取得锁时，随后登记在持锁复查时发现 S 已取消，直接取消 L。图示关注初次 Done 检查已通过的交错，箭头表示步骤先后。](assets/figures/go-context-register-race.svg)

若 L 先持锁，S 还活着，L 就进入 S 的子集合。随后 S 取得锁并取消时，集合里已经有 L，遍历会把通知传到它。若 S 先取得锁并完成取消，L 在持锁复查时会直接得到父节点的错误，走自身的取消路径。若 L 第一次检查 Done 就发现它已关闭，还可以更早返回一个已取消的子节点。这三条路守住同一个不变量：**一次完成的派生要么已经接入父节点的取消传播，要么直接继承已经发生的取消。** 在取消传播尚未走完整棵树时，各节点的 Done 可以先后关闭。[父节点初查、持锁复查及登记](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L471-L503)

## 谁承担传播，谁负责真正退出

把关系登记在相邻两层，入口只需保留 `cancelS` 和 `cancelR`。推荐模块新增一个备用查询时，由它把 L 接到 S，入口无需知道 L 的存在。这节省了全局维护任务清单的成本。代价落在每个可取消节点的状态、锁和子集合上。取消方要遍历尚登记的后代，按树向下取得锁。每个已创建的 Done 还可能有多个等待者需要唤醒。操作正常结束后也应调用自己的取消函数，使父节点尽快释放对这条分支的引用。[context 的资源释放约定](https://pkg.go.dev/context@go1.25.0#WithCancel)

普通派生用这些登记就能传信号，避免为每条关系各开一个监听 goroutine。若父上下文的实现不能复用这套子集合，固定版本源码还会尝试通过父节点的 `AfterFunc` 方法登记回调，或起一个 goroutine 同时等父节点和子节点的 Done。业务仍要负责在阻塞 I/O 或结果交付时传递并检查取消信号。`CancelFunc` 返回后，要求确认画像已关闭连接、库存已释放资源的调用方，还需要等这些工作各自报告结束。[兼容其他父上下文的传播路径](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/context/context.go#L505-L526) · [CancelFunc 的完成边界](https://pkg.go.dev/context@go1.25.0#CancelFunc)

可以改变一个条件再推演。若画像查询在一个耗时操作里从不观察 H，`cancelS()` 返回后，页面可以看到 H 的 Done 已关闭。此时依据哪个状态判断画像连接已归还？如果业务必须等到连接归还才能开始下一项工作，这项确认应由谁发出？

Linux 的 `cgroup.kill` 也让上层以一个子树表达操作范围，并要处理动作与成员变化的交错。在 cgroup v2 的非根、非线程模式 cgroup 写入 `1`，内核向这一组及后代组中的进程发送 `SIGKILL`，并处理并发 fork 和迁移。Go 的边由代码派生上下文时建立，动作沿这些边发布协作取消信号，接收者可以执行自己的收尾逻辑。两者都借用分组关系圈定影响范围，但一个依靠内核终止进程，一个依靠库和调用者共同完成退出。[Linux 内核的 cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)
