# RocksDB：读到稳定旧值，为什么提交仍可能失败

继续昨天的两份额度：甲有 100，乙有 40。请求 T1 要从甲转给乙 10，请求 T2 要转 20。它们同时读取 (100,40)，分别算出 (90,50) 和 (80,60)，再先后提交完整 WriteBatch。最终是 (80,60)，总量仍为 140，却只体现了后一笔转移；两笔都成功时应得到 (70,70)。没有半份更新，也没有不一致读取，业务仍然出错。今天要解决的矛盾是：怎样让计算并发进行，又不允许它悄悄用过时依据覆盖别人的进展。

RocksDB 是嵌入应用的键值引擎。前面的 LSM、WAL、文件发布和快照解释了数据怎样存、怎样恢复、读者怎样守住旧答案；WriteBatch 解释了怎样整体公布多次修改。事务层接在这些机制之上：先暂存计划写入的编辑，同时记录需要保护的键，提交前决定是否允许把编辑交给引擎。原子批次保障结果一起生效，冲突检查保障生成结果的依据没有遭到不允许的干扰，两者承担不同职责。

最自然的方案，是从第一次读取到最后写入都持有应用互斥锁。它确实能解决本例：T2 等 T1 完成，随后按 (90,50) 算出 (70,70)。竞争集中在少数键、计算很短、访问入口统一时，这个方案值得保留。问题是，把所有额度共用一把锁，会让修改互不相关账户的请求也排队；若计算耗时，等待就覆盖整个计算过程。按键加锁能提高并发，却要维护锁的归属、顺序和退出路径。

乐观并发控制选择另一种分工：先允许各自读取和计算，提交时再证明依据仍然可用，证明失败就撤销这次尝试。这不是假定冲突不会发生，而是把“事前等待”转成“事后检测和重做”。RocksDB 有 `OptimisticTransactionDB` 和采用悲观控制的 `TransactionDB`，不能把两者的检查时机混用。本文选前者，并明确选择固定源码中串行校验策略 `kValidateSerial`；该提交的默认策略是并行校验，本篇没有把串行路径写成默认。[事务类型与适用取舍](https://github.com/facebook/rocksdb/wiki/Transactions)、[校验策略定义](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/include/rocksdb/utilities/optimistic_transaction_db.h#L34)

用一个教学时序看清楚。仍是单列族、普通键值、普通有序写入；不讨论用户时间戳、范围删除或其他特殊事务路径。初始甲@1=100、乙@2=40 都已完成。T1、T2 各创建事务并 `SetSnapshot()`，取得边界 2，再把事务的快照交给读取选项。两者通过 `GetForUpdate` 读取甲、乙，得到同一组旧值，同时登记这两个键从序号 2 起需要保护。这里的序号是修改顺序，不是时间；时序与状态都是教学推演。

```text
事务 T：在按串行校验策略打开的 OptimisticTransactionDB 上创建
T.SetSnapshot()
read_options.snapshot = T.GetSnapshot()
甲值 = T.GetForUpdate(read_options, 甲)
乙值 = T.GetForUpdate(read_options, 乙)
T.Put(甲, 甲值 - 转移量)
T.Put(乙, 乙值 + 转移量)
提交结果 = T.Commit()
```

这是接口骨架，不是已运行的完整程序；实际调用必须检查每次读取、编辑及提交的 Status，失败后不能继续当作成功。事务的 `SetSnapshot` 决定校验依赖所用的基准，`ReadOptions.snapshot` 决定返回哪个版本。让两者使用同一快照，才把本例的计算依据与校验边界接起来；只给读取选项一个旧快照，不能自动等同于设置了事务的冲突基准。[读取快照与校验基准的区别](https://github.com/facebook/rocksdb/wiki/Transactions#repeatable-read)

`GetForUpdate` 这个名字容易让人以为已经独占了键。在这里，源码中的 `TryLock` 实际登记键及其基准序号，然后返回成功，冲突检查留到 Commit。事务 Put 也会登记写入键；所以本例甲、乙都要写回时，它们本来就在写入保护范围里，不能把成功全归功于多加两个 `GetForUpdate`。显式登记读取依赖，是为了把这项职责说清，并保护后面要讨论的只读条件。[乐观事务的依赖登记](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/utilities/transactions/optimistic_transaction.cc#L153)、[读取与 Put 的登记入口](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/utilities/transactions/transaction_base.cc#L301)

T1 先提交。它需要保护甲、乙，基准都是 2，检查时没有发现更晚修改，于是把暂存的两次编辑交给原子写入，生成甲@3=90、乙@4=50。对其他普通读者，新状态整体生效，T1 获得成功。T2 使用的底层快照仍对应 (100,40)，它也已经暂存了 (80,60)，但“旧答案还能读取”不代表“旧依据还能提交”。事务若读取自己已暂存的键，会先看自己的编辑；这里的旧答案指底层快照。

现在 T2 提交，校验发现甲的最新修改序号 3 大于基准 2，已足以拒绝这次尝试；乙的 4 也同样越过边界。在本例假设修改历史足够、没有其他错误时，返回冲突状态 Busy，T2 的暂存批次没有交给正常写入生效，数据库仍是 (90,50)。先看图：T2 的读取为什么可以成功，提交却必须失败？

判断根据的是修改序号，不只是当前值是否碰巧相等。如果甲被别人改过，又改回 100，最新修改仍晚于 2，不能仅因数字回到了原值就宣称期间无人干扰。固定提交 `72beaf8` 的 `TransactionUtil` 查询受保护键的最新修改，普通序号规则下晚于基准就给出 Busy。这是保守的冲突条件，不是理解任意业务计算后自动判断它是否还能交换顺序。[冲突条件源码](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/utilities/transactions/transaction_util.cc#L109)

重试还有结束条件。应用先终止 T2 的失败尝试，再创建新的事务 T2′，重新取得边界 4，读取 (90,50)，重新计算转移 20 的结果 (70,70)。若这次校验前没有相关新修改，提交生成甲@5=70、乙@6=70，两项请求才都完成。如果只是反复 Commit 原来的 T2，它仍拿着边界 2；若换个新 batch，却仍写 80、60，计算错误也没有消失。

为什么不能在应用里先检查一下最新序号，再调用 WriteBatch？因为检查通过与写入之间还可以插入别人：T1、T2 都通过检查，随后依次覆盖，最初的错误又回来了。必须把“检查仍成立”与“接受这份结果”放进同一个受保护的提交次序。在选定的串行路径中，`CommitWithSerialValidate` 使用写入回调，让校验进入引擎写入队列；该回调禁止和其他写者批量合并，失败的检查不能进入正常写入。回调成功后的批次再由昨天的安装、整体发布和 WAL 路径承接。[串行提交回调](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/utilities/transactions/optimistic_transaction.cc#L72)、[禁止批量合并的校验回调](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/utilities/transactions/optimistic_transaction.h#L82)

核心不变量是：成功提交时，已登记键从校验基准起不能发生被本例规则判为冲突的修改，而且检查结果到本次写入之间不能失去保护。范围同样重要。若转移还依赖一个单独的“允许转移”键，但只用普通 Get 读它、从不修改它，它不会因为事务存在就自动成为读取依赖。别人把许可关闭后，这份计算仍可能提交。使用 `GetForUpdate` 登记许可键，才能让它参与检查。按键登记也不等于自动登记“所有满足某个范围条件的未来键”；不能把本篇点键示例推广成完整 SQL 谓词保护。

证明本身需要资源。这个乐观实现做基于内存历史的冲突检查；如果保留的 memtable 修改历史不够老，不能证明从边界 2 起没有干扰，它可能返回 TryAgain。它表达证据不足，不能假装成确定发现了另一笔修改。长期事务即使还能通过 SST 和快照读到旧值，也不因此保证有足够内存历史完成这项检查。这又把读取历史保留与提交校验历史区分开来。[历史不足的状态分支](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/utilities/transactions/transaction_util.cc#L72)

代价由此很具体：每个事务维护依赖集合与暂存编辑，提交要查询修改历史，冲突时已做的计算要重来，串行校验还占用共同写入次序。竞争较少、准备阶段有较多工作时，避免长期持锁有吸引力；热点键频繁变化时，重试会反复浪费工作，悲观控制或直接排队反而可能更合适。应用应区分冲突、证据不足与其他错误，设置合理尝试次数和等待，确保重复计算不会重复执行不可撤销的外部动作。提交成功后的掉电承诺仍由 WAL、同步选项及底层存储承担，冲突检查不能替代持久化协议。

这个结构可以与 Git 的引用更新比较。先基于提交 C0 准备 C1，再用 `git update-ref` 提交“把引用改为 C1，但要求它仍是 C0”，若其他人已经推进引用，就拒绝这次更新。共同结构是先在外部准备，再把旧依据当作发布前提；差异是 Git 这里核对单个引用的预期对象标识，而 RocksDB 核对一组键从基准序号以来的修改历史。Git 若把引用移走又移回 C0，当前预期值比较仍可能通过，不能照搬 RocksDB 的序号干扰判断。两者都是条件发布的结构比较，不是历史传承结论。[Git 引用更新的旧值前提](https://git-scm.com/docs/git-update-ref)

最后独立推演：若 T1 只修改另一个不在 T2 依赖集合中的键，T2 是否一定冲突？若 T2 快照仍能读旧值，却缺少足够内存修改历史，为什么应拒绝而不是猜测？这个设计值得欣赏的地方，是把长时间计算与短时间接受结果分开，同时把“我依赖过什么”变成可检查的契约。自由并发来自明确的保护范围和拒绝条件，也必然由记录、校验与重试支付成本。本文核对了官方文档和固定提交的静态源码，没有运行 RocksDB、制造并发冲突或测量性能；图中序号与状态只用于推演。
