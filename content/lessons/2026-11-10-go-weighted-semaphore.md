# Go 的加权信号量为什么让小任务等在大任务后面

昨天的 singleflight 让几个请求共用一次回源。今天换一个条件。图片服务收到的都是不同文件，解码工作无法合并，但它们需要共用进程里有限的内存预算。假设服务按图片尺寸和解码格式事先估算开销，把预算换成 5 个额度单位。A 需要 3 个，B 需要 1 个，正在解码。随后 C 需要 4 个，D 需要 1 个。此时还有 1 个空位，D 明明放得下，为什么 Go 的加权信号量仍让它排队？

最容易写的是限制同时运行的任务数，比如用带缓冲的 channel 给每个任务一个位置。如果图片差不多大，一个位置代表一张图就足够了。大小差异大时，同样两个位置可能是两张缩略图，也可能是两张大图。若位置数按最坏情况设置，轻任务扎堆时会浪费预算。可以进一步让任务按重量从 channel 逐个取额度，但这样会引入部分持有。仍以 5 个单位为例，两个都需要 4 个单位的任务分别拿到 3 个和 2 个，接下来都等对方让出额度。按照“凑齐才做，做完才还”的规则，两者都无法开始。

`golang.org/x/sync/semaphore` 把准入放在解码之前。一次 `Acquire(ctx, n)` 申请整个重量，成功后调用方才进入受控工作，真正结束后以 `Release(n)` 归还。总预算在创建时固定，一个锁保护已占用量与等待队列，业务代码在锁外运行。本篇按 v0.16.0 源码推演，5 个单位及任务重量都是教学设定，所有重量取正整数。 [Weighted 的状态与调用契约](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L19-L59)

这里的预算由进程内一个共享的信号量维护。每次解码都走同一个入口，大小不同的图片才会算在同一本账上。实际接入时，可以在分配像素缓冲区前申请，成功后把归还安排在覆盖解码和清理的作用域里。若解码结果中的像素缓冲区会移交给下游并继续占用内存，额度也要保留到下游用完，或者把这段占用单独纳入预算。并发上限来自准入点和释放点的位置。

## 空位先留给谁

记总预算为 5，已占用量为 `cur`，可用量就是 `5 - cur`。A 和 B 已成功准入，`cur = 4`。C 来时凑不齐 4 个单位，代码把它的重量和一个专用的 `ready` 通道记在队尾，随后放锁等待。排队的 C 持有 0 个单位。D 紧接着来，1 个单位本来够它用，但直接授予需要同时满足容量足够和队列为空。D 因此排在 C 后面。连无需等待的 `TryAcquire(1)` 也检查队列为空，避免从另一个接口绕过队首。 [Acquire 的登记路径](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L38-L75) · [TryAcquire](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L109-L118)

假设两个等待者都未超时，B 先完成，A 后完成。沿图一看，哪次归还会真的改变排队状态？C 拿到 4 个单位之后，还有多少留给 D？

![图一。总预算 5。A 持有 3、B 持有 1，C 申请 4 后排在 D 的 1 之前。B 归还后空闲 2，仍等队首 C。A 归还后空闲 5，在一次队列扫描中先划给 C 4 个、再划给 D 1 个。箭头表示教学时序。](assets/figures/go-weighted-admission.svg)

B 归还后有 2 个单位可用，`notifyWaiters` 只看队首，C 要 4 个，扫描到此停止。等 A 归还，空闲达到 5。扫描在锁内先把 C 的 4 个单位计入 `cur`，移走队首，再关闭 C 的 `ready`。它接着看 D，刚好还剩 1 个，于是也为 D 记账、移出队列并通知。两个通知完成后，空闲降到 0，队列清空。实际运行时 D 有可能比 C 先得到 CPU，分配顺序约束的是谁先取得预算。等两者各自完成并归还，`cur` 才回到 0。 [归还与队首授予](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L121-L159)

这里有一个比唤醒顺序更重要的不变量。每份已授予的额度都必须体现在 `cur` 中，即使收到通知的 goroutine 还没恢复运行。假如唤醒就代表获准，但要等任务自行加账，A 归还后通知 C 和 D 时，账面可能还空着 5 个单位。队列已空，新到的任务也可能拿走这些额度，最后几方都开始解码。若改成醒来再争抢，能够用锁保住上限，却又可能丢掉 C 原先的顺位。先记账再通知把容量与排队承诺放在同一次状态变更中。 [队首记账、出队和通知的顺序](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L133-L159)

## 放弃等待也会推动队列

改动时序。A、B 仍在运行，C 的等待期限先到，D 仍愿意等。此时谁释放了内存？如果没有任务完成，D 又是怎么开始的？

![图二。A 持有 3、B 持有 1，空闲 1。C 超时后从队首移除，已占额度仍为 4。D 成为队首，随即取得原本空着的 1 个单位。C 返回超时错误，D 成功获准。箭头表示教学时序。](assets/figures/go-weighted-cancel.svg)

C 退出时还在队列里，从未占用额度。取消路径在锁内移除 C，并因它原来是队首且存在空闲而重新扫描。D 于是取得已经空着的那 1 个单位。A 和 B 一点都不用提前结束。如果 C 超时与归还恰好交错，检查结果可能相反。C 的 `ready` 已关闭，说明队列扫描已经替它记了 4 个单位。若等待中的 C 此时观察到取消并返回错误，库会把这 4 个单位退回并重查队列。错误返回的调用方手里没有额度，只有成功返回才应归还。若任务已获准，后续取消如何让解码结束，则由业务代码负责，不能仅凭超时信号提前释放仍在使用的额度。 [排队取消和已授予额度的退回](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L69-L106)

让 D 先跑确实能用上眼前的空位。问题出现在持续有小任务到达时。假如 1 个单位一有空就能被后来者拿走，预算可能始终只在 0 到 1 个空位间波动，等了很久的 C 仍攒不到 4 个。让空位先为队首积攒，消除了这类插队造成的饥饿，条件是持有者会释放、队首请求本身放得进预算。代码对超过总预算的申请甚至不入队，而是等它自己的上下文结束。代价也在图一里，B 释放之后那 2 个单位闲着，D 的等待时间被更重的 C 拉长。小图响应时间更重要、任务类别又容易区分时，拆出独立预算可以隔离这段等待，同时也会减少两类任务之间可借用的空间。应用还得估准每个任务的权重，信号量约束的是账上的总重量，真实内存能否守住上限取决于估算以及解码之外的开销。 [超过总预算的处理](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L62-L67) · [队首策略的源码说明](https://github.com/golang/sync/blob/v0.16.0/semaphore/semaphore.go#L135-L153)

还有一个成本落在等待侧。入队时会为每个等待者保存队列节点和通道，队列长度独立于 5 个单位的预算。突发流量下，持有额度的解码工作受控，等候解码的请求却仍可能积压。请求期限能让超时者离队，至于入口能同时容纳多少等待者，服务还需要自己决定。

Rust 的 Tokio 也允许一个异步任务申请多个许可，并采用同样的队首策略，后面的单许可请求会为队首的大申请等候。两边都要约束发放，也都要处理归还，但接口分工不同。Go 由调用者记住重量并显式归还，Tokio 的普通用法把许可封装进返回对象，许可对象被丢弃时归还。若把许可绑定到比解码更短的作用域，记账仍然可能早于工作结束。准入机制负责排序，持有范围仍需要与真实资源的生命周期相符。 [Tokio Semaphore 的公平性和许可生命周期](https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html)

试着交换 C 和 D 的入队顺序，再假设 D 在 A 完成前一直占用那 1 个单位。按 B、A 的归还顺序推演，C 最早在哪一步可以获得 4 个单位？如果你要让小图的响应时间更稳定，会愿意为它单独留多少预算？
