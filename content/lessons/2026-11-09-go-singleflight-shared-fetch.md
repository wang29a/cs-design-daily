# Go 的 singleflight 怎样让三个请求共用一次回源

商品 SKU42 的价格刚从缓存中过期，R1、R2、R3 三个页面请求都来查它。假设三个请求查的是同一币种、同一套定价规则下的公开价格，后端本次会返回 69 元。最直接的写法是缓存没命中就去后端查，查到再填回缓存。这在请求零散时足够简单。但如果三个请求都在第一次回填之前读了缓存，后端就会收到三次内容相同的查询。缓存挡住了已经有结果的查询，却挡不住这段尚无结果的窗口。

给缓存加一把大锁，持锁查后端，也能堵住这个窗口。代价是 SKU42 的慢查询会拦住其他商品的缓存缺口。换成每个键一把锁，再让拿到锁的请求复查缓存，可以解决成功回填时的重复查询。不过如果后端返回错误，缓存仍为空，三个人可能接力查三次。此时可以再设计一份可共享的完成记录，让排队者一起看到这次失败。Go 的 `golang.org/x/sync/singleflight` 就把这个记录放在缓存与回源函数之间，由使用方决定什么工作可以合并。下面依据 v0.16.0 的源码推演普通返回路径，三个请求及 69 元都是教学输入。 [Group 与调用记录源码](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L55-L89)

## 给尚未完成的查询一个可加入的身份

服务在这个进程内共用一个 Group，把本例的查询键记为 K，即 SKU42 的公开人民币价格。R1 缓存未命中后调用 `DoChan(K, fn)`。Group 为 R1 准备一个容量为 1 的结果通道 ch1，然后在组锁保护下检查映射。K 没有条目，它就创建调用记录 C，把 C 登记为 K 的当前调用，记下 ch1，释放组锁，再启动一个 goroutine 执行 R1 提供的 fn。fn 去价格后端查询，并在成功时负责回填缓存。组锁保护的是谁在查、谁在等。实际查后端时，别的键也能进入登记流程。 [DoChan 的查找、登记和启动顺序](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L117-L141)

假设 R2 和 R3 都在 C 完成前进入 `DoChan`，它们会在持锁查表时遇到什么？看图里三个通道分别属于谁，又是谁在执行查询。

![图一。R1 的 DoChan 在表中登记 K → C。R2 和 R3 查到同一个 C，各自添加结果通道 ch2 和 ch3。C 执行 R1 提供的 fn，向后端发出一次查询。深色箭头表示登记关系，绿色箭头表示查询方向。](assets/figures/go-singleflight-register.svg)

R2 和 R3 各自拿到 ch2 和 ch3，C 的重复加入计数增加两次，它们提供的函数在这一轮都无需执行。后来者也无需持锁等查询结束。这里需要守住的不变量是，在同一个 Group 内且没有主动 Forget 的情况下，对某个键检查并登记当前调用必须是一个持锁动作。假如 R1 和 R2 先各自查表，看到空后解锁，然后才分别创建并安装记录，即使两个写表动作各有锁，也已经有两个调用决定要执行。合并成功依赖的是检查与登记之间没有这条缝。 [重复加入与首个调用的分支](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L121-L138)

## 一个请求可以离开，共享查询还有自己的寿命

沿用前两讲的取消例子，假设 R2 的页面请求先到期限。它用 `select` 同时等 ch2 和自己的 `ctx.Done()`，这一次走取消分支，返回给自己的调用方。Group 仍保留 ch2，R1 和 R3 还在等 C。相较于 `DoChan`，同步接口 `Do` 的重复请求会在调用记录的 WaitGroup 上等待，接口本身没有单独传入等待上下文的位置。 [Do 与 DoChan 源码](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L86-L141)

如果 R2 已经离开，C 完成时向 ch2 送结果会不会卡住其他人？图二从三人已经登记开始，留意每个通道的容量，以及 R2 取消发生的位置。

![图二。三个请求加入 C 后，R2 的请求上下文先取消并结束等待。C 继续查询，回填 69 元后完成。它从表中撤下 K → C，向 ch1、ch2、ch3 各投递一个结果。ch2 无接收者时由它的一格缓冲接住结果。箭头表示教学时序。](assets/figures/go-singleflight-delivery.svg)

当查询得到 69 元，fn 先回填缓存再返回。C 保存返回值与错误，在收尾时持组锁唤醒同步等待者，并在表里仍是自己时删除 K 的映射。普通返回路径向每个已登记的结果通道各发送一次。即使 R2 已不再接收，空的单格 ch2 也能接住这次发送，所以 C 不必等 R2 回来。发送结束后释放组锁。R1 和 R3 可以各自从通道取到 69 元。若 fn 返回错误，留在这一轮的请求也共用这次错误。返回的结果通道按接口约定保持打开，接收方应等待一份结果或自己的取消。 [调用收尾和结果发送](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L150-L180) · [结果通道契约](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L117-L122)

这与上一讲的 errgroup 有一个实际的归属差异。errgroup 中的子任务共同服务一个父请求，这里 C 服务多个请求。若 fn 直接捕获 R1 的请求上下文，R1 先离开时，遵守该上下文的后端查询可能随之结束，R3 也会拿到这次失败。对仍值得完成的公共查询，可以让服务为 C 管理自己的截止时间，每个请求分别决定等多久。这也把开销留给了服务。所有请求都离开时，库仍会保留本轮登记并让 fn 执行到返回。若业务希望最后一个等待者离开就取消，还需要额外记录等待者的加入和退出，并协调晚到的加入。 [DoChan 的加入与独立执行边界](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L121-L141)

## 键和完成点决定可以合并多少工作

C 完成后，Group 撤掉的条目是一次在途调用的身份。69 元能留多久由缓存决定。改动一下到达顺序。假设 R3 在外层看到缓存未命中，却等到 C 撤掉以后才进入 Group，它会建立下一次调用。让 fn 取得执行资格后先复查缓存，就可以发现已经填好的 69 元，避免这次查后端。选择 K 也在选择共享边界。若两个用户按不同权限或规则看到不同价格，键里必须包含这些区分维度，否则后加入的人会收到先加入者那一次查询的结果。共享返回值若含有可变对象，接收方还要约定只读或独立复制。 [调用的建立、删除与结果共享](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L121-L180)

热点键的回源数降了，代价是这批请求共享 C 的延迟和故障，通道列表和完成发送也随加入人数增长。主动 `Forget(K)` 可以让后来者开始新调用，同时旧调用仍可能运行。假设旧 C 被忘掉后 R3 建了 C2，C 先完成时若无条件删除 K，下一人就会看不到仍在执行的 C2，又启动一次回源。源码用 `g.m[key] == c` 检查身份才删除。这个检查保护组表，若新旧两个函数都会回填缓存，缓存更新仍需自己的版本规则来防止旧结果覆盖新结果。 [按调用身份删除](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L156-L161) · [Forget](https://github.com/golang/sync/blob/v0.16.0/singleflight/singleflight.go#L207-L214)

Nginx 的 `proxy_cache_lock` 也把同一个缓存键的填充集中到少数请求，让其他请求等缓存出现或锁释放。它的等待目标是缓存项，超过 `proxy_cache_lock_timeout` 的请求可以自行回源，其响应不入缓存。这里的 Group 让等待者直接收取本轮计算的值和错误，作用域是应用共用的这一个 Group。两者都把缺口期间的工作单独表示，但一个由代理缓存控制何时绕过等待，一个把共享查询和调用者的等待策略留给业务代码。 [Nginx 缓存锁与超时文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_lock)
