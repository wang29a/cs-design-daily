# Kafka 为什么让一笔未结束的事务挡住后面的消息

订单 42 的付款流水已经写进 Kafka，相关副本也追上了。生产者还要把通知任务写进同一笔事务，决定两条记录一起成立还是一起作废。与此同时，另一个生产者写下了一条普通审计心跳。心跳与付款无关，也已经复制完成，消费者却仍然读不到它。今天要解释的是，这种等待为什么会发生，以及 Kafka 为何让一条日志保留两种不同的读取边界。

昨天的幂等设计解决了同一批次重试会不会再次追加。它不能单独表达“两条不同记录必须属于同一个结果”。最自然的办法是客户端逐条发送，收到成功后继续下一条；但第一条成功、第二条失败时，读者可能已经依据半份结果执行了后续操作。Kafka 的事务生产者允许把多次写入归入同一笔事务，随后提交或中止。要让读取遵守这个决定，消费者也必须选择 `isolation.level=read_committed`。 [事务读取接口的约定](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/consumer/KafkaConsumer.java#L405-L424)

另一个自然方案是把所有记录留在生产者内存，等整笔准备好再发。小批次一次提交给合适的存储接口时，这很直接；但 Kafka 的事务可以跨多个批次和分区，网络发送与副本复制无法成为一次物理动作。它选择允许数据先陆续进入日志，把事务结果另行确定，再约束哪些记录能够交给应用。这样分开了写入进展与业务可见性，也引出了今天的等待成本。

本文核对 Kafka Java 客户端与 broker 4.1.0。例子只观察一个分区 P0，事务生产者已完成初始化并开始事务 T，消费者从 offset 100 顺序读取，使用 `read_committed`，关闭自动提交。每批一条记录，没有清理、截断、换 leader 或其他事务；所有数字与交错都是教学设定，没有运行集群。付款流水和通知任务只是两条 Kafka 记录，本文没有把真实扣款或短信发送放进 Kafka 事务。

P0 原有 0 至 99。T 先写付款流水到 100，普通生产者 U 插入心跳到 101，T 再写通知任务到 102。我们依次等三次追加达到复制确认条件，确保得到这个布局，但 T 尚未提交或中止。日志末尾是 103，高水位 HW 也为 103，意味着小于 103 的记录已经跨过复制提交边界。T 的两次发送收到追加确认，不等于整笔事务已经提交。

如果直接把 HW 以下的所有记录都交出去，消费者会看到 100、101、102。万一 T 随后中止，已经交付的付款流水和通知任务无法从应用记忆中收回。Kafka 默认的 `read_uncommitted` 模式允许读到这类事务记录，适合不依赖事务过滤的读取需求；需要排除中止结果的业务必须显式选择另一种模式。两种模式都不把复制完成自动变成外部业务完成。 [读取模式与默认值](https://kafka.apache.org/41/configuration/consumer-configs/#isolation.level)

关键洞察是，在复制前沿之内再确定一个“结果已经稳定”的前沿。Kafka 称它为 Last Stable Offset，简称 LSO。这里严格按 4.1.0 实现把 LSO 当作不包含自身的上界：`offset < LSO` 才进入稳定读取范围。它不是“最后一条可以读的记录编号”。若第一个尚不稳定的事务记录在 100，那么边界就是 100，可以越过的最后一个位置是 99。 [源码对边界及计算方式的定义](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L669-L684)

看图一。100 和 102 属于 T，101 属于 U。HW 已经到 103，为什么绿色的普通心跳仍留在读取范围之外？

![图一。教学布局，向下箭头表示 offset 增大。P0 的 100 为事务 T 的付款流水，101 为普通生产者 U 的心跳，102 为 T 的通知任务。三条均已复制，HW 为 103；T 未结束，首个不稳定位置和 LSO 均为 100。从 100 开始的 read_committed 消费者暂时不能交付这三条，包含无关的心跳。](assets/figures/kafka-lso-frontier.svg)

一种看似更积极的方案是先跳过 100，把 101 交给应用。可若 T 随后提交，再回头交付 100 就打乱了分区内的 offset 顺序；若读取进度已经前进并把 100 永久略过，又漏掉了一条应交付的已提交记录。也可以增加客户端缓存、保留缺口和补交规则，但要继续保持日志顺序，101 的最终交付仍需等待这个缺口得到解释。Kafka 的读取契约使用稳定前缀，把这一等待直接表达在分区边界上。

因此，本例的 LSO 为 `min(HW, 第一个不稳定位置)=min(103,100)=100`。broker 的 `TXN_COMMITTED` 读取路径选择稳定边界作为上限；普通模式则选 HW。客户端不必把这个边界之后的未决事务数据全部拉回来，缓存到结果确定为止。一个整数压缩了“前面的事务结果已可解释”的共同条件，但代价是后面的无关记录也一起等待。 [broker 为读取模式选择上界](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L1596-L1605)

边界怎样前进？生产者请求提交或中止后，事务协调器推动决定，相关分区会追加 COMMIT 或 ABORT 控制标记。本例把标记放在 103。仅仅追加到 leader，日志末尾变为 104，还不足以放行：假如标记尚未跨过 HW，换副本后就可能无法承接这份结果。4.1.0 的生产者状态管理同时追踪未决定事务和结束标记尚未复制完成的事务，用两者最早的起点限制稳定边界。 [不稳定事务与标记复制的条件](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/ProducerStateManager.java#L241-L265)

图二给出互斥的两种结局。两支都等位置 103 的结束标记进入复制共同前缀，HW 到 104，且没有其他未稳定事务，此时 LSO 才能到 104。越过同样的边界，会交付同样的记录吗？

![图二。两条互斥的教学分支，均从图一出发。在 103 追加 COMMIT 并复制完成后，HW 与 LSO 为 104，顺序交付 100、101、102，隐藏控制标记。若 103 是已复制的 ABORT，边界同样为 104，但过滤 T 的 100、102，仅交付 U 的 101，也隐藏标记。完整扫描至末尾后下一读取位置均可到 104，这不代表消费组已提交 104。箭头表示选择结局。](assets/figures/kafka-lso-outcome.svg)

提交分支中，读取可以依次交付付款流水 100、心跳 101、通知任务 102。中止分支中，100 和 102 在当前日志里仍占位置，但不应作为业务记录交付。broker 随读取结果提供相关中止事务的信息，Java 客户端依据生产者身份和事务批次属性过滤这些记录。心跳来自 U，不属于 T，即使夹在两条中止记录之间，也会正常交付。过滤对象不能简单写成“把 100 至 102 整段丢掉”。 [客户端识别并跳过中止批次](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/consumer/internals/CompletedFetch.java#L203-L220) · [中止集合与事务批次属性的匹配](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/consumer/internals/CompletedFetch.java#L351-L363)

这说明 LSO 以下的含义是“结果已稳定，可以正确筛选”，并非“每条都是已提交的业务数据”。控制标记有自己的 offset，客户端在两种读取模式下都将它隐藏；中止的数据则只在 `read_committed` 下被过滤。完整扫描完本例的数据和标记后，下一读取位置可以到 104，应用却可能只拿到一条 offset 为 101 的心跳。这些空洞不表示日志传输丢失，读取位置推进也不表示业务已经完成，更不表示组的恢复位置已经提交。 [控制记录的跳过与位置推进](https://github.com/apache/kafka/blob/4.1.0/clients/src/main/java/org/apache/kafka/clients/consumer/internals/CompletedFetch.java#L224-L236)

真正必须维护的不变量有两部分：稳定边界不能越过结果尚不可靠的事务；越过后，过滤还必须保留不属于中止事务的记录。若把 HW=103 直接当成稳定边界，T 中止前可能泄露半成品；若一见 ABORT 就删除整个数值区间，U 的心跳又会被错误吞掉。前沿负责限制可以判断到哪里，事务身份负责判断这个范围内该保留谁，两者缺一不可。

代价也由这两层承担。broker 维护事务状态、索引和额外标记，协调器负责推进决定，读取客户端承担过滤。更直接的代价是，一个长事务把 LSO 留在 100，即使后面的心跳不断追加并复制，这个分区的稳定读取仍会落后。另一个分区有自己的边界，并不因此自动一起停住。普通事务可以由 `transaction.timeout.ms` 约束保持开放的时间，但超时处理和标记复制仍需系统推进，不是墙上时间一到，读者就能瞬间跨过缺口。 [普通事务超时的配置契约](https://kafka.apache.org/41/configuration/producer-configs/#transaction.timeout.ms)

如果独立心跳必须低延迟交付，值得重新审视它为何与长事务共用分区，或者缩小事务范围与持续时间。换分区又会改变共同排序范围，不能只看到等待消失。需要事务结果过滤时，改用 `read_uncommitted` 也改变了语义。事务记录可以分多次 `poll` 返回，应用不能把一次 `poll` 当成完整事务；本文更没有推出跨分区读取拥有数据库式的共同快照。

这个结构与先前 RocksDB 的批次发布可以相互照亮。普通有序写入允许内部逐步安装两次修改，但可见序号要等完整安装后才公布。Kafka 也把“数据已经存在”与“允许读者解释它”分开，不过日志可以继续接收后来者，稳定读取还需等待分布式事务的结果及复制证据。前者主要等待安装，后者可能连带阻塞已经写好的无关消息。相同的边界思想，在不同约束下把等待成本交给了不同部件。 [RocksDB 普通有序写入的发布条件与等待成本](https://github.com/facebook/rocksdb/wiki/unordered_write#background)
