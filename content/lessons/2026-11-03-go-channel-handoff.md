# Go：channel 怎样把值的交付与任务唤醒接在一起

前几篇我们已经看到，Go 调度器能把可运行任务交给不同执行者，也能暂停长计算。但程序经常不是缺执行机会，而是缺别人算出来的一个值：接收者应该等在哪里？发送者怎样找到它？如果发送恰好撞上接收者准备睡下，会不会两边都等下去？今天从一次无缓冲 channel 交接，理解通信怎样接入调度、栈管理与内存可见性。

先明确系统位置。goroutine 是 Go 运行时管理的任务 G，系统线程 M 执行任务；channel 不负责替操作系统调度线程，而是保存通信状态，必要时让 G 等待，并在条件满足后把它重新交给调度器。本文固定 Go 1.25.0 官方提交 `6e676ab2`，只分析普通发送与接收，不涉及关闭、nil channel 或 select。下面的状态和时序是依据源码建立的教学模型，没有运行程序、采集 trace 或测量性能。

## 值到了，接收者却不必已经继续执行

设共享变量 `meta` 初始为 0，`c := make(chan int)`，容量为零。任务 GS 先写 `meta = 7`，再执行 `c <- 42`；任务 GR 执行 `v := <-c`，随后读取 `meta`，计算 `result := v + meta`。没有其他任务读写这些变量，GS 写入 7 后不再修改 meta。我们选定 GR 先到达接收操作，最终结果应为 49。

最自然的通信方案，是安排一个共享槽位，接收者不停检查“值来了没有”。在等待极短、资源专用时，轮询可以成立；若等待时间未知，大量 G 都这样做，就会把执行机会耗在尚不能推进的任务上。让每个等待者占着一条阻塞的系统线程，也没有充分利用 Go 能在同一执行者上切换任务的能力。真正需要保留的是“谁在等什么，以及满足后从哪里继续”，不必为此一直保留正在执行它的线程。

Go 的 channel 内部因此既有等待发送者、接收者的队列，也有保护状态的锁；有缓冲 channel 还维护数据环形缓冲区。容量为零只表示没有存放待领取元素的数据缓冲区，不表示 channel 没有状态。语言规范规定，无缓冲发送要等到接收者准备好才能推进；下面的队列与直接交付则是固定版本实现这些语义的方式。[发送语义](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/doc/go_spec.html#L6059)，[channel 内部状态](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L33)

GR 先持有 channel 的锁，检查后发现没有发送者。它建立一条等待记录，源码称为 `sudog`，把 GR 和接收目标地址联系起来，再挂到接收队列。为了画清引用关系，本文假定目标 v 位于 GR 的栈上；具体编译结果可能改变存储位置，这不是语言保证。随后运行时让 GR 进入 Waiting，释放 channel 的锁，让执行者可以去运行其他 G。[接收者登记与等待](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L632)

这时 GS 写好 meta，带着 42 进入发送路径。持锁发现接收队列里的 GR 后，GS 不必先把 42 放进一个公共邮箱，再等 GR 来取：它可以直接把值复制到等待记录指向的接收目标，清除这次交接的目标引用，然后释放锁、标记交接成功，并通过 `goready` 让 GR 变为 Runnable，也就是有资格再次运行。[寻找接收者](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L229)，[直接交付与唤醒](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L318)

观察下面三个时刻：42 已经写到哪里？哪一步仍没有承诺 GR 的业务完成？

图中第二阶段最容易被误读。GR 已可运行，不等于它已经拿到执行机会。GS 可以先从发送语句返回，GR 随后才恢复接收路径、读出 meta 并算得 49；另一次执行也可能让 GR 更早继续。无缓冲交接要求双方配对，不要求发送者等待接收者跑完后面的代码。如果 GS 必须确认 49 已经算好，需要另一个结果或确认操作，不能把发送返回当成业务完成。

这里还隐含另一个问题：meta 并没有放进 channel，GR 凭什么应当读到 7？Go 内存模型规定，一次发送与对应接收的完成之间存在同步顺序。把本例的先后接起来，就是“写 meta=7 → 发送 → 对应接收完成 → 读取 meta”。在没有后续并发改写的假设下，这保证 GR 读到 7，而不是让读者凭 CPU 缓存直觉猜测。无缓冲 channel 还提供接收到对应发送完成的反向同步关系，但它同样不包含 GR 接收之后的业务计算。[Go 内存模型的 channel 同步规则](https://go.dev/ref/mem#chan)

## 找不到对方与登记等待，必须是一个受保护的决定

只知道“有等待队列，之后唤醒”还不够。假想一个错误实现：GR 检查没有发送者，先解锁，打算稍后登记自己。间隙中 GS 到达，看不到接收者，于是登记发送等待并睡下。GR 随后依据刚才的检查结果登记接收等待，也睡下。42 和接收者都在，却没有任何正在执行的一方再去配对。

这个反事实指出真正的不变量：在本文排除 select 的范围里，同一个 channel 的发送、接收等待队列不能同时有等待者；发现可配对对象就应当完成交接，不能让双方各自排队。源码开头明确写出了这个约束，也注明 select 的例外。因此“检查没有对方”和“把自己登记成等待者”必须受同一把锁保护，不能把过时判断带到锁外。[队列不变量及其边界](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L9)

但即便登记在锁内，如果先解锁、再把自己设成等待，发送者仍可能过早尝试唤醒一个尚未进入等待状态的 G。Go 把停下任务和释放锁接在一起：`gopark` 转入调度器的 `park_m`，先将 GR 从 Running 改成 Waiting，再调用 channel 的提交回调 `chanparkcommit`；回调完成相关栈状态设置，最后释放 channel 锁。GS 只有此后才能取得锁、处理等待记录。[停车的状态转换](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L4215)，[提交等待并解锁](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L748)

看图时找出那个受保护的边界：GS 最早什么时候能进入 channel，为什么那时 GR 已经可以被可靠唤醒？

![图二：上半部是故意拆开检查与登记的错误教学实现，导致 GS、GR 都等待；下半部展示真实路径先持锁检查登记，再提交 Waiting 并解锁，最后由 GS 交付和唤醒。箭头只表示动作先后，不表示计时。](assets/figures/go-channel-wait-race.svg)

可靠性不是来自“发送者碰巧晚一点”，而是发送者无法穿过那把锁提前观察半完成的等待状态。反过来，GS 复制完成后也不应持着 channel 锁调用 `goready`：源码明确要求先解锁，以免与栈收缩路径的锁依赖形成死锁。等待、交付、恢复各有交接点，顺序本身就是正确性的一部分。

## 少一次中转，运行时就要承担更多配合

直接写入另一个暂停 G 的接收目标，把 channel 接回了前面讲过的栈搬迁。若 v 在 GR 栈上，等待记录持有的地址就不能在搬栈后失效。该版本搬栈路径会锁住相关 channel，调整等待记录并复制相应栈区域；直接交付路径则在取得目标地址到使用它之间避免抢占点。对于含指针的元素，复制还要与 GC 的写屏障配合，不能当作任意裸内存搬运。本例传 int 不涉及堆指针，但通用 channel 实现不能只为 int 正确。[搬栈与等待记录同步](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/stack.go#L845)，[跨栈复制与屏障](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L382)

因此它也不是“零复制”：42 仍被复制，只是省掉了数据缓冲区的中转。收益是业务不必分别维护值、等待队列、调度恢复与发布可见性的协议；成本由运行时承担，包括锁、等待记录、复制及必要的调度和 GC 配合。无缓冲还把生产者与消费者进度绑得很紧：对方不到，自己就不能越过这次通信。这可以形成背压，也可能形成永远等不到的依赖，channel 不会自动证明业务一定有进展。

若把容量改成 1，GS 在缓冲区有空位时可以先放入 42，没有 GR 到场也能返回。改变的是发送完成需要满足的条件，并不取消发送到对应接收完成的正向同步保证：GR 取到这次的 42 后仍应读到 meta=7。可以先独立推演一个问题：容量为 1 时，看到 GS 的发送已经返回，是否足以断定 GR 曾执行过接收？再用“空位是否已经足够让发送推进”检查自己的答案。

这也能与 Unix 管道形成具体比较。两者都把生产者与消费者连起来，并在不能推进时等待；但普通管道是有界字节流，没有内建消息边界，写入可以在数据进入内核缓冲区后返回，不能据此认定读取方已经处理完。Go 的无缓冲 channel 则把一次类型化值的配对交接直接接到 G 的等待与恢复。共同的漂亮结构是把“暂时不能做事”变成受管理的等待；不同的缓冲条件、交付单位和同步契约，决定了返回究竟承诺到哪一步，不能仅凭“都会阻塞”把保证互相套用。[Linux 管道的字节流与阻塞语义](https://man7.org/linux/man-pages/man7/pipe.7.html)
