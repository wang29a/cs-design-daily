# TCP 滑动窗口：怎样把等待变成可控的并行

这篇补上 2026 年 10 月 5 日的内容。知识库需要把一批笔记传到另一台机器。网络有传播延迟，还可能丢包、重复或乱序。我们需要一个既能可靠传输，又不会让发送方在每次网络往返里都闲等的设计。

最直观的可靠办法是停等：发送一段，等收到确认，再发送下一段。假设每段有效数据为 1000 字节，往返时间为 0.1 秒，忽略序列化时间、处理开销和丢包，那么每秒只能完成大约 10 次等待，吞吐约为 10000 字节每秒。即使链路很快，这套发送规则也可能让链路大量时间空闲。

能不能一次把全部笔记发出去？这又需要承担无限数量的未确认数据，接收端缓冲区可能被塞满，网络也可能被过量流量压垮。矛盾因此变得清楚：等待过于保守，完全不等待又缺少资源约束。

滑动窗口在两者之间建立了一个有界的未完成范围。发送方允许多个字节区间同时等待确认，收到反馈以后回收已完成区间，释放新的发送额度。TCP 的序号针对字节，累计确认表示下一个期望收到的序号。下面忽略序号回绕、连接建立和关闭时的序号消耗，只讨论已建立连接的数据传输。[TCP 标准 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)

先用一个没有丢包的例子。最早未确认字节是 1000，接下来待发送字节也是 1000，可用窗口为 4000 字节。发送方可以发送序号从 1000 到 4999 的数据，而不必每发一段就等一次。假设它先发出三段：1000—1999、2000—2999、3000—3999。

此时最早未确认位置仍是 1000，下一个待发送位置已是 4000，尚未确认的数据量为 3000 字节。窗口里还剩 1000 字节额度。如果接收端确认到 2000，意味着此前连续的数据已被接收；最早未确认位置移动到 2000。发送方就能回收那一千字节的等待状态，让新的数据进入允许发送的范围。这就是窗口“滑动”的实际含义。

为了看清为什么不能只用一个“发了多少包”的计数器，我们给中间一段制造丢失。第一段到达，第二段丢失，第三段到达。接收端已经拥有 1000—1999 和 3000—3999，但连续前缀只到 1999，累计确认仍然指向 2000。它不能确认到 4000，否则发送方可能误以为缺失的那段也已经安全收到。

这个状态说明可靠性依赖一个不变量：累计确认的前沿只能跨过已经连续收到的字节。后面收到的内容可以先缓存，但前面缺失的数据仍然需要补齐。第二段重传到达后，缺口消失，连续前缀才能推进到 3999，确认随之到 4000。

如果确认本身丢失，发送方可能再次发送已经到达的字节。序号让接收端能够识别这些字节对应同一个区间，而不是把重复传输误当成新的数据。序号与确认共同把“发送方是否知道完成”和“接收方实际收到什么”这两种状态连接起来，但它们不可能在每个时刻都完全同步。

超时又是另一个设计问题。假如发送方固定等待很短的时间，正常网络延迟也可能被误判成丢包，造成大量无谓重传；固定得很长，真正丢包时又会恢复缓慢。TCP 的重传超时计算会利用往返时间估计与变化，并在连续超时时退避。这不是本篇要展开的完整算法，但它说明反馈本身也需要面对不确定性。[重传计时器 RFC 6298](https://www.rfc-editor.org/rfc/rfc6298.html)

接下来问最关键的资源问题：这个窗口应该由谁决定？接收窗口反映接收端能够接纳的范围；拥塞窗口反映发送方依据网络反馈所允许的在途数据量。经典 TCP 的发送受两者共同约束。接收端有空闲内存，不代表网络还有空闲承载能力；网络畅通，也不代表接收端应用正在及时消费。[TCP 拥塞控制 RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html)

在一个稳定、持续发送、无丢包的简化模型里，可把窗口约束下的吞吐近似写成：

```text
吞吐 ≤ 有效窗口 / RTT
```

如果 RTT 为 0.1 秒，有效窗口为 100000 字节，得到的窗口约束是约每秒 1000000 字节。它是一个上限条件，真实吞吐还可能被链路带宽、丢包、协议开销、发送节奏、CPU 与应用限制。这个公式不能替代实际测量。

反过来看，假设链路目标吞吐为每秒 25000000 字节，RTT 仍为 0.1 秒，为了持续填充这条链路，需要容纳的在途数据量约为 2500000 字节。这就是带宽与往返时间相乘得到的尺度。链路越快、往返越久，就越需要足够多的工作同时在途，才能覆盖等待时间。

代价由此直接出现。发送方保存未确认数据以便重传，接收方可能缓存乱序数据，双方维护窗口、序号和计时器。窗口太小浪费可用带宽，窗口过大也可能增加排队与内存压力。并且 TCP 提供有序字节流，某个前部缺口可能延迟后部已经到达的数据向应用交付；可靠顺序本身带来等待关系。

这里还要区分三层完成。send 返回成功通常说明数据已被本机发送路径接受，并不证明远端收到。TCP 确认说明相应字节到达了远端 TCP 层，也不证明远端应用已经把笔记可靠保存。要表达“笔记已保存”，仍需应用协议里的确认，以及相应的持久化语义。把传输确认当成业务完成，会把错误的承诺交给用户。

这一讲和管道的联系，现在可以精确说出来：两者都使用有限容量协调生产与消费，但 TCP 的反馈需要跨网络传播，因此在反馈到来之前必须允许一批工作继续进行。它把一个漫长的等待周期，转换成有界的在途状态。

在异步任务系统里，也可以借用这种结构：允许最多一批任务尚未完成，完成一个就回收一个名额。迁移时仍须重新定义“完成”——拿到任务、完成计算、保存结果、向用户交付，各自不是同一个边界。窗口控制资源，完成协议定义语义，两者都需要。

最后检验一个反事实。收到第三段时，假如接收端直接确认到 4000，后来第二段一直没有补到，会发生什么？发送方可能不再保留或重传第二段，而应用又缺少该区间的数据。累计确认不能跳过缺口，并非保守偏好，而是它所表达的承诺必须成立。

本篇核对了停等吞吐、窗口约束与在途数据量的算术结果，只推演序号、累计确认与窗口约束，没有进行抓包或网络吞吐测试。真实 TCP 还包含选择性确认、不同拥塞算法、发送节奏与更多边界处理；这里的数值是教学假设，不是设备基准结果。
