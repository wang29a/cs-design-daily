# Go：程序还在改引用，垃圾回收怎样避免删掉活对象

昨天我们看到，Go 能搬迁 goroutine 的栈，因为编译器与运行时掌握了哪些位置保存引用。今天把目光移向堆：请求创建了一批节点，有些仍在使用，有些已经没人能找到。运行时要回收后者，可请求还在把节点从链表取出来、放进局部变量，又交给共享容器。回收器沿引用寻找对象时，引用关系一直在变，怎样避免把“还没看见”误判成“已经没用”？

最自然的办法是暂停全部业务，扫描所有根和可达对象，再回收剩下的内存。这里的根，是从程序执行状态直接取得的引用，例如栈上的活跃引用与全局引用。世界不再变化，扫描就容易推理；堆不大、停顿可接受时，这是一种清楚的方案。Go 标准运行时则让主要标记工作与业务交错推进，用额外的写入责任换取较少的整体停顿。本篇固定 Go 1.25.0 官方提交 `6e676ab2`，讨论这个实现，不把它当成语言规范要求。[固定版本的 GC 阶段说明](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mgc.go#L5)

先看一个不并发的扫描。把尚未发现的对象叫白色；发现并登记、还没检查完内部引用的叫灰色；内部引用已经检查完的叫黑色。扫描灰对象，发现它引用白对象，就把后者也登记为待扫描；本对象完成后变黑。这些颜色描述回收进度，不是业务里的颜色字段。所有根和待办都处理完，仍然白着的对象才成为本轮清扫候选。仅仅“某处队列暂时为空”远远不够。

## 一个引用转移，就能躲过两次观察

设 GA 正在处理一条链表。堆对象 H 有字段 next，指向节点 C；C 的 value=7、next=nil。GA 的局部 h 指向 H，局部 p 最初为 nil。另有节点 D，从任何根都不可达。H、C、D 都在本轮标记前已经存在。以下是教学交错，没有运行程序或采集 GC trace；排除 finalizer、弱引用、cgo 和任意 unsafe 操作，只考虑合法的普通 Go 引用与一个业务修改者。

选择这样一个时刻：GA 的栈已经扫描过，h 使 H 被发现为灰色，但 GC 还没检查 H.next，所以 C 仍为白色。GA 恢复执行，先做 `p = H.next`，再做 `H.next = nil`。业务没有弄丢节点：p 仍指向 C；但如果没有额外协议，GC 随后扫描 H，只看见 nil，先前扫描过的栈又不会自动重扫，C 就能从两个观察之间溜过去。

问题不在于引用数量突然归零，而在于引用从“还没检查的位置”搬到了“已经检查过的位置”。回收器若据此清扫 C，GA 后续读写 p 就会访问被错误回收的对象。这也说明只给对象记一个“本轮扫描过”标志，不能单独解决并发更新。

Go 的一个关键安排，是在覆盖需要屏障的指针槽之前，把槽里旧引用的目标交给标记机制。于是 `H.next = nil` 虽然写入的是空值，也不能一概省略旧值的处理：被删掉的那个引用可能正是 GC 原本会走的路。C 从白色进入待处理范围，GC 不必再次碰巧找到 p，也能继续扫描 C。这里保护的是旧引用所指向的对象，不是禁止业务删除这条链。[删除屏障与堆到栈的转移](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mbarrier.go#L24)

## 为什么新写进去的引用也要照顾

只看删除还不够。换一个独立的标记时刻：GA 的栈尚未扫描，p 指向白色 C；从已处理的全局根可以到达容器 B，B 已经扫描完、为黑色，B.next 最初为 nil。GA 执行 `B.next = p`，再令 `p = nil`。如果只记录被覆盖的旧值，第一步只遇到 nil，第二步又是当前局部变量写入；后来扫描 GA 栈看不到 C，而 B 也不会再按普通流程重扫，C 再次被隐藏。

这次需要在安装新引用时，把新目标 C 也交给标记机制。这样即使栈上的 p 随后清空，B.next 仍指向一个已被登记、将继续扫描的对象。下面不是图 1 的后续，是同一类节点在另一种起始状态下的独立推演。

图 2：已扫描的 B 和未扫描的栈构成另一种漏看窗口；同样合并指针缓冲与后续标记，不画真实线程时序。

把旧目标的删除保护与新目标的插入保护组合，才是这里的混合写屏障。源码注释给出的原理模型，是总照顾旧目标，并在当前栈尚未扫描时照顾新目标；这个固定版本的实现更保守，在需要的路径把旧、新目标都交给屏障缓冲，不逐次测试栈是否已经扫描。编译器能证明不需要处理的情况仍可省略，不能反过来说每一条赋值都执行相同工作。[两部分为何配合](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mbarrier.go#L24)，[缓冲实现对新目标的保守处理](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mwbbuf.go#L212)

这里不是要求“黑色对象永远不能指向白色对象”这么简单。混合屏障的论证允许某些暂时的黑到白关系，要求它们仍有灰色堆对象通往目标的保护路径；保护路径上的引用若要被切断，删除屏障会接住责任。待办全部消失时，就不能还留着这样未获保护的可达白对象。正文用两种转移解释责任，不把两个例子冒充完整正确性证明。[设计提案中的弱三色不变量](https://github.com/golang/proposal/blob/master/design/17503-eliminate-rescan.md#reasoning)

## 记录变化，还要证明记录已经处理完

编译器在需要的堆或全局指针写入处安排屏障；已知写入当前栈帧的普通局部槽通常省略。这样 GA 经常改动局部变量，不必每次都把它变成 GC 工作。代价是堆与栈之间的转移必须由刚才那套合作兜住，channel 等运行时特殊复制也有自己的处理，不能把“局部写可省略”推广成所有内存复制都能绕过屏障。[编译器判断与记录旧、新值的路径](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/cmd/compile/internal/ssa/writebarrier.go#L81)

实际快路径先把相关指针放进每个 P 的写屏障缓冲，缓冲刷新时才过滤 nil、找到堆对象、检查标记并产生后续扫描工作。P 是运行时调度资源，不是 goroutine 私有的一份堆。这样能摊薄处理成本，却多了一类尚未进入公开队列的待办。所谓屏障也不是业务互斥锁，更不等于一次 CPU 内存屏障；它不会让有数据竞争的容器自动安全。[缓冲与刷新职责](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mwbbuf.go#L5)

因此核心不变量可以说成：**可达对象不能在本轮被误当成垃圾；已经接下的发现与扫描责任，不能在宣布标记结束时遗漏。**`gcMarkDone` 要协调局部工作和屏障缓冲，刷新后若又出现工作就继续标记；进入停止世界的结束检查时若仍发现待办，还能恢复并发标记。它不是检查一次全局队列为空就关闭屏障。[标记结束的协调与重试](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mgc.go#L866)

回到图 1，GC 最终处理 H 和 C，C.value 仍为 7。GA 通过 p 读出 7、改为 8，交出结果 8。根、标记工作与缓冲全部处理完，D 仍未被标记，后续清扫可以收回 D 的对象空间，供分配器复用；这不等于立即把内存交还操作系统。若 GA 在 C 被标记后也清空 p，C 可能已经不可达，却仍被本轮保留，等后续周期再处理。允许暂时多留对象，换来不能错删活对象的安全边界。

## 停顿的成本，转移到了修改路径

这个设计有价值的地方，是让已扫描的栈无需因为恢复执行而在结束阶段统一重扫，把持续变化转成受追踪的增量责任。它仍需要阶段切换时的整体暂停，也要暂时停住某条 goroutine 扫描其栈；本轮标记期间的新分配按已标记对象处理，否则刚创建的活对象又会带来漏洞。它并没有让 GC 永不打断业务。[固定阶段、根扫描与新分配规则](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/mgc.go#L30)

付出的代价包括指针写入的额外工作、缓冲和扫描占用的 CPU，以及暂时保留的垃圾。分配太快时，业务 goroutine 还可能参与辅助标记；并发降低整体停顿的需要，不保证总计算量更少。本文没有测量暂停、吞吐或容量，也不把设计提案的历史实验数字当成本机结果。[Go GC 的并发成本说明](https://go.dev/doc/gc-guide#Latency)

这与此前 Linux 页缓存写回有一个具体相似点：旧一轮写回期间，应用又把 XY 改成 XZ，修改者必须重新留下脏状态，不能让旧 I/O 完成替新修改注销责任；Go 中，已扫描的栈或 B 也不能证明之后转移的 C 已处理完。共同结构是由修改路径补记后台工作尚未覆盖的变化。区别在于脏状态推动字节写回，GC 记录推动可达性扫描；前者最终还有持久化责任，后者只是内存安全的保守判定，两种标记不能互相替代。[Linux 脏状态与写回结束的不同职责](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/page-writeback.c#L2987)

最后先独立推演：图 1 删除 H.next 时，只记录新值 nil 会漏掉什么？图 2 写入 B.next 时，只记录旧值 nil 又为什么不够？若 C 后来不再可达，本轮仍保留它算不算错误？把“不能错删”和“不必立即收回每个死对象”分别想清楚，才能判断这个合作设计究竟买到了什么。
