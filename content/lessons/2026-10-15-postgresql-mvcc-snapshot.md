# PostgreSQL：快照为什么不能只记一个序号

报表正在读两份额度，甲有 100、乙有 40；另一个事务把甲的 10 转给乙，改成 90、50。报表不希望读到半份转移，也不希望读到一半突然换了年代，却又不愿为了读几分钟而阻止所有更新。前几篇 RocksDB 已经让我们熟悉了版本与读取边界。今天进入 PostgreSQL，追问一个更具体的问题：如果事务可以先取得编号、稍后才提交，快照还能仅凭一个序号决定哪些修改可见吗？

先交代系统位置。PostgreSQL 是提供 SQL 与事务的数据库服务器，客户端通过连接提交请求，服务器进程负责查询与文件访问。执行查询时，扫描或索引访问找出候选行，行版本的可见性规则再决定哪些属于本次读取；缓冲、WAL 和后台维护各有职责。今天只深入普通表行的多版本可见性，不把整套数据库压缩成一幅架构图。[PostgreSQL 的客户端与服务器分工](https://www.postgresql.org/docs/18/tutorial-arch.html)

最自然的方案，是读者把需要的行锁住，写者等它读完。更新不频繁、读取短小且访问约定清楚时，这样做可以很直接。长报表却会把稳定读取的代价转成写入等待。另一个方案是复制整份数据给报表，隔离清楚，但复制量和创建时间又随数据增长。多版本并发控制，简称 MVCC，改变的是责任分配：更新保留旧版本并生成新版本，读者按自己的视图选版本，清理者等旧版本无人需要后再回收。

固定讨论 PostgreSQL 18。以下是教学模型：只读报表使用 Repeatable Read，更新事务正常提交，只有图中这些带编号的顶层事务，省略子事务、事务自身写入、行锁型 xmax、MultiXact、冻结与编号回绕。100、101、102 是人为安排的事务编号，不是实际运行所得；它们表示编号分配顺序，不能直接当成提交顺序。我们也不把索引和页面布局画成已经观察到的物理记录。

初始事务 T100 已提交，留下甲=100、乙=40。T101 更新两行，产生甲=90、乙=50 的新行版本，同时给旧版本标记由 T101 替换。普通行版本的 `xmin` 表示创建它的事务，`xmax` 可表示使它失效的删除或替换事务；真实 xmax 还可能承担锁等其他用途，所以本例明确排除了那些分支。旧甲行的标记为 xmin=100、xmax=101，新甲行为 xmin=101、xmax=0；乙同理。xmax=0 在这里表示尚无删除或替换标记。[行版本的系统列](https://www.postgresql.org/docs/18/ddl-system-columns.html)

看看第一幅图：T101 已经写出新版本，但还没提交，为什么旧版本仍然不能消失？

![教学图：甲的旧版本 100、新版本 90，以及乙的旧版本 40、新版本 50同时存在。旧行 xmin=100、xmax=101，新行 xmin=101、xmax=0；行标记描述创建与替换事务，不等于该版本已可见。箭头表示本例更新生成新版本，省略索引、页面和备注行。](assets/figures/pg-row-versions.svg)

因为其他事务不能把 T101 的未提交结果当成正式数据，而旧读者还需要完整的 (100,40)。修改字节已经进入某处，不是允许读取的充分条件。若 T101 最后回滚，新版本仍不能成为正常可见的结果，旧版本上的替换标记也不能按有效删除处理。读取必须把版本上的事务身份、事务状态和自己的快照结合起来。

让事情再多一层：T101 迟迟没提交，后来取得编号的 T102 只把一条无关备注从“待核”改成“已核”，先提交了。报表 R 此时开始读取，应当看见已提交的备注，却继续看见旧额度。若把“编号小于 103”当成可见条件，就会错误纳入 T101。编号更小的人还没完成，编号更大的人却已完成，一个单调前沿覆盖不了这个空洞。

R 使用下面的事务形式，并在 T102 已提交、T101 未提交时执行第一次 SELECT。单独 BEGIN 不是本例快照建立时机；PostgreSQL Repeatable Read 的视图从第一条非事务控制语句开始。这里第一条就是查询。默认 Read Committed 的普通 SELECT 则每条语句取得新快照，不能把跨语句稳定性推广给所有隔离级别。[两种隔离级别的快照范围](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT name, balance FROM accounts ORDER BY name; -- 此时固定 R 的视图
-- 在别的连接提交 T101 后，再执行同样的 SELECT
COMMIT;
```

这只是接口时序说明，表名代表教学场景，并非声称已执行这段实验。R 保持只读，也没有通过函数强行申请事务编号。它取得的教学快照 S 可写成 `101:103:101`：下界 S.xmin=101，上界 S.xmax=103，进行中集合为 {101}。下界之前没有快照时仍在进行的事务；上界及以后当时尚未完成；中间的编号要检查是否在集合中。T102 不在集合，且已提交；T101 在集合。快照保存的是取快照时的事实，集合以后不会随 T101 提交而改写。行的 xmin/xmax 标记事务身份，快照的同名字段标记范围，两者不能互换。[快照组成与编号边界](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-PG-SNAPSHOT)

第二幅图要观察：同样小于上界 103，101 与 102 为什么不能得到相同结论？

![教学图：R 的快照 S.xmin=101、S.xmax=103、进行中集合={101}。100 已提交，101 取快照时未完成，102 已提交，103及以后在此次范围之外；101 后来提交也不会从 S 的集合中消失。这里只描述顶层事务的教学状态，可见行还需结合创建与失效标记判断。](assets/figures/pg-snapshot-hole.svg)

可以用少量伪代码复述“相对 S 尚未完成”的判断，而不把它误写成完整行可见性算法：

```text
unfinished_in_S(x):
    if x < S.xmin: return false
    if x >= S.xmax: return true
    return x in S.active
```

这里 x 是被检查的其他事务编号，普通数字比较只适用于本例无回绕的假设。返回 false 也不自动代表它成功提交，事务可能已经回滚。真实源码还处理子事务、恢复模式与当前事务等情况。PostgreSQL 18.0 固定提交 `3d6a828` 的 `SnapshotData` 保存边界和集合，`XidInMVCCSnapshot` 正是在范围判断后检查事务集合。[快照结构](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/include/utils/snapshot.h#L142)、[相对快照的进行中判断](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/utils/time/snapmgr.c#L1860)

把规则接回一行。R 检查旧甲：创建者 100 已提交，而且对 S 已完成；替换者 101 却在 S 的进行中集合里，因此不能把这次替换视为已经发生，旧甲仍可见。R 检查新甲：创建者就是 101，它相对 S 未完成，新版本不可见。对乙重复同样过程，选择旧乙=40。于是查询返回 (100,40)，遇到的其他物理版本不会混进结果。

随后 T101 提交。事务状态确实从进行中变成已提交，但 R 的集合仍有 101。再次检查时，新甲的创建者仍不属于 S 可见的提交，旧甲的替换仍不属于 S 已发生的事实，R 再次返回 (100,40)。新读者 N 此后取得自己的快照，不再把 101 排除，看到其创建的新行，跳过其替换的旧行，返回 (90,50)。行版本标记没有为每个读者单独重写，每个读者只是用不同的视图解释同一份记录。[创建与失效事务的可见性分支](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/heap/heapam_visibility.c#L1063)

第三幅图追踪结束条件：T101 完成以后，为什么 R 还不能换成新额度？

![教学图：T101 先更新额度但未提交，T102 后取得编号却先提交备注；R 首次 SELECT 固定 S=101:103:101，返回 100、40；T101 提交后，R 在同一只读 Repeatable Read 事务内仍返回 100、40，新快照的 N 返回 90、50。向下表示事件顺序，R 结束前不更换 S。](assets/figures/pg-snapshot-readers.svg)

不变量是：对于本例其他事务的普通表行修改，提交发生在 S 建立之后，不能改变 R 在 S 下的答案。若只记当前提交状态，R 第一次看见旧额度，T101 提交后第二次就变成新额度；若只记一个编号上界，甚至可能提前看见未提交额度。前者破坏稳定视图，后者纳入没有完成的事实。集合并非装饰信息，它补上了编号顺序与完成顺序之间的差距。

系统并没有因此免除所有同步。更新同一行的写者仍可能相互等待，显式锁和表结构操作也有各自规则；“普通读不必等这次更新完成”不能夸大成数据库从不加锁。Repeatable Read 的稳定视图也不等于所有业务约束都已获得可串行化保证，写事务还可能需要处理失败和选择合适隔离级别。今天只读模型不能直接当成并发转移业务的完整实现。

代价转移给了行版本存储、读取时的事务判断、快照维护与清理。长期持有 R，会延长旧版本仍可能有用的时期；R COMMIT 后，其他保护条件也不再需要这些旧版本，清理才有资格回收它们，而非 COMMIT 当场保证释放磁盘。普通 VACUUM 通常把空间交还给表内复用，也不等于把所有空闲字节立即归还操作系统。[旧版本为何必须等待及怎样回收](https://www.postgresql.org/docs/18/routine-vacuuming.html#VACUUM-FOR-SPACE-RECOVERY)

这与 RocksDB 的快照可以作一个具体比较。两者都把“保留旧答案”交给多版本，而不是为每个读者复制整个数据库。普通有序 RocksDB 路径把可见修改序号推进到完整安装的边界，读者按已发布前沿读取；本例 PostgreSQL 的事务编号在提交前就分配，所以旧快照还要保留范围中的未完成集合，并结合事务提交状态。共同目标是固定可见历史，差异来自编号表达什么、何时公布完成。不能把一边的序号比较移到另一边，也不能据此断言所有 MVCC 都必须使用同一种快照结构。[RocksDB 普通路径的发布边界](https://github.com/facebook/rocksdb/wiki/unordered_write#ordering-in-vanilla-rocksdb)

最后留一个独立推演：若 T101 在 R 第一次 SELECT 之前已经提交，R 该选哪两行？若 T101 改为回滚，新读者又会怎样？先分别判断创建与替换，再决定结果。这个设计值得欣赏的地方，是承认并发进程并非按编号整齐完成，用边界压缩大部分历史，再用有限的集合准确保存例外。稳定读取不再要求冻结整个系统，但必须由版本、状态和回收约束共同兑现。本文核对了 PostgreSQL 18 文档与 18.0 固定源码，没有运行数据库、导出真实行头、注入故障或测量性能；图和数字是保持关键语义的教学模型。
