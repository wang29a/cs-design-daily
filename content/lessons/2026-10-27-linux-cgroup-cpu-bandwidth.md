# Linux：容器开了多个线程，为什么仍只能用半个 CPU

昨天的 PID namespace 让一组进程拥有局部编号，却没有替它们划出独占的计算能力。假设同一台机器上运行在线服务和离线计算，离线任务突然开出很多工作线程。它们在容器里看起来属于自己的小世界，在调度器面前却仍要与在线请求争用同一批 CPU。今天的问题是：怎样限制一项服务的总消耗，又不把它永远绑在一块专属硬件上？

最自然的办法是限制线程数。只有一个线程，确实不会同时占满多个 CPU；但它仍可能持续占满一个 CPU，而且服务还可能创建子进程。另一个办法是指定允许运行的 CPU：线程亲和性决定它能去哪些逻辑 CPU，适合控制放置位置，却不能直接表达“每段时间只允许消耗半个 CPU 的运行量”。少量可信后台脚本也可以主动休眠，但每个程序都要正确配合，管理者难以统一约束。[Linux 线程亲和性的接口](https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html)

关键洞察是，把限制的对象从“某个线程”改成“某项服务的共同账户”，把限制的量从“能去哪颗 CPU”改成“可以累计执行多久”。Linux 的 cgroup 核心负责组织进程，CPU controller 把这层归属接到调度器的记账和运行资格上。容器运行时、服务管理器负责把业务放进合适的组；内核在实际执行时扣账。namespace 组织视图，cgroup 组织资源责任，两者可以配合，却没有谁自动替代谁。[cgroups 的核心与资源控制器](https://man7.org/linux/man-pages/man7/cgroups.7.html)

## 半个 CPU，先把单位说清楚

本文固定讨论 Linux 6.12、cgroup v2、普通公平调度任务，相关内核功能和 CPU controller 已启用；不推广到实时调度，也不讲特殊的 threaded 子树。普通进程组中，同一进程的线程一起归属，fork 出来的孩子继承创建时的组。因而服务多开线程或子进程，默认不会多得到一份独立额度；有权限的迁移另当别论。[cgroup v2 的进程组织](https://docs.kernel.org/6.12/admin-guide/cgroup-v2.html#organizing-processes-and-threads)

设服务所在的非根组叫 G，它的接口内容为：

```text
cpu.max        50000 100000
cpu.max.burst  0
```

这是一份配置示意，没有在本机写入这些文件。`cpu.max` 的两个数分别是额度 Q 和周期 T，单位都是微秒，所以这里 Q=50 ms、T=100 ms。一次 CPU 执行 1 ms 计为 1 CPU·ms；两个 CPU 各执行 1 ms，就消耗 2 CPU·ms。“半个 CPU”来自 Q/T=0.5，表达按周期给定的运行时间带宽，不是拿走一半物理核心，也不是保证完成一半数量的请求。CPU 频率、指令和等待行为都会影响同样运行时间能完成多少工作。[cpu.max 与时间单位](https://docs.kernel.org/6.12/admin-guide/cgroup-v2.html#cpu-interface-files)

G 中只有工作线程 A、B，各处理一项独立计算。教学假设每项恰好需要 40 CPU·ms，两颗允许使用的逻辑 CPU 都空闲，A、B 可同时运行；祖先没有更紧的限制，无 I/O、锁等待及调度开销。t=0 对齐一个新周期开始，不考虑过去遗留的 CPU 本地额度。以下是机制推演，不是本机调度轨迹或性能测量。

先看这份额度属于谁：A、B 分到不同 CPU 后，会各自得到 50 ms 吗？

## 线程越多，可能越早把预算用完

用 R 表示教学模型中本周期尚可消耗的总运行额度，包含已分到 CPU 本地但尚未使用的部分。初始 R=50 CPU·ms。A、B 同时运行，经过 25 ms 墙钟时间，每个完成 25 CPU·ms，合计消耗 50，R 降到零，各自仍欠 15 CPU·ms。此刻两个线程都有工作，却不能继续取得运行时间：G 的这轮额度已用完。

暂停的是这组任务参与公平调度的资格，不是把 CPU 关掉，也不是让程序退出。其他具备运行资格的任务仍可使用机器；即使没有其他任务，额度限制也不会自动变成一份额外许可。在本模型的 25—100 ms，A、B 等待补充。到 t=100 ms 新周期开始，额度重新可用，两者各执行剩余 15 ms，在 t=115 ms 都交出结果，随后没有任务需要继续运行。这就是本轮工作的结束条件，额度有剩余不要求程序把它用光。

观察图中的暂停区间：工作还没完成与额度暂时耗尽，是怎样同时成立的？

图 2：时间从上到下；R 是教学总余额，不等于源码中只保存未分配额度的全局字段。精确边界是简化假设，图不表示实际测量。

这里有一个反直觉之处：整个任务用掉 80 CPU·ms，却在 115 ms 内结束，80/115 大于 0.5，并没有推翻配置。额度按自己的周期补充，不是要求任意起止区间的运行量都恰好压到一半，更不是让程序始终匀速运行。若一直有这两项计算之外的新工作，理想模型每个完整周期共同消耗 50 CPU·ms；短任务的起止位置会改变观察到的比值。不能把这一教学完成时间写成真实容器的延迟保证。

## 一个共享账户，不能变成每次执行都争同一把锁

需要守住的关系是：**同一组在不同 CPU 上的执行，要归入同一份带宽约束；创建更多执行者不能凭空扩大总额度。**反事实地给 A、B 各发完整的 50，两个线程就可在同一周期消耗 100 CPU·ms，原来的“半个 CPU”已经被翻倍。以服务为单位限制资源，要求管理归属与调度记账真正接通。

但每执行一点时间就争用全局账户，也会增加多核竞争。实际实现把额度分批送到各 CPU 的组运行队列，本地执行先扣本地余额，再按需申请。固定源码中，`update_curr` 把执行增量送进 `account_cfs_rq_runtime`；`__account_cfs_rq_runtime` 扣减本地 `runtime_remaining`，不足时尝试续领。`assign_cfs_rq_runtime` 在组带宽锁保护下，从共享剩余额度转出一批。这使日常扣账留在本地，同时让额度来源仍然统一。[固定源码：执行时间记账](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/sched/fair.c#L1216)，[额度分配与本地扣减](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/sched/fair.c#L5772)

拿不到额度以后，调度路径通过 `check_cfs_rq_runtime` 与 `throttle_cfs_rq` 限制组运行队列；周期处理 `do_sched_cfs_period_timer` 补充共享额度，并向被限制的队列分配运行量、解除相应限制。因此“暂停—恢复”由内核运行资格和定时补充衔接，业务不必自己写循环计算睡眠时间。恢复资格仍不等于马上得到 CPU，其他调度竞争可能让实际推进更晚。[固定源码：限制队列](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/sched/fair.c#L6488)，[周期补充与解除限制](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/sched/fair.c#L6279)

分批分配也带来边界：CPU 本地未用尽的一小部分额度可以跨周期保留，所以真实实现不是图中那种毫秒边界上严丝合缝的总计器；配置的 burst 机制又是另一种有上限的积累能力，本例设为零。要判断实际服务，必须核对运行环境和统计，不能把“每周期50”推成所有短窗口绝不多一丝的数学保证。[带宽控制的本地额度与边界](https://docs.kernel.org/6.12/scheduler/sched-bwc.html#cfs-bandwidth-quota-caveats)

## 上限保护了谁，等待又由谁承担

G 不是整台机器。它可以位于更大的服务组下面，祖先额度耗尽时，即使 G 自己还有余额，也可能无法继续运行。子组组织业务，父组约束整体；把 G 内部重新分组，不会撤销外层责任。这也是排查“本组额度没用完却在停顿”时必须向上看的原因。[层级带宽限制](https://docs.kernel.org/6.12/scheduler/sched-bwc.html#hierarchical-considerations)

相对权重与硬额度承担不同目标。`cpu.weight` 在活跃兄弟组之间影响分配比例；竞争者不需要 CPU 时，权重并不要求本组停在固定份额。`cpu.max` 则提供带宽上限，付出的代价是可用机器时间与服务延迟之间可能留下空隙。预算也不是保底供给：没有足够 CPU 机会时，G 得不到配置的全部额度。若只想让后台利用空闲，权重可能更合适；若必须约束某项服务的消耗，单靠降低权重又不等于上限。[权重与限制的不同资源模型](https://docs.kernel.org/6.12/admin-guide/cgroup-v2.html#resource-distribution-models)

周期还决定等待怎样集中出现。保持 Q/T=0.5，把周期缩短，会同时缩小每轮可用额度，通常也缩短耗尽后等待下一轮的时间尺度，却增加补充与管理的频度，并改变突发能力。多开线程可以更快完成一小段并行计算，也可以更早触碰同一额度；延迟敏感服务因此需要把并发度与额度一起判断。`cpu.stat` 的使用量和限流统计可提供观察入口，但本文没有采样这些数据，也没有把统计存在当成一次故障已被定位。

先保留一个独立推演：只允许 A、B 在同一颗 CPU 上交替运行，仍沿用50/100的配置，两项工作能否照旧在 t=25 ms 耗尽额度？如果新请求恰在额度耗尽之后到来，多加一个线程能否让它马上计算？先沿“墙钟时间—累计执行时间—组余额”分别回答，再决定是否应增加并发。

这一设计与前面 RocksDB 的写入背压形成了具体联系。两者都让前台推进承担共同资源责任，增加线程不会自动增加背后的承载能力。区别是 RocksDB 根据待刷内存、L0 或整理积欠决定减速，恢复依赖后台消化工作；这里耗掉的是运行时间额度，恢复主要依赖周期补充，机器空闲也不自动取消限制。一个反馈实际积压，一个执行分配政策，不能因为都出现等待，就套用相同的调优办法。[RocksDB 写入停顿的触发与恢复背景](https://github.com/facebook/rocksdb/wiki/Write-Stalls)
