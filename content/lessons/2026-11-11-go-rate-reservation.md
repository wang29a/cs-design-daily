# Go 的限流器怎样为下一次发送预约额度

一个 Go 服务把通知发往下游。假设下游允许偶尔连发两条，但长期平均只能接收每秒两条。服务空闲了一阵，积压的通知突然同时到来。前两条可以立即发送，第三条和第四条都愿意等。第三条算出半秒后就有额度，如果第四条也算出半秒，它们醒来时该由谁拿走那一个新额度？

昨天讲的加权信号量可以约束同时有多少个任务占用资源。拿到许可的发送如果一毫秒就结束，许可一归还，下一次发送马上可以开始。这样能限制在途请求，却无法限制一秒内发出了多少条通知。定时每隔半秒只放一条则能控制速率，但即使上游安静了十秒，也只能按原节奏发，浪费了下游明确允许的短时突发。如果下游根本不允许连发，按固定节奏发就很合理。这里需要允许短时存量，又让连续发送的额度按时间增长。

Go 的 `golang.org/x/time/rate` 把这个决定放在应用执行外部动作之前。服务共用一个 `Limiter`，每发一条通知消耗一枚令牌。桶容量为 2，开始时满桶，补充速率固定为每秒 2 枚。发送完成不会把令牌还回来，空闲时间才会补充它。以下按 v0.12.0 源码推演，数字是教学设定，时间以秒计，假设预约按给出的顺序记账、时刻单调递增、参数在过程中保持不变。 [Limiter 的接口与构造](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L32-L66) · [初始令牌数](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L98-L106)

## 先扣账，再告诉调用者等多久

一种自然的令牌桶写法是用后台定时器持续向桶中投币。Go 的实现保存上次记账时刻和当时的余额，有操作时才根据时间差计算当前余额。若上次余额是 `x`，已经过了 `Δt` 秒，扣除本次需求前的余额就是 `min(2, x + 2 × Δt)`。因此空闲十秒也只会积到 2。实现允许小数余额，例如过了四分之一秒就补 0.5 枚，具体请求仍按整数枚申请。这里的计算只发生在需要读取或修改这份状态的时候。 [时间推进与容量封顶](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L383-L400)

在 `t = 0`，A 代表前两条通知的一次批量申请，先取走 2 枚，余额归零。接着 B 申请 1 枚。如果仅计算“再等 0.5 秒就有一枚”并让 B 去睡，C 来时还会看到同样的余额。它也会认为可以在 0.5 秒出发。即使把每次查询余额都放在锁里，两个决定也都没给未来留下痕迹。醒来再争一遍可以修正重复使用，但输的一方仍要重新计算和等待，两者在睡之前都无法确定各自什么时候能发。

Go 的预约在算出等待时间时就先扣掉请求的令牌，允许账面余额变成负数。看图一。B 和 C 在同一时刻各要一枚，为什么 C 要等整整一秒？

![图一。教学时序，总容量 2，每秒补 2 枚。t = 0 时 A 取走 2 枚立即发送，B 再扣一枚后余额为 −1，可在 0.5 秒发送，C 再扣一枚后余额为 −2，可在 1 秒发送。绿色箭头表示记账先后，右侧标明每次申请的最早发送时刻。](assets/figures/go-rate-reservation.svg)

B 扣掉一枚得到 −1，缺口除以每秒 2 枚，等待 0.5 秒。C 随后看到 −1，再扣一枚得到 −2，等待变成 1 秒。两次扣账和等待时间的计算都受同一把锁保护。到了 0.5 秒，B 可以按预约发送，无需再扣一次。此时如果有人来查账，补充了 1 枚之后的余额仍是 −1，因为 C 也已记账。到 1 秒，两枚缺口都被时间填平，C 可以发送。调用结束点是取得发送许可，通知真正发出和下游返回由调用者处理。 [reserveN 的扣账、等待计算与提交](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L335-L380)

这里需要守住的关系是，成功预约必须立即进入共享账本，且调用方必须等到约定时刻才能使用它。否则 B 和 C 都在 0.5 秒发出，连同 A 的两条，就会用掉四枚额度，而这段时间内只有初始两枚加后来补的一枚。库的三个入口复用同一笔计算。`AllowN` 把允许等待时间设为零，必须现在就能用才扣账。`ReserveN` 给出预约和等待时间，调用方负责遵守。`WaitN` 则把上下文剩余时间交给预约函数，能等才扣账，随后用计时器和取消信号决定何时返回。假如 C 的期限在 0.75 秒，它会在预约阶段失败，账面也不会被这次失败的请求扣到 −2。 [三个入口](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L108-L118) · [ReserveN 与 WaitN](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L211-L295)

## 预约撤销以后，哪些额度还能退

现在 B 和 C 都已预约，设其中一方在 0.25 秒取消，而且调用方及时处理取消。若取消 C，之后在 1 秒到来的 D 能否立即发一条？若改成取消 B，结果是否一样？

![图二。两条独立的教学分支，起点都是 B 预约 0.5 秒、C 预约 1 秒。0.25 秒取消最后一笔预约 C 时，推进余额到 −1.5 再退 1 枚，余额为 −0.5，D 在 1 秒可扣一枚。改为取消 B 时，算法算得可退 0 枚，C 保留原时刻，D 在 1 秒拿不到新额度。箭头表示各分支的时序。](assets/figures/go-rate-cancel.svg)

取消 C 时，它的最早发送时刻就是账本记录的最新事件时刻，两者相差 0 秒，算法可以退回 C 的一枚。账本先按时间推进到 −1.5，再加一枚得到 −0.5。到 1 秒又过了 0.75 秒，补 1.5 枚，余额为 1，所以 D 可以用 `AllowN` 立即取得一枚。B 的预约照常在 0.5 秒使用。

取消 B 时，最新事件仍是 C 的 1 秒，和 B 的时刻相差 0.5 秒。按原速率，这段时间会补一枚，源码从 B 想退的一枚中扣掉它，得到可退 0 枚。这是保守的局部撤销。限流器保留余额、上次更新时刻和最新事件时刻，预约对象交给各调用者，并没有一张可供重排的完整发送队列。C 继续等到 1 秒，D 同时来查账时可用余额是 0，申请失败。两种情况下都没有改写已交给别人的发送时刻。如果取消处理时已经过了预约的时刻，代码会直接放弃退回。 [CancelAt 的退回条件与公式](https://github.com/golang/time/blob/v0.12.0/rate/rate.go#L166-L204)

省去集中排程的代价，是取消未必能把原来的空档重新利用起来。愿意等待也会占用调用方的 goroutine 和计时器，限流器本身没有给等待者数量设上限。再者，预约得到的是最早可执行时刻，goroutine 调度晚了，实际发送仍可能靠得很近。单个限流器的账也只管经过它的请求，多进程各有一份账时就会各自计算额度。若慢下游还需要限制在途数量，发送速率与在途数量是两笔要分别算的账。

Envoy 的 HTTP 本地限流也用令牌桶保存可突发的存量，在启用且强制执行时，没有额度就直接返回默认的 429。等待成本因此留给选择重试的客户端。Go 里用 `WaitN`，应用可以选择在请求期限内吸收短时波动，代价是服务器自己要保留等待状态。该用哪种接口，取决于过载时更希望留住请求，还是更希望及时反馈并让调用方决定下一步。 [Envoy HTTP 本地限流](https://www.envoyproxy.io/docs/envoy/v1.40.0/configuration/http/http_filters/local_rate_limit_filter.html)
