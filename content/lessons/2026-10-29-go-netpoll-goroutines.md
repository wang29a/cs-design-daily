# Go：一个请求在等网络，为什么不必占住一条系统线程

一个服务同时处理两个请求。A 的客户端很慢，迟迟没有发来下一字节；B 的输入已经齐全，马上就能计算结果。如果用唯一的服务线程直接阻塞读取 A，B 明明有工作也只能等；如果每个请求配一条系统线程，代码顺序清楚，连接较少时也很好用，但大量闲连接会同时留下大量线程及其管理状态。今天理解 Go 的一个核心分工：请求可以保持顺序写法，等待请求却不必独占执行它的线程。

先交代系统位置。本文讲 Go 标准工具链的 runtime，固定 Go 1.25.0 官方提交 `6e676ab2`、Linux 上由标准库管理的 TCP 连接。编译后的程序带着运行时，在操作系统提供的线程和网络接口之上组织 goroutine。语言的 `go` 语句启动并发执行，运行时负责调度、栈与相关资源；它并没有替换 Linux 内核，也不能把系统的 CPU 和内存约束取消。下面核对的是固定实现，不声称所有 Go 实现都必须采用相同内部结构。[Go 官方对 goroutine 与线程的说明](https://go.dev/doc/faq#goroutines)

另一个自然方案是让少数线程用 epoll 管理大量连接，每次只推进当前就绪的请求。这已经避免了每连接一线程，但应用需要保存读到哪一步、还缺什么、下一次事件来了该继续哪里。复杂协议会把顺序逻辑拆成许多状态转移。Go 的关键洞察，是让运行时保留每项任务的可恢复执行状态，再把这些任务复用到系统线程上：等待关系继续存在，执行资源可以先交给别人。

## 把任务、线程和执行资源分开

设两个业务 goroutine 叫 GA、GB，这只是教学标签，不是程序可依赖的 goroutine ID。显式设置 `GOMAXPROCS=1`，得到一个调度资源 P0；当前系统线程叫 M1。GA 正在执行，GB 已可运行。GA 要从连接 A 的描述符 fd 7 读取一个字节，GB 不需要继续等网络，已有输入足够计算本地结果 B。排除超时、关闭、其他读者、cgo 和线程绑定；忽略运行时的其他内部任务。这是一条选定的教学时序，没有运行服务器、记录调度 trace 或测量性能。

这里才引入三个名称。G 是 goroutine，包括自己的栈和执行状态；M 是操作系统线程，真正承接指令执行；P 是执行用户 Go 代码所需的一组运行时资源，包括调度和分配器状态。可以把 P 先理解成带资源的执行资格，但它不是一颗固定的物理 CPU，也不是某个 goroutine 的私有财产。M 要执行用户 Go 代码，必须与 P 配合，再选择一个 G。[固定版本的 G、M、P 职责](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/HACKING.md#L16)

因此 `GOMAXPROCS=1` 限制的是同时执行用户 Go 代码的规模，不是只准创建一个 G，也不是进程最多只有一个系统线程。后台管理和阻塞系统调用等情况仍可能涉及其他 M。P0 让本例两个业务任务交替推进，不能让它们同时在两颗 CPU 上计算；操作系统若限制 CPU 带宽，拿着 P 也不等于随时获得物理执行时间。[Go 1.25 的 GOMAXPROCS 语义](https://pkg.go.dev/runtime@go1.25.0#GOMAXPROCS)

## 看似阻塞的 Read，内部怎样让出线程

GA 调用连接的 `Read`，目标缓冲长度为1。此时连接没有数据，对端也没有关闭。这个标准库 TCP 连接由网络轮询器管理，底层读取走非阻塞路径，暂时无数据时得到 `EAGAIN`。关键是：标准库不把这次底层结果直接当作业务读取失败返回，也不在用户代码里不停重试，而是转入等待读取条件的路径。[固定源码：读取、EAGAIN 与等待后的重试](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/internal/poll/fd_unix.go#L141)

标准库内部的等待桥接到 `runtime_pollWait`，运行时的 `netpollblock` 建立等待关系并通过 `gopark` 挂起当前 G。GA 的调用没有结束，局部变量与继续读取的位置仍能恢复。调度器的 `park_m` 把它从 Running 转为 Waiting，解除当前 M 与这个用户 G 的执行关联，再寻找其他可运行任务。在选定时序中，M1 继续持有 P0，换去执行 GB；没有为 GA 留一条线程专门睡在那次 socket read 里。[固定源码：网络等待与挂起](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/netpoll.go#L548)，[挂起后继续调度](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L4215)

GA 等待时，客户端送来字节 Q。Q 先进入内核的连接接收路径，不会直接跳进 GA 的 Go 缓冲区。GB 继续完成结果 B；当运行时轮询取得 fd 7 的读取就绪事件时，Linux 版 `netpoll` 通过 `netpollready` 找出相应等待者，调度器再把 GA 变成 Runnable，纳入可以继续执行的工作。这时只是具备了恢复资格，尚未说明读取已成功。[固定源码：epoll 事件交给网络等待者](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/netpoll_epoll.go#L156)，[调度器接收网络任务](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L3469)

我们继续选择 M1 与 P0 执行 GA。恢复后，它沿先前的读取循环重新调用底层 read；本例只有一个读者、Q 仍可读，因此返回1个字节，Go 的 `Read` 才以 n=1、err=nil 结束。GA 使用 Q 计算结果 A 并退出；GB 已经交出结果 B，两项本地工作至此结束。若程序还要通过网络发送响应，那又有写入与业务完成的责任，不能把这次读成功提前当成响应已送达。

这也解释了为什么通知后仍要真正读取：就绪是重试线索，不是一份已经取出的数据。完整协议若需要多个字节，还得按协议积累内容；本例刻意只读一个字节，避免把一次 Read 误写成总能收齐整条消息。实际恢复还可能由其他 M 承接，不应让业务逻辑依赖“我醒来一定还是原来的系统线程”。

## 最危险的窗口，在决定等待的那一刻

这里必须守住的不变量是：**一次读取条件的变化，要么被记录为待消费的就绪通知，要么能找到已经建立的等待关系；不能在两者之间无声丢失。**假如 GA 读到 EAGAIN，准备挂起，Q 恰在它正式睡下前到达；通知方发现还没有等待者便什么都不记，GA 随后又按旧判断睡下，就可能把已经存在的数据一直晾在内核里。

固定版本的 `pollDesc` 给读取等待保存不同状态：没有待处理条件、已有就绪通知、准备挂起、已登记的 G。`netpollblock` 先尝试消费已经记录的就绪状态；需要等待时再建立准备状态。真正提交挂起的 `netpollblockcommit` 用原子操作把准备状态换成 G 指针；若并发事件先把它改成就绪，提交就不能照旧成功，任务会继续推进。反过来，G 已登记后事件才能取得等待者，交给后续调度。[固定源码：等待状态的约定](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/netpoll.go#L51)，[提交与唤醒的衔接](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/netpoll.go#L529)

这是对同步职责的压缩，不是建议应用照抄几个状态就实现调度器；关闭、超时、对象复用还各有保护。它与此前 futex 的等待交接相似，但保护的是用户态 G 的挂起和网络条件，不能拿一个系统的具体原子操作直接证明另一个系统正确。

## 等待便宜了，保留的请求仍有成本

当全部业务 G 都在等网络，运行时也可以让某个线程阻塞在网络轮询中，避免空转；它不承诺“整个进程永远没有线程等待”。省下的是大量请求各自绑住一条等待线程的需求。真正阻塞的其他系统调用、某些文件 I/O 或外部代码，也不能不加区别地套用刚才的非阻塞 socket 路径。[固定源码：无可运行任务时的网络等待](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/proc.go#L3706)

代价被转移给运行时：它维护 G 的栈与状态、可运行工作和网络等待关系，承担调度与同步复杂性。挂起并不释放请求持有的全部对象，慢客户端依然可能长期占内存；没有足够 CPU 时，把更多任务变成 Runnable 也不会增加机器的计算能力。所以 goroutine 适合表达并发，不等于可以无限接纳工作。本文没有测量线程数、吞吐或栈开销，也不把两个教学任务推广成容量结论。

先独立判断：若 Q 一开始就在 fd 7 的缓冲里，GA 还必须挂起一次吗？若 GA 变成 Runnable 时 P0 正在执行别的任务，可读通知又保证了什么？把“等待条件满足”“取得执行资格”和“完成业务”分别回答。

接回 Linux epoll，就能看见两个系统的接口分工。epoll 保存文件对象的关注与就绪关系，让线程取得哪些 I/O 值得重试的线索；Go 在此之上保存任务的调用状态，把同一线索接到“哪个 G 可以恢复”。共同结构是把众多等待者与当前可推进者分开，差别是内核不替业务保存 Go 调用栈，运行时也不替 TCP 完成协议消息。顺序代码、有限执行资源和大量等待请求能够共存，依赖的正是这些边界被逐层接通。[Linux epoll 的就绪通知职责](https://man7.org/linux/man-pages/man7/epoll.7.html)
