# WAL：怎样在随时可能中断的世界里确认一次修改

这篇补上 2026 年 10 月 3 日的内容。个人知识库要保存一篇笔记，事务里同时更新正文与检索索引。我们用简化的两个页面表示它：页面 A 存正文，页面 B 存对应的索引。合法状态只有旧正文配旧索引，或者新正文配新索引；新正文配旧索引是应用不能接受的中间状态。

最自然的实现是直接覆盖 A，再覆盖 B。即使没有其他线程，进程也可能恰好在两次写入之间退出。加锁解决的是运行中的相互干扰，机器断电以后，锁不能替你补完第二次写入。这里要处理的是完成一半的持久化动作。

可以提出一个看起来更直接的办法：让磁盘把两页同时写完。但页面可能位于不同位置，事务也可能修改更多页，而系统还存在内存缓存、操作系统缓存与存储设备。不能仅靠应用连续调用两次 write，就假定整个修改获得了一个统一的原子边界。

WAL 引入的关键洞察是：先把足以支持恢复的信息可靠保存，再允许正式数据页落后于这份记录。这样，应用确认成功所依赖的持久化路径，和后续整理数据页的路径可以分开安排。对使用 WAL 的数据库而言，修改对应的日志必须先于相关数据页持久化；具体日志内容、恢复算法与事务可见性则依实现而异。[PostgreSQL WAL 原理](https://www.postgresql.org/docs/current/wal-intro.html)

为了具体说明原子边界，我们接下来只讨论 SQLite 的 WAL 模式。它把修改后的数据库页面追加到 WAL 文件，而不是在事务提交过程中直接覆盖主数据库的旧页面。WAL 有提交边界，读取要选择属于有效提交范围的页面。以下数字是教学模型，省略真实文件头、校验与锁协议。

假设主数据库仍然保存 A0 与 B0。事务生成 A1 与 B1，并准备把它们记入日志。用逻辑记号表示过程：

```text
主数据库：A0，B0
日志追加：A1
日志追加：B1，事务提交边界
```

现在看三个中断位置。如果在追加之前退出，当然只能看到旧版本。如果 A1 已经写入，但事务提交边界尚未成立，这些尾部内容不能作为一个完整的新事务向读者发布。如果新版本的有效提交已经可靠保存，即使主文件仍是 A0、B0，数据库也能通过主文件与 WAL 的组合提供 A1、B1。关键是识别有效事务边界，而不是把日志里出现过的所有字节都当成正式状态。[SQLite WAL 文件格式](https://www.sqlite.org/walformat.html)

这时容易产生疑问：如果数据页没有写回主文件，读取为什么还能正确？因为数据库的逻辑状态不必等同于一个文件当时的内容。WAL 模式下，读事务记住自己开始时可见的日志结束位置。要读某页，先在这个范围以内寻找它的最近版本，找不到才读主文件。[SQLite WAL 的读者算法](https://www.sqlite.org/wal.html#concurrency)

把读者也放进例子。读者 R 在新事务提交之前开始，记住旧的可见边界。写者随后提交 A1、B1，新的读者 N 可以读取新版本，但 R 仍沿着旧边界读取 A0、B0。只要 R 的事务还没结束，它就不必在查询一半时突然换到另一个版本。SQLite 用这种方式提供 WAL 模式下的快照隔离。[SQLite 隔离说明](https://www.sqlite.org/isolation.html)

这里有两个不同问题：提交是否形成一组可见的修改，以及这些修改在何种故障之后还能保留。前者涉及原子性与读取规则；后者涉及持久化顺序和同步策略。不能因为调用了 COMMIT，就在任何配置下都声称已经获得相同的掉电保证。

例如，SQLite 在 WAL 模式下采用 synchronous=FULL 时，会在每次事务提交后同步 WAL；NORMAL 会减少同步，但某些已经提交的事务可能在掉电或操作系统崩溃后丢失。讨论“已提交不会丢”时，必须把同步配置和底层存储保证带进结论。进程退出、操作系统崩溃和机器断电，也不是同一个故障模型。[SQLite synchronous 文档](https://www.sqlite.org/pragma.html#pragma_synchronous)

再问一个问题：既然读写都能依靠 WAL，为什么还要检查点？因为日志不应无限增长。检查点把已经合适写回的页面搬回主数据库，使旧日志最终有机会被复用。但它不能把一个旧读者还需要的视图破坏掉。一个持续很久的读事务，可能让检查点不能推进到最新位置。这是快照稳定性换来的维护成本。

所以 WAL 的代价不只是“多写一份日志”。系统增加了第三类动作——检查点，需要协调它与读者、写者的关系。页可能先写入日志，再写回主文件，形成额外 I/O；同步操作影响提交延迟；长读事务影响回收；SQLite 还需要共享 WAL 索引，并仍然限制同一时刻只有一个写者。读取稳定性与存储回收之间存在真实矛盾。

可以用反事实检查这个设计。如果系统在日志尚未可靠保存时，就把新页面覆盖到主文件，然后断电，恢复会缺少什么？可能缺少解释或修复已经覆盖内容所需的信息。先写日志这一顺序约束，正是为了避免正式状态走到了恢复依据前面。

再把这个设计放回软件工程。你实现一个可恢复工作流时，需要先定义哪些信息足以重建进度，再决定什么时候可以对外确认完成。只打印“开始保存”并不足够；日志必须有稳定格式、边界、存储保证与恢复解释器。WAL 的漂亮之处，在于把恢复从事后猜测，变成正常写入协议的一部分。

事件溯源可以从相近角度理解：保留事件，使状态能够通过规则重建。不过，它记录的可能是业务事件；SQLite WAL 记录的是页面版本。两者在记录粒度、重放规则和事务语义上并不相同。设计思想可以迁移，具体正确性证明不能直接搬过去。

阅读完成以后，试着解释这个状态：主数据库还没有新正文，但保存 API 已经成功返回，新的查询也能读到新正文。它未必矛盾，因为读者的正式视图可能来自主文件与已提交 WAL 的组合。接着必须追问同步配置，才能判断机器断电后是否仍保证保留。

本篇在本机 SQLite WAL 模式下运行了双连接更新与快照读取：写者提交 A1、B1 后，已开启事务的旧读者仍读到 A0、B0，新连接读到 A1、B1。这个实验验证了快照行为，没有模拟进程崩溃或真实断电。页面序列仍是教学模型，也没有把 PostgreSQL 与 SQLite 的恢复实现混为一套算法。两个页面代表事务修改的关系，并非声称某个具体 SQL 语句只触碰两个页面。
