# Kafka 为什么把消息保留和消费进度分开

订单服务接连产生“下单、付款、发货”三条事件。通知服务要逐条联系用户，统计服务要把三条事件计入报表。统计很快，通知很慢。第一条消息被统计读完以后，消息系统能不能把它删掉？如果为了通知留下它，明天新增的审计服务又能否从头读取？

最直接的办法是给每种业务各建一条队列，处理完成就确认，随后回收消息。只有一个工作池、处理完就不再需要历史时，这个方案很合适。但每增加一种独立用途，就需要再准备一份投递状态，甚至再保存一份消息。若产品后来要求重算昨天的报表，已经被确认并回收的数据也无法从这条队列里重取。矛盾出在我们让“某个业务已经处理完”和“这条历史可以消失”共用一个结束条件。

Kafka 选择把它们分开。生产者把事件写入主题，主题分成若干分区，broker 保存分区日志的副本，消费者通过网络按位置读取。每个分区里的记录有自己的 offset，代表逻辑位置。同一种业务的消费者组成组，共用这一业务的消费进度；不同组可以独立读同一条分区日志。今天从 Kafka 4.1 的普通消费者组进入，沿一个分区 P0 推演。假设三个事件已经可读，位置恰为 100、101、102，主题使用 `cleanup.policy=delete`，教学场景只使用本地存储与非事务记录。数字及段界都是教学设定。 [Kafka 的基本部件与主题](https://kafka.apache.org/41/getting-started/introduction/) · [消费者组与分区分配](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#consumergroups)

通知组记为 N，统计组记为 S。两组起初都准备从 100 开始。S 处理完三条事件，保存进度 103；N 只处理完下单事件，保存进度 101。保存的数字表示接下来应从哪里继续，所以 103 是这段日志的末尾位置，那里暂时没有第四条事件。在这个例子里 N 还欠付款和发货两条，S 已追上。offset 的作用域是分区，换一个分区，相同的 101 会指向另一份记录。真实记录的位置还可能有空洞，本例的连续编号只是为了便于推演。 [offset、读取位置和已提交位置](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#offsets)

看图一。两组都读取过 100，N 接下来要 101，S 接下来等 103。图中哪份状态发生了变化，哪份数据仍被共同使用？

![图一。P0 保留 100 下单、101 付款、102 发货三条记录，末尾为 103。通知组 N 已提交 101，统计组 S 已提交 103。深色箭头指向各组恢复后下一次读取的位置。共享的是这份逻辑日志，实际部署另有分区副本。](assets/figures/kafka-log-cursors.svg)

N 提交 101、S 提交 103，改变的是各自保存的进度，日志里的三条记录仍在。新增审计组时，只要 100 还在保留范围内，就可以为它选择从 100 开始，让它独立走一遍历史。重算报表也可以用独立组读取，原统计组的进度继续保留。存储不必为每个新用途复制整条逻辑流，新增的读取仍会消耗网络、缓存与计算资源。这个分工让“还想再读一次”成为有地址可定位的操作。 [分区进度与主动回退的设计](https://kafka.apache.org/41/design/design/#consumer-position)

一个整数能表示进度，依赖于它代表已经完成的连续前缀。沿 P0 顺序处理，处理完 100 后记 101，处理完 101 后再记 102。若应用把多条记录并行交给工作线程，先完成 102，却还有 101 没做完，就不能仅因为最大完成位置是 102 而提交 103。崩溃后从 103 恢复，会把中间那条未完成的付款通知跳过去。应用必须汇总连续完成边界，才能继续用一个数字表达恢复承诺。

这里还要分清客户端拿到了什么和业务完成了什么。假设 N 一次 `poll` 就拿到 101、102，它的本地读取位置会前进到 103。此时付款通知可能还没发，持久保存的组进度仍应是 101。本篇选择关闭自动提交，由应用在业务步骤完成后明确提交相应位置。提交到 Kafka 的消费进度可以供重启后的实例恢复，提交请求成功也不会证明用户已经收到通知。 [Java 消费者的位置推进与手动提交](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

现在 N 已经成功发送 101 对应的付款通知，但还来不及提交 102 就崩溃了。图二中，重启后它会先读哪条？S 的进度要跟着倒退吗？

![图二。N 原已提交 101，读取付款事件 101 并完成通知，提交 102 前崩溃。重启仍从 101 读取，因此付款通知可能重复。再次处理并成功提交 102 后，N 才继续到发货事件。S 的已提交位置始终为 103。箭头表示教学时序。](assets/figures/kafka-log-replay.svg)

新的 N 实例恢复到 101，再拿到付款事件。这次重读没有改变记录地址，也没有修改 S 的 103。N 再处理并成功提交 102，随后处理发货并提交 103，便追上了这段输入。问题是第一次付款通知可能已发出，第二次执行会重复。若反过来先提交 102、再发送付款通知，崩溃窗口又会变成漏发。这两个外部动作之间需要应用自己的协调，例如让下游识别事件的唯一标识、重复请求复用既有结果。用 offset 保存恢复点，使重读可控，也把外部业务能否安全重复的责任留给处理方。 [处理输出和消费位置之间的故障窗口](https://kafka.apache.org/41/design/design/#message-delivery-semantics)

再从图一分出另一种时序。N 停在 101 很久，S 仍是 103。日志始终保留，磁盘迟早会不够；若全等最慢的组确认，新建后就被遗忘的组可能拖住整份历史。Kafka 让主题的保留策略决定可读历史的长度。删除型主题按时间或大小条件回收旧日志段，不以每个消费者组是否读完为前提。完成消费不会立即删记录，尚未消费也不会自动保护记录。 [主题删除与保留配置](https://kafka.apache.org/41/configuration/topic-configs/#cleanup.policy)

看图三。假设 100、101 位于已封闭的旧段，102 位于后一个段。旧段满足保留策略和删除所需条件并被清理后，N 保存的 101 还够不够它恢复付款通知？

![图三。独立于图二的过期分支。旧段含 100、101，后段保留 102。旧段被清理后，可读起点推进到 102，N 的已提交 101 落在范围之外，S 的 103 仍是末尾。箭头表示清理前后变化，段界为教学简化。](assets/figures/kafka-log-retention.svg)

N 再请求 101，日志已经无法提供它。客户端可以按 `auto.offset.reset` 选择跳到仍保留的最早位置，或者跳到末尾，也可以通过配置让越界暴露为错误。选择最早位置 102 能继续读取发货，但这份日志无法补出已经消失的付款事件。已提交进度保存的是地址，地址有效还依赖相应历史仍在。 [消费位置越界时的策略](https://kafka.apache.org/41/configuration/consumer-configs/#auto.offset.reset)

实际回收以日志段为单位，时间条件还要结合段内时间戳和清理过程，配置“保留一天”并不等于每条记录满一天那一瞬间就单独消失。Kafka 4.1.0 的 `UnifiedLog.deleteOldSegments` 进入大小和时间保留检查，时间路径用段的最大时间戳判断，再交给受保护的段删除流程。运营方因而要给正常处理、停机修复和重算留足时间与空间，并观察最慢业务离日志起点还有多远。 [保留条件的源码入口](https://github.com/apache/kafka/blob/4.1.0/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java#L1880-L1913)

这也接回最早讲过的 Unix 管道。管道与 Kafka 日志都让生产和处理可以不同步，但有限管道的未读字节填满缓冲后，通常的阻塞写会等待，消费速度直接影响写方推进。Kafka 把历史留在日志中，让多个组分别记录位置，慢组首先积累落后量，继续落后则可能越过保留边界。等待、存储和历史丢失的成本分配因此不同。若需求只有一个工作池取走任务，完成后即可回收，逐条确认的队列仍有直接的适用场景；若多个独立业务需要按各自节奏重读，日志与进度分离就能减少彼此之间的牵制。 [Linux 管道的容量与阻塞](https://man7.org/linux/man-pages/man7/pipe.7.html)
