# RocksDB：两次修改，怎样一起对读者生效

一个服务用 RocksDB 保存两份额度：甲有 100，乙有 40。现在把甲的 10 转给乙，希望状态从 (100,40) 变成 (90,50)，总量始终是 140。最自然的代码先 Put 甲=90，再 Put 乙=50。每个调用单独看都正确，但两个调用之间，读者可能看见 (90,40)，进程也可能在第一步后退出。业务的一次修改，被存储接口拆成了两个可以分别成立的事实。今天要理解：怎样保留逐条写入的实现，却只向读者公布完整结果。

RocksDB 是嵌入应用进程的键值引擎。前几篇已经讲过，WAL 提供恢复依据，memtable 接受最近更新，SST 承接刷出的有序数据，后台合并整理历史。昨天的快照把读者固定在某个序号边界，并让合并保留旧答案。今天从边界另一侧切入：写者怎样决定哪些序号现在可以被读取？这里讲普通 WriteBatch 与默认有序写入路径，单列族、普通 Put，排除 unordered_write、特殊事务写入、原地更新和自定义回调等分支。数字均为教学状态，不是本机运行记录。

给两个 Put 外面套应用互斥锁，可以防止配合使用同一把锁的线程插入读写；数据小、所有访问都经过同一入口时，这是可行方案。但锁不把两条 WAL 记录合成一次修改，进程崩溃后也不会继续持有它。只增加读者锁，不能补足恢复协议；要求每个调用者遵守应用规则，还扩大了协作范围。我们需要存储引擎知道这两次更新属于同一组。

WriteBatch 就是这份声明。调用者先构造有序编辑集合，再一次交给 `DB::Write`。构造 batch 时并没有修改数据库，调用成功后才获得接口承诺。组内操作顺序仍有意义：同一键先 Put、再 Delete，与相反顺序不同；“一起生效”不等于把组内顺序抹去。[WriteBatch 的原子更新接口](https://github.com/facebook/rocksdb/wiki/Basic-Operations#atomic-updates)

```cpp
rocksdb::WriteBatch batch;
batch.Put("甲", "90");
batch.Put("乙", "50");
rocksdb::WriteOptions options;
options.sync = true;                 // 本例开启 WAL，要求同步持久化
rocksdb::Status status = db->Write(options, &batch);
// 实际程序必须检查 status；这里不是读取并发控制的完整实现。
```

先把输入固定：甲@1=100、乙@2=40 都已经写完，当前可见序号 V=2。新批次的两次 Put 分配序号 3、4。V 表示普通路径中读者可取得的最新边界；分配了序号，并不意味着对应修改已经对外生效。旧快照 P2 固定在 2，新读者也从已公布的边界取得自己的读取视图。

批次写入先把恢复记录交给 WAL，按本例 `sync=true` 完成要求的同步，然后安装到 memtable。为了讲清楚，假设先插入甲@3=90，再插入乙@4=50。安装第一条时，内存已经含有新甲，但 V 仍是 2。此时取得边界 2 的读者跳过序号 3，读甲@1=100；读乙仍是 40。内部出现过半成品，外部却没有获得观察它的边界。等两条都安装成功，再把 V 从 2 推进到 4，随后获得边界 4 的读者才会选中完整的新状态。

先看图并预测：甲@3 已经进入内存、乙@4 还没进入时，一个新读者为什么不能直接返回甲=90？

核对固定源码提交 `72beaf8`，普通写入路径先调用 `WriteGroupToWAL`，随后 `WriteBatchInternal::InsertInto`，成功后才 `SetLastSequence`；源码在发布条件旁明确强调不能发布部分批次。序号存储还使用相应内存次序，实际正确性需要它与 memtable 的并发访问规则配合，不是随意改一个普通整数就够了。[写入安装与发布条件](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/db_impl/db_impl_write.cc#L1377)、[可见序号的发布](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/db_impl/db_impl_write.cc#L1553)、[序号的内存次序](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/version_set.h#L1511)

核心不变量是：读者取得的可见边界必须停在完整批次的边缘，并且不能越过尚未完成的安装。反事实地在甲安装后就公布 V=3，新快照会选中甲=90、乙=40，总量变成 130；它还可能把这个错误中间状态固定下来。只给两个更新分配相邻序号并不够，必须约束公布边界的时机。旧 P2 则在 V 推进以后仍读 (100,40)，这正接回昨天的历史保留义务。

真实写入还会把多个线程的请求组织成写入组，合并日志工作，memtable 安装也可能并行。普通有序路径要等组内安装完成，再推进可见边界；所以这里的“一起”可以由更大的组共同实现，不要求每个应用 batch 都单独同步一次磁盘。代价是同组较快的写者可能要等待较慢的安装者。官方 unordered_write 文档专门比较了这个取舍：放宽安装与发布顺序能够减少等待，却会改变普通批次原子可见性和快照不变性；本篇没有启用它，也没有测量吞吐。[有序写入与放宽顺序的语义差异](https://github.com/facebook/rocksdb/wiki/unordered_write#ordering-in-vanilla-rocksdb)

这解释了运行中的读者，重启怎么办？V 是内存里的发布状态，不能独自承担持久性。WriteBatch 的编码保存起始序号、操作计数和有序编辑；普通日志路径把一个合并批次的内容交给 WAL 的 `AddRecord`，作为一个逻辑记录。恢复先取得完整日志记录，再解释其中的批次，不能把“已经读到第一条 Put”当作一个独立完成的业务修改。[批次头部](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/write_batch.cc#L783)、[写入逻辑日志记录](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/db_impl/db_impl_write.cc#L2315)

逻辑记录并不等于一次不可分割的物理写。较长记录可以拆成 FIRST、MIDDLE、LAST 片段，读取器只有获得完整记录才交出它；中断尾部不能被当作完整批次前缀来正常重放。损坏处理还受恢复模式约束，可能报错而非继续打开，这里不把任意磁盘损坏都承诺成自动恢复。[WAL 的分片格式](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-File-Format)、[完整记录读取与尾部处理](https://github.com/facebook/rocksdb/blob/72beaf8dfb9a96efc960502d4cb7b68c43c0d120/db/log_reader.cc#L96)

若完整批次日志已经可靠同步，却在安装甲之后、安装乙之前崩溃，成功恢复会根据日志重建两次修改，不依赖那份已经丢失的半成品内存。若同步之前掉电且日志尾部未完整留下，本次新状态就没有本例成功同步的持久化承诺。即使恢复得到新状态，调用者也可能没收到成功返回，重试业务仍需要自己的去重办法。原子恢复、收到响应、业务只执行一次，是三个不同问题。默认 `sync=false` 或关闭 WAL 时，也不能照搬本例的掉电保证；同步还依赖文件系统与设备兑现承诺。[同步写的条件](https://github.com/facebook/rocksdb/wiki/Basic-Operations#synchronous-writes)

还有一个容易踩中的阅读边界。假设监控先独立 Get 甲，得到 100；此后完整 batch 生效；再独立 Get 乙，得到 50。它算出 150，但引擎从来没有公布 (100,50) 这个单一视图。它拼接了两个合法时点。原子写保障一次读取视图不会落在批次中间，不保证任意多次独立调用自动共享同一时点。监控应取得显式快照，并把它用于两次读取，最后安全释放。

第二幅图区分的是：出错的究竟是写者公布了半批次，还是读者跨了两个完整状态？

![教学图：两次独立 Get 在完整批次生效前后分别读取甲=100、乙=50，拼出 150；两次读取都使用 P2，则即使中途批次生效也仍得到甲=100、乙=40，总量 140。箭头表示调用顺序；图中没有发布半批次。](assets/figures/rocksdb-batch-read-view.svg)

WriteBatch 也不自动检查你算出这些新值时读到的依据。若两个线程都读取 (100,40)，分别算出转移 10 后的 (90,50) 和转移 20 后的 (80,60)，再按这个顺序提交完整批次，最后是 (80,60)。每次写入都完整，总量也都等于 140，但预期累计转移 30 的结果 (70,70) 没有实现。旧依据覆盖了另一线程的进展。要保护“读—计算—写”的依赖，需要覆盖整个过程的应用同步，或使用具备相关冲突保护的事务接口；只换成 batch，甚至只让初始读取使用快照，都不够。RocksDB 的事务文档用 `GetForUpdate` 把读取值作为提交需要保护的前提，这是另一层职责。[事务对读取依赖的保护](https://github.com/facebook/rocksdb/wiki/Transactions#guarding-against-read-write-conflicts)

可以与已经讲过的 SQLite WAL 接起来：页面先追加到 WAL，提交边界再使一组页面形成有效的新状态，读者固定自己的结束位置。共同结构是允许内部逐步准备，再通过受控边界公布整体结果；区别在于 SQLite 以页面和事务提交记录组织更新，RocksDB 普通批次以键编辑、序号发布及逻辑 WAL 记录配合。不能因为都有边界，就把 RocksDB WriteBatch 当成具备全部 SQL 事务隔离语义的对象。这是机制比较，不是历史传承判断。[SQLite WAL 的提交与读取边界](https://www.sqlite.org/wal.html#how_wal_works)

这个设计的价值，在于把“很多位置真的在同一瞬间改变”改写成“所有读者只能选到完整边界”。代价由序号管理、版本维护、日志封装和组内等待承担；应用还负责选择一致的读取视图、保护计算依据及处理失败。留一个独立判断：若监控固定在 P2，转移连续发生三次，它会跟着变化吗？若把 `sync` 改为 false，改变的是快照答案还是掉电后的承诺？分别追问边界由谁负责，才不会把几个“原子”混为一个保证。本文是官方文档核对、静态源码分析和教学推演，没有运行 RocksDB、注入故障或做性能测量。
