# Linux：文件怎样变成一段可以直接读取的内存

假设你正在写一个索引器，需要在一个大文件里反复跳转，读取不同位置的字段。最直接的方案是申请缓冲区，用 `read` 或 `pread` 把文件内容读进来，再解析缓冲区。这个方案边界清楚，也很适合顺序流式处理；但如果只访问其中零散的一部分，提前读完整个文件浪费内存和工作，自己维护分块缓冲又要处理“这一段是否已经读入、旧块何时替换、字段跨块怎么办”。

前一篇已经认识了 Linux 页缓存：普通缓冲读取通常先经过内核缓存，再把数据复制到用户缓冲区。如果多个进程解析同一份文件，内核里可以只有一份缓存，进程却可能各自再留一份副本。这里有一个值得重新分配的职责：程序真正需要的是“通过地址访问文件内容”，未必需要“拥有文件内容的另一份拷贝”。既然 CPU 已经通过页表把虚拟地址翻译成物理地址，能不能让那段虚拟地址直接接到文件的缓存页上？Linux 的文件映射 `mmap` 正是沿这条思路工作。它处在进程虚拟内存、页缓存与文件系统之间，把文件访问接入已有的地址翻译机制。[Linux 6.12 VFS：address space](https://docs.kernel.org/6.12/filesystems/vfs.html#the-address-space-object)

## 先登记一项承诺，再兑现具体的一页

我们固定一个教学例子，后文的地址与图都沿用它。普通文件 I17 长 8192 字节，基础页大小假设为 4096 字节，因此文件页 P0 覆盖偏移 0—4095，P1 覆盖 4096—8191。文件偏移 `0x34` 的字节是 A，偏移 `0x1034` 的字节是 K。下面只讨论普通文件的只读映射，文件不被并发修改或截断，省略大页、DAX、预先填充映射及失败重试的细节；这是机制推演，没有实际运行追踪或性能测量。

进程甲调用 `mmap(NULL, 4096, PROT_READ, MAP_SHARED, fd, 4096)`，映射文件的第二页。假设调用成功，内核选择的起始虚拟地址为 `a = 0x40000000`。这里把返回值写成固定数字只是为了计算，并没有要求应用强占这个地址；实际程序还须检查 `MAP_FAILED`。文件偏移参数必须按系统页大小对齐，我们的 4096 正好满足这个条件。[mmap 接口约定](https://man7.org/linux/man-pages/man2/mmap.2.html)

映射成功不意味着第二页已经从设备读入。先建立的是一段地址区域的约定：这一段地址可以读，它对应哪个文件，从文件的哪个偏移开始。Linux 用 VMA 表达这样的区域属性，页表则负责表达具体虚拟页当前对应哪个物理页。二者分工很关键：**一个区域合法存在，不要求它包含的每一页都已经有可用的页表项**。在 Linux 6.12 的普通通用文件映射路径中，`generic_file_mmap` 主要挂接文件映射操作；后续缺页才进入相应处理，并非在这里把整个区域读完。[固定版本源码：generic_file_mmap](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/filemap.c#L3729)

现在选择一个冷的初始状态：甲的目标页表项尚不存在，页缓存中也没有 P1。甲执行一次普通内存读取，地址是 `a + 0x34`。观察下面的过程：哪一步只是在确认“可以读”，哪一步才使 CPU 真正能够读到 K？

![甲从未建立页表项且 P1 不在缓存的状态开始，缺页处理按文件偏移找到 P1，读入 F42，建立只读页表项，然后重试原来的读取。](assets/figures/linux-mmap-fault.svg)

图 1：一次成功的冷页读取教学模型。箭头表示处理顺序；实际内核可能预读、释放锁并重试，图不代表一次缺页必然对应一次设备请求。

CPU 找不到可用翻译，触发缺页异常。内核检查地址是否位于合法 VMA，以及访问是否符合权限，然后根据映射关系算出文件位置：`文件偏移 = 映射起始文件偏移 +（访问地址 − 映射起始虚拟地址）`。这里得到 `0x1000 + 0x34 = 0x1034`，所以需要文件页 P1 中偏移 52 的字节。注意文件偏移和虚拟地址不是同一套坐标；两者只通过区域记录的关系连接。

没有缓存页时，内核需要取得承载数据的内存并通过文件系统读入内容；读取可以涉及预读，也可能等待 I/O。把这次成功得到的物理页记作 F42。只有页内容已经可用、映射关系仍有效，缺页处理才可以完成页表安装，让甲的这个虚拟页以只读权限指向 F42。异常处理结束后，CPU 继续执行原先那次读取，得到 K。它不是额外返回一个 `read` 的结果，程序仍在执行原来的内存访问。[Linux 6.12 页表与缺页处理](https://docs.kernel.org/6.12/mm/page_tables.html)

源码中可以看到这个分工：`filemap_fault` 按文件和页索引寻找缓存 folio，处理缺失、读取及有效性检查；`do_read_fault` 在适用时先尝试批量建立邻近映射，否则调用缺页操作，再完成映射。因此，这张图表达的是依赖关系，不是所有机器都必须逐个经过的固定调用清单，也不能用来数磁盘请求。[固定源码：filemap_fault](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/filemap.c#L3301)，[do_read_fault](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/memory.c#L5277)

## 地址各自独立，文件页可以共用

接着，进程乙也只读映射 I17 的第二页，但得到 `b = 0x70000000`。乙读取 `b + 0x34` 时，自己的目标页表项仍然缺失，可是 P1 仍留在页缓存中。这次需要解决的是“给乙建立翻译”，不必为目标 P1 重新取得一份文件内容。暖缓存路径还可能通过 `filemap_map_pages` 建立映射；不能把每次缺页都等同于磁盘读取。[固定源码：filemap_map_pages](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/mm/filemap.c#L3630)

看下面两条路径：为什么虚拟地址不同，最后却能读到同一个 K？

![甲的 0x40000034 和乙的 0x70000034 经各自只读页表项指向同一个文件缓存页 P1，教学物理页 F42 的页内偏移 52 为 K；甲解除映射后乙仍可引用它。](assets/figures/linux-mmap-sharing.svg)

图 2：实线表示地址翻译，虚线表示文件页的身份关系；P1、F42 与页内偏移沿用图 1。图下方单独展示甲解除映射后的引用关系。

关键不是两个进程约定同一个指针，而是各自的映射都指向同一个文件的同一页。虚拟地址属于进程自己的地址空间，物理页则可以共享。与普通缓冲读取相比，这里免去了把缓存内容再复制到每个用户缓冲区的那一步；仍然有页表维护、缓存管理和必要的文件读取工作。所谓“直接访问”必须具体到这条路径，不能理解成 CPU 绕过内核、设备或所有数据搬运。

这也给出了设计必须守住的不变量：**区域记录的文件身份、文件偏移、访问权限，必须与最终可访问的页一致，而且数据尚未有效时不能交给 CPU 使用**。假如内核忘记映射从文件偏移 4096 开始，把甲的虚拟页误接到 P0，甲的地址计算仍然完全正确，却会读到 A 而非 K。问题出在翻译兑现了错误的承诺。实际路径还要应对并发截断等变化，Linux 会重新检查缓存归属和文件长度，必要时重试或返回错误；这一复杂性由内核承担，才使程序能够使用普通读取指令。[filemap_fault 的检查与重试契约](https://docs.kernel.org/6.12/core-api/mm-api.html#c.filemap_fault)

这个例子的结束条件也要说清。甲读完后调用 `munmap(a, 4096)`，撤销自己的地址关系，相应翻译需要被拆除；乙仍有映射，不会因为甲离开就失去文件页。双方都解除映射后，干净的页仍可能作为缓存留下，并不要求立即释放。文件描述符与映射的生命周期也不同：成功建立映射后关闭原来的 fd，并不会自动撤销映射。读完、关 fd、解除映射，是三个不同事件。[mmap 与 munmap 的生命周期约定](https://man7.org/linux/man-pages/man2/mmap.2.html)

## 节省拷贝以后，谁来付账

这个设计好在复用了已有的分工：应用通过地址表达访问，VMA 保存区域约定，页表落实当前翻译，页缓存负责文件数据的驻留，文件系统负责缺失数据的取得。程序不用为每个字段显式调度读块，但成本转移到了缺页异常、页表内存、地址翻译缓存 TLB，以及内核的回收与同步路径。访问没有驻留的数据时，一条看似普通的读取指令也可能停下来等待。映射成功只是建立关系，不能承诺后面的读取全部立即完成。

因此，`mmap` 并非总比 `pread` 快。顺序处理时，一个可复用的大缓冲区配合批量读取就很自然，也容易控制 I/O 的提交边界；映射是否更合适，要看访问分布、重复利用、内存压力和缺页成本。这里没有测量，不能据此给出性能胜负。对于偏移驱动、需要多次访问同一数据的程序，映射可以让文件布局和程序的读取方式直接对应；代价是潜在 I/O 等待藏进了普通内存访问。

边界同样真实。本文是只读映射，写入会违反权限。扩展到可写 `MAP_SHARED` 时，还需要应用自己的并发协议，映射本身不提供事务，也不把“改了内存”变成持久化完成；控制同步写回要看 `msync` 等接口及文件系统语义。换成 `MAP_PRIVATE`，写时复制允许私有修改，但它不等于“映射时冻结文件快照”，接口并未保证映射建立后外部文件修改的可见性。文件若被截断，访问落到新的文件末尾之后的整页还可能触发 `SIGBUS`，不再是可任意解引用的一段稳定数组。[mmap 的共享、私有与信号边界](https://man7.org/linux/man-pages/man2/mmap.2.html)，[msync 同步约定](https://man7.org/linux/man-pages/man2/msync.2.html)

可以先独立推演一个变化：乙仍从 `b + 0x34` 读取，但建立映射时把文件偏移改为 0。乙应该看到什么？它与甲共享哪一页的条件还成立吗？再想想，如果乙关闭 fd，却没有 `munmap`，哪一条关系真的消失了。回答这两个问题，比记住几个系统调用名称更能检验是否掌握了设计。

回看此前的虚拟内存讲义，两者共有的结构是“先维护地址空间的语义，再按需兑现具体物理页”；区别在于文件映射把地址接到了一个具有外部身份、可能变化的文件对象上，所以还必须处理文件偏移、缓存一致性和截断边界。与前一天页缓存的联系更直接：同一份文件缓存既可以作为 `read` 的复制来源，也可以成为页表映射的目标。漂亮之处在于把不同访问接口接到同一个数据身份上；能否采用，则取决于你是否愿意用隐式缺页与映射生命周期，换取更直接的访问表达和更少的用户副本。

再联系此前 RocksDB 的旧文件回收：甲撤销映射不代表乙结束使用，就像新 Version 已经发布，也不代表旧迭代器不再需要原来的 SST。共同结构是把“撤销一个入口”和“资源可以销毁”分开判断；区别在于 RocksDB 依赖不可变 SST 和版本持有关系保护旧读取路径，普通共享文件映射所连接的文件内容却可能改变，映射存活并不提供数据库的一致快照。这是生命周期结构的比较，不能把一边的快照保证搬到另一边。[RocksDB 存活文件与引用关系](https://github.com/facebook/rocksdb/wiki/How-we-keep-track-of-live-SST-files)
