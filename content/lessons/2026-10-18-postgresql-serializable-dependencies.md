# PostgreSQL：两笔事务各自都没错，为什么一起提交会出错

一个值班组只有甲、乙两人，规则是至少留一人在岗。每个人申请下班时，程序先查当前在岗人数：多于一人，就把申请者改成离岗；只剩一人，就拒绝。这段逻辑单独执行没有问题。现在甲、乙同时申请，两笔事务各自读到两人在岗，分别只修改自己的那一行，最后却都提交成功。没有读到脏数据，没有相互覆盖，值班组仍然变成了零人。

前几篇 PostgreSQL 解释了快照怎样保留旧答案、索引怎样找到正确版本。今天把问题推进一步：每笔事务都拥有稳定视图，为什么仍然不能保证它们一起做对事？我们固定讨论 PostgreSQL 18 的普通持久表。MVCC 负责版本与快照，行更新有自己的冲突控制；今天的 Serializable Snapshot Isolation，简称 SSI，接在读取、写入及提交的路径上，判断一组事务的相互依赖是否允许它们同时成功。

先把教学模型说清楚。表 roster 只有甲、乙两行，on_call 初始都为 true。A 处理甲的申请，B 处理乙的申请，两者都先读人数，再按结果决定是否更新自己；没有其他写者、显式行锁或额外业务约束。首先让它们使用 Repeatable Read，在任何一笔更新之前分别通过首次 SELECT 建立快照。以下时序与结果是根据语义推演，没有运行数据库，也不把图当成真实事务追踪。

A 查询 `WHERE on_call` 的人数，得到 2；B 同样得到 2。A 据此把甲改成 false，B 把乙改成 false。两笔事务更新不同的行，不会仅因为这两次更新发生同一行写冲突。Repeatable Read 继续给各自保留原来的读取视图，也没有自动把“另一人在岗”变成提交前要重新核实的条件。在本例时序中，两者可以都提交，最终甲=false、乙=false。这类用同一份旧状态作判断、却分散修改不同记录的异常，通常叫写偏斜。[稳定快照仍允许序列化异常](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)

观察第一幅图：两个写入目标完全不同，为什么仍然影响同一条业务规则？

![教学时序：初始甲、乙均在岗，人数为 2。A、B 都在任何更新前读取人数 2；A 只把甲改为离岗，B 只把乙改为离岗。Repeatable Read 下这两笔不同目标的更新可同时成功，最终人数 0。向下箭头表示事件推进；这是状态推演，不是运行记录。](assets/figures/pg-ssi-write-skew.svg)

问题不在单行的新旧版本选错，而在两个判断互相借用了对方尚未离岗的状态。若 A 完整执行后再执行 B，B 应读到 1，拒绝乙下班；若 B 在前，A 就应拒绝甲下班。两种串行顺序都不可能产生“双方都批准”。因此，需要保住的不只是读者自己的稳定视图，还包括：成功事务的整体效果，应当能解释成某一种逐笔执行的顺序。这里的“串行化”是结果契约，不要求数据库真的一次只运行一个事务。

最自然的办法，是让整个值班组的申请统一排队，前一个读完、更新并结束后，下一个才开始读取。访问入口统一、竞争集中在一个小组时，这很直接。但若所有组共用一个队列，互不相关的请求也要等待；按组组织互斥，又要保证每条修改路径都遵守约定。传统严格锁协议也可以通过保护读写范围实现串行化，只是要承担等待与死锁处理。SSI 选择保留快照读的并发性，增加依赖监测，必要时撤销一次尝试。[PostgreSQL 对串行化实现策略的设计说明](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/README-SSI#L73)

关键洞察来自“我为什么必须排在你前面”。A 读到了乙仍在岗的旧版本，而 B 把乙改成离岗；若要把 A 的这次读取解释为串行执行，A 就必须在 B 前。记一条 `A → B`，箭头从读者指向改变了这份读取依据的写者。反过来，B 读到甲仍在岗，A 修改甲，又要求 `B → A`。这类边称为读写反依赖，简称 rw：它记录的是读者没有看见并发写者的修改，并不是读者读到了写者的新值。

第二幅图中的两条箭头都成立时，能否给 A、B 排出一个满足要求的顺序？

![教学依赖图：A 读乙在岗、写甲离岗；B 读甲在岗、写乙离岗。A 到 B 的 rw 箭头表示 A 读到的旧乙要求 A 在 B 前；B 到 A 的箭头表示旧甲又要求 B 在 A 前。箭头表达串行顺序约束，不是消息发送、等待或提交先后。两个要求组成环，无法同时满足。](assets/figures/pg-ssi-dependencies.svg)

不能。先排 A 会违反 B→A，先排 B 会违反 A→B。图把错误从“人数变成零”追到了更一般的结构：读取依据与写入之间构成了循环顺序要求。也因此，仅检查写集合是否重叠不够；两笔事务虽然没有写同一行，仍然可能通过读集合相互制约。[rw 方向与依赖环的源码说明](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/README-SSI#L136)

实现怎样知道“某人读过这里”？PostgreSQL 用 SIREAD 记录读取覆盖的对象，在 pg_locks 中可见的模式名是 SIReadLock。它与普通排他锁职责不同：不会因为记录了读取，就阻塞随后写入；它帮助写者发现自己碰到了并发读者的依据。若写入先发生，后来的读取也能结合 MVCC 信息发现相应依赖。读取、写入两侧配合，才能覆盖两种先后次序。[SIREAD 的用途与不阻塞性质](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/predicate.c#L26)

保护范围也不能只限于已经返回的行。假设程序检查“某个时段没有其他申请”，查询返回空集合，别人插入一条符合条件的记录，仍会改变判断依据。实现因此要通过页、索引范围乃至整张表的对象来覆盖查询谓词，具体粒度取决于实际访问路径，并不等于把 SQL 条件原样存成字符串。细粒度记录太多时还能合并成粗粒度，以控制内存；代价是某些实际上互不影响的操作也可能被保守地视为相关。[谓词覆盖范围与记录粒度](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/predicate.c#L33)

不过，不能把第二幅教学图误写成“PostgreSQL 保存所有依赖，每次完整找环”。SSI 利用快照隔离的性质，监测由两条相邻 rw 边构成的危险结构，再结合提交顺序等条件决定是否中止事务。环一定包含所需结构，但所监测的结构未必最终成环，所以可能发生保守中止。单独一条 rw 边也不意味着一定失败；许多读写交错本来就能排出合法顺序。PostgreSQL 18.0 固定提交 `3d6a828` 的设计说明与冲突检查把这个取舍写得很清楚。[危险结构与保守检测](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/README-SSI#L166)、[新增依赖时的检查](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/predicate.c#L4517)

回到值班组，改用下面的业务骨架。它是伪代码，count 的结果由应用判断；不能把 if 行直接当成 SQL 执行。

```text
BEGIN ISOLATION LEVEL SERIALIZABLE
n = SELECT count(*) FROM roster WHERE on_call
if n > 1:
    UPDATE roster SET on_call=false WHERE name=申请者
else:
    本次业务结果 = 拒绝下班
COMMIT
```

A、B 仍可以先读到 2，再并发准备更新；SSI 不能允许刚才那种双方批准的执行都成功提交。为追踪后续，第三幅图选取一种允许的结局：A 提交成功，B 的尝试收到 SQLSTATE `40001`，需要回滚并开始新事务。检测可能发生在语句执行或提交阶段，不能据此预测任意调度里固定由 B 失败。[失败处理及完整重试要求](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)

重试要保留“乙申请下班”的意图，丢弃旧的批准依据。B′ 取得新快照，读到甲已离岗、乙仍在岗，人数为 1；应用按同一规则拒绝乙下班，不再写 false，然后正常结束。最终一人在岗，两个请求都得到了确定结果，但并非两人都获准离岗。第三幅图要看清楚：什么是数据库冲突失败，什么是重试后正常得出的业务拒绝？

![教学时序：取一种允许的结局，A 提交、甲离岗；B 的旧尝试因序列化冲突失败并回滚。B′ 重新开始事务，读到甲离岗、乙在岗，人数 1，按业务规则拒绝乙下班并结束。最终乙继续值班。箭头表示重试步骤，不承诺真实调度的固定失败者或报错时机。](assets/figures/pg-ssi-retry.svg)

若只重发旧 UPDATE，或者在新事务中沿用“刚才人数是 2”的判断，就绕过了机制要保护的因果关系。需要重试的是整段读取、判断、写入逻辑，并为持续竞争设置合适的重试与等待策略。对外宣告“下班已批准”等不可撤回动作，也不能仅凭事务中暂时读到的结果提前完成；应等提交成功，并另行处理外部动作的可靠交付。

此时不变量有两层。应用的每笔事务在串行执行时都必须保持“人数至少为 1”；数据库保证成功的相关 Serializable 事务能按某个串行顺序解释。两者结合，才保住业务规则。SSI 不理解“值班”这个词，也不会替不检查人数、直接改状态的程序发明约束。依赖这项保证的相关访问还必须一致采用 Serializable，不能只升级一个入口，就假定其他较弱隔离级别的修改也自动获得同样保护。[SSI 的适用范围与混用边界](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/README-SSI#L208)

成本转移到了读取记录、依赖跟踪与重做。某些 SIREAD 信息在事务成功提交后仍有必要保留，直到重叠事务不再需要它们；否则 A 刚提交就擦掉读取痕迹，仍在运行的 B 可能无法补齐依赖。长事务与较多并发事务因此会增加维护压力。热点组频繁竞争时，反复重算也可能比直接排队更贵。SIREAD 不阻塞写者，不等于数据库没有普通锁或所有执行都不会等待。[记录生命周期与资源约束](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/storage/lmgr/predicate.c#L38)

这与前面的 RocksDB 乐观事务有具体联系：二者都区分“旧答案还可以读”与“依据它做出的决定还可以提交”，把等待的一部分换成记录、检测和失败重做。但那篇按登记的键及修改序号校验，普通 Get 不自动登记读取依赖，更不能直接保护 SQL 范围中的未来记录；这里要根据 SQL 访问跟踪谓词相关依赖，判断能否共同串行化。不能把一个单键的 GetForUpdate 当成完整 SSI，也不能把所有 SSI 失败都理解为“我读过的任意键只要变了就中止”。[RocksDB 的事务读取与校验边界](https://github.com/facebook/rocksdb/wiki/Transactions)

最后独立推演：如果只运行 A、没有 B，人数会怎样变化？如果 B 读取甲在岗，却只写一份不影响 A 判断的日志，是否仅凭“发生并发读写”就能断言必须失败？这个设计值得欣赏之处，是把“各自正确”与“共同存在一个合理顺序”明确分开，用可监测的依赖关系保护后者，同时承认检测、重试和保守中止的代价。本文核对官方文档与固定源码，没有运行 PostgreSQL、采集锁或依赖事件、注入故障或测量吞吐；状态图与失败结局都是教学推演。
