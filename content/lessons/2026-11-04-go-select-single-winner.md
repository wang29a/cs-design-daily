# Go：同时等待结果和取消，怎样只选中一条分支

昨天，一个发送者把 42 直接交给等待中的 goroutine，再让它恢复调度。但真实请求常常有两个出口：后台算好了就取结果，用户取消了就离开。结果与取消可能几乎同时到达。今天理解 Go 怎样让同一个任务参加多条 channel 的等待，却只兑现其中一次通信，并妥善撤回其他登记。

位置仍在 Go 运行时内部。channel 保存通信和等待状态，调度器维护 goroutine 的执行资格，编译器把 select 的分支信息交给运行时。Go 的 select 是选择 channel 通信的语言结构，不是 Linux 同名的文件描述符接口。本文固定 Go 1.25.0 官方提交 `6e676ab2`，分析两条不同 channel、两个接收分支、没有 default 的普通阻塞路径。图和交错均是静态源码支持的教学模型，没有执行 Go 程序或测量竞争概率。

设 `c := make(chan int)` 传结果，`done := make(chan struct{})` 表达取消，两者都无缓冲。GS 负责发送 42，GX 最多关闭一次 done，GR 执行以下片段；answer 仅由 GR 使用。

```go
select {
case v := <-c:
    answer = v * 2
case <-done:
    answer = -1
}
```

选结果就得到 84，选取消就得到 -1。初始两个 channel 都打开，GS 尚未发送，GX 尚未取消。关闭空的 done 会让接收可立即推进，适合作为不携带业务值的信号；它不等于强行终止另一个任务。这里不关闭 c，也不加入超时、nil channel 或重复 channel 的分支。[关闭后的接收语义](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/doc/go_spec.html#L5300)

## 多登记几处，为什么还需要一个共同决定

最自然的方案，是先阻塞接收 c，再检查 done。但 c 的结果若永远不来，取消已经发生也轮不到检查。改成不断轮询两个对象，又重新占用了本可交给其他任务的执行机会。也可以各开一个辅助 goroutine 代收，再把答案汇总；这会增加任务、转发和退出责任，而且必须处理两个辅助任务都完成、其中一个无人接收的情形。

select 把“一起等待这些可能性”的责任交给运行时。语言规定只选择一个可推进的通信，然后执行对应分支；若都不能推进且没有 default，就阻塞。若检查时多个分支均可推进，规范要求在可行分支间作均匀伪随机选择，源码顺序不是优先级。因此把取消分支放在第一行，不会自动获得取消优先的业务协议。[select 的执行规则](https://go.dev/ref/spec#Select_statements)

固定版本实现先生成打乱的检查顺序，再按稳定顺序取得所涉及 channel 的锁。两种顺序承担不同职责：前者服务通信选择，后者防止两个 select 分别拿着 c、done 的锁互相等待。全都锁住以后，GR 先寻找已经可完成的通信；只有确认没有任何分支可行，才进入登记等待。[检查顺序与锁顺序](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/select.go#L167)，[持锁复查](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/select.go#L251)

GR 为 c、done 分别建立一条 sudog 等待记录，记为 Sc、Sd，挂入各自接收队列。每条记录都指向 GR，并标为来自 select；记录还串在 GR 自己的等待链上，以便恢复后找齐。Sc 携带接收 42 的目标槽位，实际编译器可能先用临时槽位再赋给 v，本文不把目标地址当作语言保证。登记的是两份候选交接，不是创建了两个 GR。[多队列登记](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/select.go#L309)

![图一：教学模型中 c.recvq 的 Sc 与 done.recvq 的 Sd 都指向同一个等待任务 GR，二者共同受 GR.selectDone 标记仲裁；细箭头表示引用，0 表示本轮尚无人取得唤醒资格。](assets/figures/go-select-registration.svg)

c 的锁只能保护 c，done 的锁只能保护 done。GS、GX 可以在不同线程上分别持有这两把锁，各自看见一条等待记录。如果双方仅凭“我的队列里有人”就交付、唤醒，就会争着覆盖 GR 的交接结果，甚至重复尝试把同一个 G 置为可运行，破坏调度状态约束。需要跨越两条队列的共同不变量：**本轮 select 的所有登记，共用至多一个获胜资格。**

Go 把这枚标记放在 G 上，字段名为 `selectDone`。对于来自 select 的等待记录，队列取出操作必须尝试原子地把它从 0 改成 1；比较与修改合为一次操作，只有第一方成功，失败者跳过这条过期候选。标记不是 answer，也不是 goroutine 已退出的证明，只表示本轮已有一方取得交接与唤醒资格。[等待记录的约定](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/runtime2.go#L348)，[出队时争取资格](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L886)

## 结果先取得资格，取消就不能改写这次选择

还不能在登记后随意解锁再睡下，否则对方可能过早唤醒尚未停妥的 G。Go 沿用上一讲的停车协议：先进入 Waiting，再由 `selparkcommit` 设置有关栈引用的保护状态并释放 channel 锁。不同于单 channel，这次提交回调需要沿等待链释放多把锁；释放后已有操作可能让 GR 立即恢复，因此它也不能随意访问可能已被恢复路径清理的状态。[多 channel 等待的提交](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/select.go#L63)

现在选定一条合法交错。GR 已等待，GS 先拿到 c 的锁，从接收队列摘下 Sc，把 GR 的标记从 0 改成 1，取得资格；随后直接复制 42，记录成功、释放锁并唤醒 GR。这仍不意味着 GR 马上执行。GX 趁 GR 尚未恢复时关闭 done，关闭路径也从接收队列取 Sd，因同一枚标记已经是 1，争取失败，跳过 Sd，不再替 GR 写入取消结果或再次唤醒。[结果交接](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L318)，[关闭 channel 时处理等待者](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/chan.go#L414)

看下一幅图：done 已经关闭，为什么 GR 最后仍然得到 84？哪一步决定了它，哪一步只是稍后执行这个决定？

![图二：选定 GS 先取得 Sc 的交接资格并交付 42、GX 随后关闭 done、GR 最后恢复的教学顺序。GX 对共享标记的竞争失败；GR 确认获胜记录并完成清理，执行结果分支得到 84。箭头表示动作先后，不是实际计时。](assets/figures/go-select-winner.svg)

关键是选择已经发生，后来的取消不能追溯撤销这次通信。GR 恢复以后重新取得所有相关 channel 的锁，读取唤醒方留下的获胜记录，再清理本轮等待链。有些落选记录仍在安静 channel 的队列中，需要主动移除；本例 Sd 已被关闭路径摘掉，清理就识别它已离队，而不是再制造一次取消。两条等待记录最终都要释放，之后运行时把选中的分支交回编译器生成的控制流，GR 用收到的 42 算出 84 并结束这次处理。[恢复、撤销落选登记与释放记录](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/select.go#L354)，[处理已离队记录](https://github.com/golang/go/blob/6e676ab2b809d46623acb5988248d95d1eb7939c/src/runtime/select.go#L627)

这解释了为什么“只唤醒一次”还不够。如果只宣布赢家，永不撤回安静队列里的落选记录，重复执行 select 就会积累无效登记，保留过期引用和后续遍历工作。恢复时重置标记也必须与清理处在所有相关锁的保护下，不能在队列还可被并发操作时把旧登记重新变成有效候选。漂亮之处是把多处候选与唯一执行责任分开表示，再为落选关系安排明确的回收阶段。

## 选择替你收尾登记，不替整个请求系统收尾

这套结构让业务用一段顺序代码表达多路等待，成本是分支记录、锁排序、多把锁的同步以及恢复后的清理。分支多，就要检查和管理更多候选；把很多热点 channel 塞进同一个 select，也不会免费消除争用。只需一个 channel 的简单通信仍有更直接的路径，没有必要为了形式统一引入多路选择。

更重要的是，本轮唯一选择不等于系统里的所有后台任务都结束。若改成 GX 先赢，GR 选择 -1 并离开，而 GS 随后只做 `c <- 42`，在没有其他接收者的条件下，它可能一直等下去。撤回的是 GR 的接收登记，不是 GS 的发送责任。一个配合取消的生产者可以这样表达交付阶段：

```go
select {
case c <- 42:
case <-done:
    return
}
```

当 GR 已取消且没有其他接收者，结果发送无法推进，关闭的 done 让 GS 退出。但这只为交付增加退出路径，不会中断此前已经开始的昂贵计算，也不承诺任意交错下取消总是先赢。可以先推演一个独立问题：GR 进入 select 前，GS 已准备发送，done 也已关闭，把取消分支移到最上面，是否足以让 answer 必为 -1？先按规范判断，再解释业务若要求严格取消边界，还缺哪一种共同协调。

最后联系前面讲过的 epoll。两者都让一个执行者等待多个对象，减少逐个阻塞或忙等的需要；但 epoll_wait 可以交付多条就绪线索，应用随后才真正读写，也不因返回一个对象就撤销其余长期关注。这里的 select 要完成某一个 channel 通信，并结束本轮其他候选关系。共同结构是集中组织等待，边界差异则在于交付的是“值得尝试”，还是“已经选定并完成的一次通信”。这决定了为什么不能把普通事件通知直接当作唯一获胜的业务提交协议。[epoll_wait 的返回与批量事件语义](https://man7.org/linux/man-pages/man2/epoll_wait.2.html)
