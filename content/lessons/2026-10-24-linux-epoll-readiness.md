# Linux：连接大多在等待，怎样避免反复检查所有连接

假设你在写一个聊天服务。服务器维持着一万个连接，但某个时刻只有两个客户端发来消息。连接存在，不代表连接此刻有工作；大部分时间，它们只是等待网络。今天要理解的设计，是 Linux 怎样把“长期关心哪些连接”与“现在该处理谁”分开，让服务线程可以等待，醒来后集中处理有进展的对象。

最自然的办法，是为每个连接分配一个线程，直接阻塞读取。代码顺序清楚，连接不多时完全合理；不过大量线程需要维护栈和调度状态。另一种办法是把连接设为非阻塞，逐个尝试读取，没数据就换下一个。这样避免了在一个连接上卡住，却可能反复巡视大量没有变化的对象。`poll` 已经允许把一组描述符交给内核，没就绪事件时整体睡眠，并不是只能忙等；但每轮仍以整张数组表达关心的对象，内核检查数组，应用再找出哪些返回项需要处理。连接集合庞大且长期稳定、活跃对象很少时，反复重建和检查同一份关心关系，才是要进一步减少的工作。[poll 的数组与等待语义](https://man7.org/linux/man-pages/man2/poll.2.html)

沿前几天的 Linux 主线看，文件描述符把进程接到内核对象，socket 则把应用接到网络协议栈。`epoll` 位于这些对象的就绪通知机制与服务线程之间：它不负责解析聊天消息，也不替应用完成读取，而是组织“哪些对象值得再试一次”。这次只讨论一个线程管理普通非阻塞流式 socket 的成功路径，没有其他线程抢读，不使用嵌套 epoll、一次性通知或忙轮询；下文是教学推演及 Linux 6.12 静态源码核对，没有实际内核运行追踪或吞吐测试。

## 把反复提问，改成长期登记与变化通知

关键洞察是：连接集合与连接状态变化，具有不同的更新频率。集合不变时，可以保留关心关系，让对象通过既有的唤醒路径报告变化，再维护一个待检查的就绪集合。于是“我一直关心 A、B、C”和“现在 B 可能可读”，不必在每一轮重新表述。[epoll 的关注集合与就绪集合](https://www.man7.org/linux/man-pages/man7/epoll.7.html)

把一万个连接缩成三个，便于跟踪。A、B、C 对应描述符 7、8、9，起初接收缓冲都为空，对端也未关闭，接收低水位采用默认的 1 字节。[socket 接收低水位约定](https://man7.org/linux/man-pages/man7/socket.7.html)应用创建一个 epoll 实例 E，分别用 `epoll_ctl(ADD)` 登记 `EPOLLIN`，表示关心可读状态；返回事件的附带数据分别标记为 A、B、C。采用默认的水平触发模式，即不设置 `EPOLLET`。这些登记持续存在，直到修改、移除或相关对象生命周期结束，不需要每次等待都重新提交三条记录。[epoll_ctl 的登记、数据与默认模式](https://www.man7.org/linux/man-pages/man2/epoll_ctl.2.html)

现在 B 收到两个字节 H、i，A、C 保持原样。观察图中的两种关系：长期登记是否也要随着这两个字节一起消失？

图 1：虚线表示持续登记，实线表示此次通知与交付的顺序。省略网络收包细节、并发转交列表和错误处理，箭头不是实测调用追踪。

这不是内核另外开一个线程，替应用不停巡视所有连接。核对 Linux 6.12 的 `ep_insert`，可以看到它创建登记项，通过对象的 poll 接口安装等待队列回调，同时检查当前状态；`ep_ptable_queue_proc` 把 `ep_poll_callback` 接到目标对象的等待队列。登记时就已可读的对象，也不能因为没有发生“登记后的新变化”而被遗漏。[固定源码：登记与初次检查](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/eventpoll.c#L1618)，[等待队列回调的安装](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/eventpoll.c#L1413)

B 的就绪唤醒经过回调时，epoll 根据所关心的事件决定是否把相应登记项接入就绪路径，并在有等待线程时唤醒它。重复通知可以合并，已经排队的同一项无需每次再排一份。因此，就绪集合不等于网络数据包日志：收到两个包，不保证返回两个事件；返回 B，也不告诉应用消息有多少字节。它保存的是下一步工作的线索。[固定源码：ep_poll_callback](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/eventpoll.c#L1308)

## 通知留下的，是需要复查的责任

应用调用 `epoll_wait`，内核从就绪路径取出候选，重新检查对象当前状态，然后最多交付调用者指定的事件数。这里选择结果数组容量为 3，B 仍有 Hi，所以返回一项 B、`EPOLLIN`；A、C 不必作为这轮返回数组里的两个空白项出现。真实源码在扫描期间还用临时列表承接并发通知，不能把教学图里的一个框理解成整个实现只有一条简单队列。[固定源码：ep_send_events](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/eventpoll.c#L1817)，[epoll_wait 的返回边界](https://man7.org/linux/man-pages/man2/epoll_wait.2.html)

为什么还要复查？通知与读取之间有时间间隔，状态可能改变，通知也可能合并。应用仍须根据真正的 I/O 结果行动。非阻塞读取返回正数，才表示这些字节已经交给程序；返回 -1 且 `errno` 为 `EAGAIN`，表示当前没有可立即取得的数据；在本例这种流式连接上，以正数长度请求读取而得到 0，则表示接收方向到达 EOF。通知不预留数据，也不承诺一条业务消息已经完整到达。即使没有其他读者，TCP 字节流也可能只交来半条消息，解析器必须自己保留未完成状态。[read 的返回语义](https://man7.org/linux/man-pages/man2/read.2.html)

为了看清水平触发，故意让应用每次只读一个字节。第一次报告 B 后读到 H，缓冲里还剩 i。没有新包到达，第二次等待应不应该仍然报告 B？

![教学状态：B 收到 Hi 后成为候选；第一次 wait 返回 B，读 H 后剩 i；第二次 wait 仍返回 B，读 i 后缓冲为空；第三次 wait 复查 B 已不可读并移出候选，然后等待。A、C 始终无新数据且未关闭。](assets/figures/linux-epoll-level.svg)

图 2：按时间从上到下。候选表示内核仍要复查的项，不表示缓冲必然非空；应用读取和内核维护候选列表是不同动作。

水平触发的承诺是：条件仍满足，就可以继续报告。Linux 在交付 B 时，把这种登记项重新放回就绪列表，以便下次等待再次检查。第二次检查发现 i 仍在，于是再次报告 B；应用读出 i。特别注意，此时缓冲虽然空了，B 仍可能留作候选，读取不会神奇地同步删掉那一项。第三次等待重新检查，确认没有数据、EOF 或错误等可报告条件，才把它过滤掉并继续等待。这正说明为什么“就绪列表”更适合当作需要复查的责任，而不能当作永久准确的状态快照。[固定源码：复查与水平触发重新排队](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/eventpoll.c#L1865)

若改为边缘触发，不能期待残留的 i 仅因“仍未读完”就持续产生下一次报告。应用通常应采用非阻塞 I/O，处理到 `EAGAIN` 再依赖后续通知；如果为了公平性提前让出 CPU，就要自己保存尚需继续处理的工作，不能把它遗忘。这是通知责任的一次重新分配，不是给同一段代码加一个“更快”的开关。[边缘触发的处理约定](https://www.man7.org/linux/man-pages/man7/epoll.7.html)

## 真正困难的边界，是检查完以后能否安心睡眠

把第三次等待继续推演：线程看见候选为空，正准备睡眠，C 恰好收到一个字节。如果先检查、再不受保护地登记等待，中间到来的通知可能发现“没人等待”；线程随后睡下，却再也没有新数据来唤醒它。C 明明有事，整个服务仍可能停在等待里。**确认无事与建立可被唤醒的等待关系，不能留下一个双方都不负责的窗口**，这是比“用了队列”更关键的不变量。

Linux 6.12 的 `ep_poll` 在受锁保护的区间设置线程等待状态、最终复查事件，并在确实没有事件时加入等待队列；回调一侧也在同一把读写锁保护下发布候选并检查等待者。若 C 的通知先完成，最终复查能发现它；若线程先完成等待登记，回调就能唤醒它。即使唤醒发生在线程真正让出 CPU 之前，线程状态协议也要保住这次唤醒。这里压缩的是同步关系，不是建议应用照抄几行无锁检查。[固定源码：ep_poll 的最终检查与等待](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/eventpoll.c#L2039)

这个设计减少了对大量静止对象的反复检查，却增加了长期登记项、回调连接和就绪管理的内核内存与同步成本。登记和删除仍有工作，返回许多活跃对象仍要逐项处理；连接频繁增删或几乎全部活跃时，收益会改变，不能用一句“epoll 是 O(1)”替代判断。更不能在唯一的事件循环里长时间做计算或阻塞读盘：通知机制没有替业务提供 CPU 时间或消除所有等待。昨天的普通文件读取就属于另一种边界，普通磁盘文件通常不能这样注册到 epoll，`epoll_ctl` 可以返回 `EPERM`。[epoll 支持范围与登记限制](https://www.man7.org/linux/man-pages/man2/epoll_ctl.2.html)

结束一个连接时，应用还应撤销关注、关闭描述符并管理自己的连接对象生命周期；本文不引入 `dup`、`fork` 或批量返回事件里残留标记的复杂情况。可以留下两个独立推演：如果 B 一直可写，而应用没有待发送数据却始终关注可写，事件循环还容易睡下吗？如果 C 的对端关闭发送方向，服务端把每次读到 0 都当作“暂时没有数据”，会留下什么永远无法完成的工作？先用状态解释，再考虑代码。

这条设计在 Go 的网络运行时中又多接了一层。按本次查阅的 Go 官方源码（2026-10-24）：Linux 版网络轮询器把 epoll 返回的对象交给 `netpollready`，运行时再把等待相应读写条件的 goroutine 转成可继续调度的任务。共同结构是把大量等待者与少量当前可推进者分开；不同处在于 epoll 交付文件对象的就绪线索，Go 还维护 goroutine 的等待状态与调度关系。内核报告可读，依然不等于 goroutine 已经运行，更不等于业务请求完成。漂亮之处，是每一层只承担自己能兑现的承诺，而下一层明确接过继续推进的责任。[Go 官方网络轮询器源码](https://go.dev/src/runtime/netpoll_epoll.go)，[平台无关的等待与就绪状态](https://go.dev/src/runtime/netpoll.go)
